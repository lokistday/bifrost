Python 객체와 자료 계약

목록은 값의 순서를, 딕셔너리는 키와 값의 관계를 표현합니다. 변수가 같은 변경 가능한 객체를 가리키는지와 값이 같은지를 구분하세요. JSON의 true는 Python bool로 읽힙니다.

a = [{"count": 1}]
b = a.copy()
b[0]["count"] = 2
print(a[0]["count"])
print(type(True) is int)

직접 확인: 딕셔너리 안에 목록을 넣고 얕은/깊은 복사 후 원본을 비교하세요.

판단 기준과 실행 안내

2와 False입니다. 바깥 목록을 복사해도 안쪽 딕셔너리는 공유됩니다. 정수 계약에 bool을 받지 않으려면 타입을 구분합니다.

이어지는 차시: 변경 가능한 자료와 방어적 복사 · JSON 파싱과 데이터 계약

C의 객체·구조체·파일 디스크립터

포인터는 객체의 주소를 담으며 객체의 수명을 늘려 주지 않습니다. 구조체는 필드를 묶지만 패딩 때문에 sizeof가 필드 크기 합과 다를 수 있습니다. 파일 디스크립터는 바이트 버퍼 주소가 아니라 프로세스의 열린 파일 참조 번호입니다.

#include <stdio.h>
struct pair { char kind; int count; };
int main(void) {
    struct pair p = {'A', 3};
    struct pair *q = &p;
    q->count = 4;
    printf("count=%d size=%zu\n", p.count, sizeof p);
    return 0;
}

직접 확인: p를 직렬화할 때 메모리를 통째로 복사하지 않고 필드 폭과 순서를 정해야 하는 이유를 쓰세요.

판단 기준과 실행 안내

bridge.c에 저장하고 gcc -std=c11 -Wall -Wextra bridge.c -o bridge && ./bridge로 실행합니다. count=4이고 size는 ABI에 따라 달라질 수 있습니다. q->count와 p.count는 같은 객체의 필드입니다.

이어지는 차시: C 컴파일과 주소·포인터 · 구조체 배치와 명시적 직렬화 · 파일 디스크립터·dup·공유 오프셋

문자·바이트·엔디언

화면 글자 수·문자열 길이·바이트 길이를 혼동하지 않습니다. 숫자 바이트에는 폭과 순서를 명시하고, 같은 바이트의 signed/unsigned 해석을 구별하세요.

raw = bytes.fromhex("0100")
print(int.from_bytes(raw, "big"))
print(int.from_bytes(raw, "little"))
print(len("가"), len("가".encode("utf-8")))

직접 확인: 00ff를 big/little-endian으로 예측하고 중간 NUL이 있는 문자열과 이진 데이터도 비교하세요.

판단 기준과 실행 안내

256, 1, 그리고 1 3입니다. 숫자 폭·바이트 순서·텍스트 인코딩은 별도 계약입니다.

이어지는 차시: 문자열·바이트·UTF-8의 경계 · 바이트 순서와 길이 필드 복원 · 바이너리 길이와 중간 NUL

요청과 인증·인가의 경계

브라우저가 보내는 값은 요청입니다. 요청자의 신원은 신뢰한 세션 검증으로 정하고, 소유자와 권한은 서버가 가진 상태를 기준으로 확인해야 합니다. HTML 해석·CORS·CSRF는 각각 다른 경계입니다.

주체 확인 → 대상 조회 → 행동 권한 확인 → 입력 계약 확인 → 상태 변경 → 응답
실패한 요청 → 상태 유지 + 필요한 최소 오류 정보

직접 확인: 정상 주체·타인 자원·알 수 없는 필드를 조합한 4칸 시험표를 쓰세요.

판단 기준과 실행 안내

클라이언트의 owner=alice 값을 신뢰해 권한을 정하면 안 됩니다. 세션이 유효하다는 사실만으로 다른 사용자의 자원 수정이 허용되지 않습니다.

이어지는 차시: 쿠키·세션·인증 · 리소스 단위 인가 · 요청 계약과 Mass Assignment

관찰·추론·미확인을 분리하기

원시 자료에서 읽은 필드와 그 필드로 세운 가설은 다른 종류의 문장입니다. 시간 순서는 인과가 아니며 로그가 없다는 사실도 수집 범위를 확인하기 전에는 행위 부재의 증명이 아닙니다.

관찰: E3에 session=S7, event=read가 기록됨
추론: 같은 호스트의 로그인과 연결될 가능성
미확인: 실제 사용자 의도·파일 외부 반출
추가 자료: 세션 발급 이력·파일 내용·송신 기록

직접 확인: 실패 로그인 뒤 성공 로그를 보고 사실 2개·가설 2개·추가 자료 2개를 작성하세요.

판단 기준과 실행 안내

모든 결론에 자료 위치를 붙이고 가능한 대안 가설을 하나 이상 남깁니다. ±5초인 두 이벤트의 구간이 겹치면 순서를 확정하지 않습니다.

이어지는 차시: 로그 필드와 사건 가설 · 호스트·세션을 잇는 다중 로그 상관 · 시계 오차·관측 범위·사건 순서

도달·권한·관측을 따로 보기

DNS로 목적지를 찾는 일, 경로로 도달하는 일, 요청 권한을 허용하는 일, 그 사건을 로그에서 보는 일은 서로 다릅니다. IPv4/IPv6와 왕복 경로도 따로 확인해야 합니다.

이름 해석 → 라우팅/연결 → 프로토콜 처리 → 신원/권한 → 업무 결과
센서·로그 수집은 각 단계에서 실제 관측 범위를 확인

직접 확인: DNS 성공·TCP 시간 초과·HTTP 403·감사 로그 누락을 각 단계와 추가 확인 자료로 분류하세요.

판단 기준과 실행 안내

사설 IP만으로 권한이 생기지 않고, 감사 enabled=true만으로 끝까지 전달됐음을 증명할 수 없습니다. 한 단계의 실패를 모든 단계의 실패로 뭉뚱그리지 않습니다.

이어지는 차시: IP·포트·DNS와 전송 · 최장 접두사와 돌아오는 경로 · 프라이빗 엔드포인트와 DNS 경로
