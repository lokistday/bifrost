01 / UNDERSTAND

먼저 이해하기

파일 확장자와 내부 형식은 다를 수 있으므로 바이트 시그니처와 구조를 확인합니다. 그러나 서명 몇 바이트가 일치한다고 완전한 파일이나 진짜 문서라고 확정할 수는 없습니다. 다른 데이터 안에 우연히 같은 바이트가 나타나는 거짓 후보도 있습니다.

앞부분의 원리 실습은 BF 서명 2바이트와 little-endian 길이 2바이트 뒤에 본문이 오는 가상의 작은 형식을 사용합니다. fragments.hex는 실제 삭제 영역이나 디스크 이미지가 아니라 제작한 15바이트 표본입니다. Hex 텍스트를 bytes.fromhex로 바꾼 뒤 0부터 세는 오프셋에서 검색합니다.

첫 후보는 오프셋 2에서 BF, 길이 3, 본문 ABC가 전부 있습니다. 두 번째는 오프셋 10에서 길이 5를 선언하지만 뒤에 XY 2바이트만 있어 INCOMPLETE입니다. 선언 길이를 믿고 없는 바이트를 복원했다고 쓰지 않으며, Python 슬라이스가 짧아져도 오류가 안 난다는 점을 확인합니다.

carving은 파일시스템 메타데이터가 부족할 때 구조 단서로 후보를 찾는 접근입니다. 조각화·압축·암호화·덮어쓰기에서는 단순 연속 검색이 실패할 수 있고 원래 이름·경로·생성 시각은 보통 별도 근거가 필요합니다. casework.py는 구조 검사의 첫 단계만 보여 줍니다. 뒤의 signature_lab.py 실제 PNG 실습과 구분합니다.

Hex 두 자리는 한 바이트입니다. 0부터 세는 오프셋 00000008은 아홉 번째 바이트입니다. Hex 10은 십진수 16입니다. Hex 덤프의 왼쪽은 위치, 가운데는 바이트, 오른쪽은 인쇄 가능한 ASCII 문자입니다. 점은 화면에 표시하기 어려운 바이트이며 실제 점 문자라는 뜻이 아닙니다.

PNG는 89 50 4e 47 0d 0a 1a 0a의 8바이트로 시작합니다. 그 뒤 청크는 길이 4바이트(big-endian), 종류 4바이트, 데이터, CRC 4바이트입니다. IHDR은 이미지 속성, IDAT는 압축 픽셀, IEND는 끝을 나타냅니다. CRC는 청크 종류와 데이터에 대해 계산하며 출처나 작성자 신뢰를 증명하지 않습니다.

JPEG의 ff d8 ff와 ZIP 로컬 헤더의 50 4b 03 04도 식별 단서입니다. 모든 ZIP이 이 접두로 시작하는 것은 아니며 빈 ZIP·자기추출형 등 변형이 있습니다. 이 실습은 JPEG/ZIP의 접두 후보만 표시하며 내부 전체 검증은 하지 않습니다. PDF는 %PDF-라는 단서와 내부 객체 구조를 함께 검토해야 하고, 각 형식을 단일 푸터 검색으로 복구할 수 있다고 일반화하지 않습니다.

signature_lab.py는 실제 형식으로 제작한 2×2 PNG/JPEG와 ZIP, 확장자만 다른 PNG, 잘린 PNG, CRC 오류, 헤더만 있는 표본을 제공합니다. PNG 검사는 64×64 이하 RGB8 비인터레이스 교육 계약에 한정됩니다. 지원하지 않는 정상 PNG도 UNVERIFIED일 수 있습니다. 정상 판정은 악성 여부·제작자·사건 발생을 증명하지 않습니다.

원본 fixtures는 보존하고 setup으로 새 작업 폴더를 만듭니다. carve는 mixed.bin의 오프셋 17에 들어 있는 연속 PNG를 구조 검사 뒤 새 파일로 추출합니다. 원본 PNG와 바이트·SHA-256을 비교하고 이미지 뷰어로 여는 단계를 함께 수행합니다. 조각화된 파일·원래 이름·삭제 시각을 복원하는 범용 복구기가 아닙니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
python3 casework.py carve

변경 전 예상 결과와 해석

offset=2 declared=3 available=3 COMPLETE
offset=10 declared=5 available=2 INCOMPLETE

이제 단계별로 바꾸고 관찰하기

  1. 원시 바이트 길이와 오프셋 확인

    Hex 문자는 두 글자가 한 바이트입니다. 표본을 디코드한 뒤 헤더 후보 위치를 계산하고 실행 결과와 대조합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
    python3 casework.py carve
    관찰할 결과
    offset=2 declared=3 available=3 COMPLETE
offset=10 declared=5 available=2 INCOMPLETE

  2. 부족한 본문을 사본에서 채우기

    사본의 마지막에 5a3132를 붙입니다. 기존 XY에 Z12가 이어져 두 번째 후보 길이가 5가 됩니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
    python3 casework.py carve --source fragments-work.hex
    관찰할 결과
    첫 후보는 그대로이고 둘째는 offset=10 declared=5 available=5 COMPLETE입니다.

  3. 서명 없는 자료와 비교하기

    다른 사본을 00010203만 있는 Hex로 만듭니다. 후보가 없다는 결과와 데이터 자체가 없다는 주장을 구분합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
    python3 casework.py carve --source fragments-none.hex
    관찰할 결과
    출력 행이 없고 종료 상태 0입니다. 이 검색 방식의 BF 후보가 없다는 뜻입니다.

  4. 실제 형식의 작업 표본 생성

    가상 BF의 원리를 실제 파일로 연결합니다. forensic 폴더에서 실행하며 기존 폴더를 덮어쓰지 않습니다. Windows는 python3 대신 py -3를 사용하세요.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
    python3 signature_lab.py setup signature-work
    관찰할 결과
    created=8 files. 다시 같은 폴더로 실행하면 종료 상태 2로 거부됩니다.

  5. 헤더·청크·확장자를 대조

    image.png와 renamed.txt는 동일한 PNG 바이트입니다. 첫 청크 길이 00 00 00 0d는 십진수 13이고 다음 49 48 44 52는 IHDR입니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
    python3 signature_lab.py inspect signature-work/image.png
python3 signature_lab.py inspect signature-work/renamed.txt
python3 signature_lab.py inspect signature-work/photo.jpg
python3 signature_lab.py inspect signature-work/notes.zip
    관찰할 결과
    두 PNG의 SHA-256과 PNG_CONTRACT_VALID 결과가 같습니다. JPEG/ZIP은 CANDIDATE이며 전체 검증이 아닙니다.

  6. 접두가 같아도 구조 검증은 실패

    아래 세 파일은 PNG 헤더가 있지만 각각 잘림·CRC 오류·청크 누락이 있습니다. inspect 종료 상태 0은 보고 완료를 뜻하며 파일 정상 판정이 아닙니다. PNG_UNVERIFIED 행의 원인을 읽습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
    python3 signature_lab.py inspect signature-work/truncated.png
python3 signature_lab.py inspect signature-work/bad-crc.png
python3 signature_lab.py inspect signature-work/prefix-only.png
    관찰할 결과
    각각 PNG_UNVERIFIED로 표시되고 잘림, CRC mismatch, IEND missing 등의 원인이 구분됩니다.

  7. 추출 뒤 원본과 독립 대조

    출력 파일은 새 이름이어야 합니다. 추출한 파일을 이미지 뷰어로 열고 Python으로 바이트와 해시를 비교합니다. 동일성 확인과 출처 확인은 구분합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
    python3 signature_lab.py carve signature-work/mixed.bin signature-work/recovered.png
python3 -c "from pathlib import Path; import hashlib; a=Path('signature-work/image.png').read_bytes(); b=Path('signature-work/recovered.png').read_bytes(); print(a==b, hashlib.sha256(a).hexdigest()==hashlib.sha256(b).hexdigest())"
    관찰할 결과
    offset=17, 두 비교 모두 True. 기존 출력 파일은 덮어쓰지 않습니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

실제 표본 7종의 확장자·첫 8바이트·구조 판정·근거를 표로 정리하세요. mixed.bin에서 PNG를 새 파일로 추출하고 원본과 해시를 대조합니다. BF 표본의 길이 변경 실험과 실제 PNG의 청크 검증이 어떻게 다른지도 설명하세요.

막혔을 때 힌트 보기

오프셋은 Hex 문자열의 글자 위치가 아니라 디코드된 바이트의 위치입니다.

과제 해설과 예시 답안 보기
  1. 표본 끝에 5a3132를 붙여 두 번째 본문 길이를 2→5로 늘립니다.
  2. COMPLETE는 이 장난감 헤더/연속 길이 조건을 만족한다는 뜻만 적습니다.
  3. 파일명·경로·원래 문서·사용자·삭제 원인은 표본이 제공하지 않으므로 별도 파일시스템과 사건 근거가 필요합니다.
  4. SIGNATURE-GUIDE.md의 표를 채우고 실제 PNG 구조와 가상 BF 구조를 구별합니다.
  5. offset=17에서 추출한 바이트가 image.png와 같은지 독립적으로 비교하고 CRC 오류 표본은 추출하지 않습니다.

결과를 판단하는 기준

후보의 시작 오프셋·선언/실제 길이·불완전성·원래 메타데이터의 부재를 기록합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
