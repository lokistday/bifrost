01 / UNDERSTAND

먼저 이해하기

Linux 인증 자료는 배포판과 설정에 따라 텍스트 파일·journal·다른 수집기에 남을 수 있습니다. 이 차시는 sshd와 sudo 개념을 사용하는 독자적인 JSONL 표본이며 실제 auth.log나 journal 바이너리 파서가 아닙니다. 형식이 비슷해도 원본 필드와 정책을 확인해야 합니다.

인증 실패 L11과 성공 L12는 PID와 세션이 서로 다릅니다. 같은 사용자 이름의 연속 기록이라고 동일 프로세스의 재시도나 공격 성공으로 확정하지 않습니다. 호스트·사용자·세션과 UTC 정렬을 기준으로 뒤의 sudo 요청이 어느 선행 성공 기록과 연결되는지 확인합니다.

L13은 alice/S22의 선행 성공 기록과 연결되고 allow 요청입니다. L14는 bob/S23의 deny 요청이고 연결된 성공 기록이 없습니다. linked-login=True는 해당 키의 앞선 기록이 있다는 뜻이며, 지금도 세션이 활성이라는 증명이나 sudo 명령 실행 완료의 증거는 아닙니다.

sudo의 허용·거부와 실행된 프로그램의 실제 종료 상태·출력은 다른 관측 단계입니다. 원본 로그의 감사 설정과 수집 범위가 부족하면 기록의 부재를 활동 부재로 바꿀 수 없습니다. 이 도구는 현재 PC의 계정·sudo 권한을 조회하거나 명령을 실행하지 않습니다.

자주 헷갈리는 지점

allow를 명령 성공으로 번역한다.
요청 판정과 실행 결과 자료를 구분합니다.
로그인 기록이 연결되면 현재도 세션이 활성이라고 쓴다.
종료·재사용·수집 누락을 별도로 확인합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

JSONL 사본에서 L13의 session만 S99로 바꾸고 결과를 비교하세요. 명령이 실제로 성공했는지 확인하려면 어떤 추가 자료가 필요한지 두 가지 적으세요.

막혔을 때 힌트 보기

선행 로그인 연결 키는 host, user, session입니다. 요청의 allow를 명령의 성공 종료로 쓰지 마세요.

과제 해설과 예시 답안 보기
  1. L13 세션을 S99로 바꾸면 선행 성공 S22와 연결되지 않습니다. allow 자체는 유지됩니다.
  2. 실제 명령의 시작/종료 감사 자료, 종료 코드·출력 또는 프로세스 실행 기록을 요청합니다.
  3. 세션 종료·재사용·로그 누락은 이 표본에 없으므로 활성 세션과 명령 완료를 확정하지 않습니다.

결과를 판단하는 기준

인증 결과·세션 연결·sudo 허용·명령 완료를 네 단계로 구분한 기록이 있어야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

INDEPENDENT PRACTICE

도움 없이, 조건을 바꿔 보기

  1. 위 해설을 닫고 예상 결과와 근거를 먼저 적습니다.

  3. 새 반례 하나를 만들고 무엇까지 확인했는지 기록합니다.
