01 / UNDERSTAND

먼저 이해하기

TCP 애플리케이션은 바이트 스트림을 읽으며 한 메시지가 한 패킷과 같다고 보장되지 않습니다. 분석할 때 캡처 도착 순서대로 payload를 붙이면 순서가 뒤바뀐 조각이나 재전송을 잘못 해석할 수 있습니다. 각 바이트의 상대 위치와 중복 여부를 확인해야 합니다.

실습은 길이 8의 한 방향 스트림과 상대 offset을 제공합니다. 5번 조각이 먼저 와도 위치 0부터 재조립하면 BIFROST!가 됩니다. 동일 위치·동일 바이트의 중복은 결과를 두 번 늘리지 않습니다.

조각이 없으면 빈 위치를 임의의 문자로 채워 완전한 메시지처럼 보여주지 않습니다. 같은 위치에 다른 바이트가 오면 conflict로 표시하고 모형은 전체 텍스트를 보류합니다. 실제 수신자·분석기의 겹침 처리 차이가 있으므로 한쪽 해석을 무조건 정답으로 택하지 않습니다.

offset은 원시 TCP sequence number가 아니라 이미 정규화했다고 가정한 위치입니다. 연결 식별·sequence wrap·SYN/FIN·윈도·재전송 시간과 IP 조각 재조립은 구현하지 않았습니다. 이 작은 바이트 모형의 성공을 실제 PCAP의 완전성이나 TCP 구현 검증으로 주장하지 않습니다.

자주 헷갈리는 지점

패킷 한 개를 애플리케이션 메시지 한 개로 본다.
스트림과 애플리케이션 프레이밍을 따로 해석합니다.
누락 위치를 0으로 채우고 원문이라고 쓴다.
누락·가정과 복원 결과를 명확히 나눕니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

conflict 사례의 마지막 조각 58(X)을 46(F)으로 바꾸고 충돌이 사라지는지 확인하세요. gap과 conflict의 추가 수집 자료와 결론 유보 이유를 각각 적습니다.

막혔을 때 힌트 보기

offset 2의 원래 바이트는 F입니다. 같은 중복과 다른 겹침은 구분해야 합니다.

과제 해설과 예시 답안 보기
  1. conflict 사본의 마지막 hex를 46으로 바꿔 원래 F와 같게 만듭니다.
  2. 유일 바이트 8·누락 0·충돌 0과 BIFROST! 복원을 확인합니다.
  3. gap은 캡처 누락·관측 위치 등을, conflict는 원본 조각·수신자 정책·캡처 신뢰를 추가 검토하고 텍스트를 보류한다고 적습니다.

결과를 판단하는 기준

같은 바이트 중복은 무해한 재관측이지만 다른 겹침은 모호함입니다. 바이트가 채워져도 출처·연결 식별·원본 캡처 범위는 별도 검증합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
