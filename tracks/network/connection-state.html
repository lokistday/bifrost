01 / UNDERSTAND

먼저 이해하기

포트만 보는 정책과 연결 상태를 추적하는 정책은 판단 정보가 다릅니다. 허용된 새 연결이 시작되었는지, 역방향 패킷이 그 연결의 응답인지 확인하면 모든 인바운드 포트를 열지 않고도 응답을 처리할 수 있습니다.

모형은 SYN을 pending, 역방향 SYN_ACK를 reply-seen, 다시 ACK를 established로 바꿉니다. DATA는 같은 연결 키가 established일 때만 허용합니다. 키는 클라이언트·서버 주소와 포트의 조합이며 프로토콜은 TCP로 고정했습니다.

S5는 다른 클라이언트와 포트의 데이터라 서버 포트가 443이어도 기존 연결 응답이 아닙니다. S6의 CLOSE 뒤에는 상태가 삭제되어 S7을 거부합니다. 실제 TCP 종료는 여러 방향의 FIN·ACK와 타임아웃을 다루므로 이 한 단계 종료와 같지 않습니다.

이 코드는 상태의 필요성을 보여주는 상태 기계입니다. 시퀀스 번호·윈도·재전송·시간 만료·장비 간 상태 공유·공격 내성은 구현하지 않았습니다. 운영 필터로 설치하지 않고 실제 장비 문서의 상태 처리와 비교하는 데 사용합니다.

자주 헷갈리는 지점

SYN 한 번 뒤의 데이터는 모두 신뢰한다.
연결 키와 전이 순서를 확인하고 장비의 타임아웃·시퀀스 처리도 검토합니다.
stateful이면 웹 인증도 해결된다.
연결 상태는 사용자 신원과 애플리케이션 내용의 정상성을 보장하지 않습니다.

    상태를 생성·이동·삭제하는 이벤트와 상태 없이 도착한 이벤트를 비교합니다.

    python3 defense_models.py state

  3. 응답 단계 생략 실험

    S2를 제외하면 S3과 S4가 established에 도달하지 못하는지 검증합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

작업 사본에서 S2를 제거하고 S3·S4의 결과를 예측하세요. 실제 방화벽에 필요한 시간·시퀀스·종료 검증도 세 항목 적습니다.

막혔을 때 힌트 보기

SYN만 봤다고 established가 되지는 않습니다. S3은 reply-seen을 전제로 합니다.

과제 해설과 예시 답안 보기
  1. S2가 없으면 pending에서 reply-seen으로 이동하지 못한다고 예측합니다.
  2. S3과 S4 거부와 pending 상태 유지를 확인합니다.
  3. 실제 구현에는 pending 만료, 양방향 종료, 시퀀스 검증과 상태 용량 관리 등이 필요함을 기록합니다.

결과를 판단하는 기준

S2 제거 뒤 S3·S4는 DENY입니다. 모형의 pending은 자동 만료되지 않으므로 운영 장비처럼 해석할 수 없습니다.
