01 / UNDERSTAND

먼저 이해하기

백업 파일이 있다는 사실과 서비스를 복구할 수 있다는 사실은 다릅니다. 데이터 시점, 설정·비밀·의존 자원, 복원 권한, 복원 후 정상 동작을 함께 점검합니다. 읽을 수 없는 백업이나 검사하지 않은 복구 절차는 사고 시점에 처음 발견하면 늦습니다.

RPO는 허용 가능한 데이터 손실의 시간 목표, RTO는 서비스 복구 시간 목표입니다. 표본에서 사고는 10:00이고 최신 검증 백업은 09:40이므로 잠재 손실 구간은 20분입니다. 목표 15분을 넘습니다. 실제 손실 건수는 그 구간의 변경과 복원 결과가 있어야 계산할 수 있습니다.

복구 완료 확인은 10:45이고 목표 RTO는 60분이므로 사고 이후 45분은 목표 안입니다. 작업 시작이 늦어졌다면 기다린 시간도 포함합니다. 코드는 초 단위 차이를 목표와 비교하며 분을 버림해 경계 초과를 통과시키지 않습니다.

실습은 backup-records.json의 SHA-256을 공개된 기준값과 대조합니다. 일치는 파일 바이트가 이 기준과 같음을 보여줄 뿐 기준값의 진위·완전성·서비스 복원 성공을 증명하지 않습니다. RPO·RTO 목표 충족과 데이터 내용·애플리케이션 기능 검증은 각각 기록합니다.

자주 헷갈리는 지점

백업 성공 메시지를 서비스 복원 성공으로 쓴다.
복원 권한·데이터 내용·애플리케이션 정상 동작을 실제 시험합니다.
분을 버림해 목표와 비교한다.
초 단위 차이로 정확히 비교해 경계 초과를 놓치지 않습니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

사본의 backup 시각을 09:45로 바꾸고 RPO 경계를 확인하세요. 09:44:59로 바꿔 손실 구간이 목표보다 1초 길어진 경우도 비교합니다. 백업 해시가 같아도 남아 있는 복원 후 기능 시험 두 가지를 제안합니다.

막혔을 때 힌트 보기

09:45는 사고 15분 전, 09:44:59는 15분 1초 전입니다. RTO는 사고부터 기능 확인까지 셉니다.

과제 해설과 예시 답안 보기
  1. 09:45는 loss=15분으로 RPO를 충족하고 09:44:59는 15분 1초여서 실패함을 계산합니다.
  2. RTO는 사고부터 서비스 검증까지로 측정하고 대기 시간을 제외하지 않습니다.
  3. 복원 환경의 로그인 없는 정상 읽기·쓰기, 데이터 건수·최신 시점, 권한 경계·의존 서비스 동작 등 기능 시험을 제안합니다.

결과를 판단하는 기준

정확한 경계는 15분 이하입니다. 해시 일치·RPO·RTO·기능 복원을 별도 항목으로 보고합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
