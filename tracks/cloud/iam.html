IAM 최소 권한과 명시적 거부

누가 어떤 자원에 무슨 작업을 할지 좁힙니다.

준비와 연결

가상 IAM 범위 검토 · Python 3.10 이상

  • config.json을 config-work.json으로 복사하고 python3 review.py config-work.json으로 검사합니다. Windows는 py -3을 사용합니다.
  • 실제 IAM 역할·계정·키를 만들지 않습니다. ReadObject와 training-notes는 교육 식별자입니다.

01 / UNDERSTAND

먼저 이해하기

신원에는 사람과 워크로드가 있고 권한은 작업·대상·조건을 기준으로 정합니다. config.json의 action=*와 resource=*는 필요한 범위보다 넓을 가능성이 큽니다. 읽기용 역할에 정책 변경 권한까지 주지 않는 식으로 업무를 나눕니다.

AWS에서는 여러 정책 종류가 평가되며 명시적 Deny가 Allow보다 우선할 수 있습니다. 공급자별 평가 모델을 확인해야 합니다. review.py는 실제 IAM 엔진이 아니라 입력 형식과 와일드카드·장기 키 사용 같은 교육 조건을 검사합니다.

권한은 주체가 어떤 작업을 어떤 대상에 어떤 조건으로 할 수 있는지로 적습니다. 읽기 담당 reader에게 ChangePolicy나 DeleteObject가 필요한지 반례로 질문하면 과도한 권한을 찾기 쉽습니다. 사람 계정과 배포 워크로드의 역할을 분리합니다.

review.py의 identity.scope는 action/resource가 유효한 식별자인지와 와일드카드가 있는지 확인합니다. 빈 값은 INVALID이고 넓은 *·? 범위는 REVIEW입니다. 와일드카드가 없더라도 부적절한 관리 작업이거나 잘못된 대상이면 실제 최소 권한은 아닙니다.

실제 공급자 정책은 허용·거부·경계·리소스 정책·조직 정책·신뢰 관계 등이 조합될 수 있습니다. AWS의 명시적 거부 우선 같은 규칙은 공급자의 평가 모델 안에서 이해해야 합니다. 이 교육 검사기의 PASS를 실제 권한 허용 결과와 같은 뜻으로 쓰지 않습니다.

자주 헷갈리는 지점

ReadObject라고 이름을 적으면 실제 공급자도 같은 권한을 만든다고 생각한다.
교육 식별자와 공급자 실제 action·resource·조건 문법을 구분합니다.
명시적 Deny 규칙을 모든 클라우드의 동일한 평가 순서로 일반화한다.
사용하는 공급자·정책 종류의 평가 문서를 확인합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

  1. 주체·업무·대상 정의

    reader는 training-notes 읽기만 필요하다고 가정합니다. ChangePolicy·다른 저장소 읽기·자격 증명 관리 같은 불필요 작업은 거부 테스트 후보입니다.

    관찰할 결과
    정상 ReadObject / 대상 training-notes와 거부해야 할 작업·대상이 나뉩니다.

  2. 유효한 최소 범위 입력

    사본의 action=ReadObject, resource=training-notes, long_lived_key=false로 바꾸고 검사합니다. 이는 모델의 범위 조건을 만족하는 예시입니다.

    작게 나눠 확인하기
    python3 review.py config-work.json
    관찰할 결과
    identity.scope와 identity.temporary가 PASS로 표시됩니다. 다른 항목을 그대로 두었다면 전체가 8/8은 아닙니다.

  3. 잘못된 값과 실제 검증 구분

    action을 빈 문자열로 바꾼 사본은 INVALID가 되어야 합니다. 실제 환경에서는 필요한 읽기 성공, 변경/삭제/다른 자원 거부, 세션 만료를 별도 검증해야 합니다.

    관찰할 결과
    형식 오류·모델 기준·실제 접근 결과를 세 열로 나눕니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

config 사본에서 action을 ReadObject, resource를 training-notes로 좁히고 long_lived_key를 false로 바꾸세요. 어떤 기능을 시험해야 실제 최소 권한을 확인할 수 있는지도 적습니다.

막혔을 때 힌트 보기

문자열을 바꿔 PASS가 나오는 것은 모델의 조건 통과일 뿐 실제 접근 권한의 증명이 아닙니다.

과제 해설과 예시 답안 보기
  1. 업무에 필요한 작업과 대상 식별자를 구체적으로 쓰고 와일드카드를 제거합니다.
  2. 장기 키를 false로 바꾸는 것과 실제 임시 신원 발급/만료 검증을 분리합니다.
  3. 정상 읽기와 불필요한 변경·삭제·다른 자원 접근의 거부 테스트를 적습니다.

결과를 판단하는 기준

단순 빈 값으로 경고를 없애지 않고 명확한 범위를 지정합니다. PASS 이후에도 실제 정책 평가·신뢰 관계를 확인할 계획이 있습니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
