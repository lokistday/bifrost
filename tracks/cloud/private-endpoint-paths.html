01 / UNDERSTAND

먼저 이해하기

프라이빗 엔드포인트를 만들었다고 모든 클라이언트가 자동으로 그 경로를 쓰지는 않습니다. 서비스 이름이 어느 주소로 해석되는지, 클라이언트가 어떤 네트워크 경로를 갖는지 확인해야 합니다. 같은 이름도 리졸버·네트워크·DNS 설정에 따라 다른 경로를 사용할 수 있습니다.

표본 E1은 이름이 private-endpoint를 가리키고 네트워크·엔드포인트 정책·신원 권한이 모두 맞아 ALLOW_MODEL입니다. E2는 public-endpoint로 해석되어 PUBLIC_PATH로 표시합니다. 이는 공용 경로라는 관측이지 실제 허용이나 거부 판정은 아닙니다.

엔드포인트 정책은 해당 경로의 이용을 제한하는 조건입니다. 서비스의 자원 정책이나 IAM 권한을 대신하지 않으므로 E3의 신원 권한 부재와 E4의 엔드포인트 거부는 따로 나타납니다. 실제 평가는 서비스별 지원과 다른 정책 조합도 확인해야 합니다.

프라이빗 경로는 서버 신원 검증·TLS·사용자 인증과 별개이며 자원의 공용 접근을 자동으로 비활성화하지도 않습니다. 모형은 경로와 정책을 이미 평가했다고 가정한 boolean 값만 사용합니다. 실제 DNS·라우팅·보안 그룹·공급자 자원은 조회하거나 만들지 않습니다.

자주 헷갈리는 지점

private 경로면 데이터가 자동으로 암호화된다고 한다.
전송 암호화·서버 신원 검증을 별도로 유지합니다.
엔드포인트 생성으로 자원 공용 접근도 꺼졌다고 본다.
자원 정책과 공용 경로의 실제 거부를 따로 확인합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · 로컬 파일 실습 · Python 3.10 이상
python3 boundary_models.py private

변경 전 예상 결과와 해석

E1 ALLOW_MODEL
E2 PUBLIC_PATH
E3 DENY_IDENTITY
E4 DENY_ENDPOINT_POLICY

이제 단계별로 바꾸고 관찰하기

  1. 경로와 두 정책 거부 분리

    공용 해석과 신원·엔드포인트 거부를 다른 결과로 읽습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 로컬 파일 실습 · Python 3.10 이상
    python3 boundary_models.py private
    관찰할 결과
    E1 ALLOW_MODEL
E2 PUBLIC_PATH
E3 DENY_IDENTITY
E4 DENY_ENDPOINT_POLICY

  2. DNS 대상만 수정

    E2는 다른 세 조건이 이미 True인 모형이므로 경로 조건 수정 뒤 허용됩니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 로컬 파일 실습 · Python 3.10 이상
    python3 -c "from boundary_models import load,private_access;d=load();r={**d['private_requests'][1],'dns_target':'private-endpoint'};print(private_access(r))"
    관찰할 결과
    ALLOW_MODEL

  3. 신원 권한 없는 경로

    프라이빗 엔드포인트로 가는 것만으로 자원 권한이 생기지 않습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 로컬 파일 실습 · Python 3.10 이상
    python3 -c "from boundary_models import load,private_access;print(private_access(load()['private_requests'][2]))"
    관찰할 결과
    DENY_IDENTITY
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

E2의 dns_target만 private-endpoint로 바꿔 결과를 비교하세요. E3도 함께 고쳐졌다고 말할 수 없는 이유와 자원 공용 접근을 제한하려면 별도로 필요한 검증을 적습니다.

막혔을 때 힌트 보기

경로 변경은 신원 권한을 새로 부여하지 않습니다. 공용 경로와 공용 자원 정책도 다릅니다.

과제 해설과 예시 답안 보기
  1. E2 사본은 private 이름 해석으로 ALLOW_MODEL이 됩니다.
  2. E3은 여전히 DENY_IDENTITY이며 역할·자원 정책의 실제 조합을 검토해야 합니다.
  3. 자원의 공용 접근 설정·허용 주체·공용 경로 거부 시험과 private 경로 정상 시험을 별도 증거로 남깁니다.

결과를 판단하는 기준

DNS 수정은 경로 조건 하나를 바꿉니다. 자원 공용 접근·TLS 신뢰·서비스 권한까지 해결했다고 주장하지 않습니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

INDEPENDENT PRACTICE

도움 없이, 조건을 바꿔 보기

DNS는 private endpoint를 가리키지만 자원 권한이 거부된 경우의 실패 단계를 적으세요.

  1. 위 해설을 닫고 예상 결과와 근거를 먼저 적습니다.
  2. 코드·원시 자료·문서 근거로 확인하고 예상과 실제 차이를 설명합니다.
  3. 새 반례 하나를 만들고 무엇까지 확인했는지 기록합니다.
