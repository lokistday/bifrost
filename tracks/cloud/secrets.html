01 / UNDERSTAND

먼저 이해하기

소스나 이미지에 고정 키를 넣으면 복사본과 버전 기록에 남습니다. 가능한 환경에서는 워크로드 신원과 짧은 수명의 자격 증명을 사용하고 최소 권한을 부여합니다. 비밀 저장소를 쓴다고 읽기 권한과 감사·교체 설계가 없어지는 것은 아닙니다.

노출 시에는 새 키 발급·권한 확인·서비스 전환·이전 키 폐기·기록 검토가 필요합니다. Git에서 줄 하나를 지우는 것만으로 이미 복제된 비밀을 회수할 수 없습니다. 이 실습에는 실제 키를 생성하거나 붙여 넣지 않습니다.

소스·이미지·빌드 출력·로그에 키를 넣으면 복제된 위치를 모두 회수하기 어렵습니다. 환경 변수도 자동으로 비밀 저장소가 되는 것은 아니며 프로세스·로그·진단 출력의 접근 범위를 검토해야 합니다. 키 값이 필요한 주체를 최소화합니다.

짧은 수명의 자격 증명은 노출 시 사용 가능한 시간을 줄이는 수단입니다. 그러나 강한 권한을 무분별하게 주거나 공격자가 계속 새 자격 증명을 얻을 수 있다면 수명만으로 충분하지 않습니다. 역할 신뢰·최소 권한·발급 조건·만료와 감사가 함께 필요합니다.

교체는 새 키 생성으로 끝나지 않습니다. 새 자격 증명 경로의 정상 동작을 확인하고 서비스 전환, 이전 자격 증명 폐기, 남은 사본·캐시·배포 기록 확인을 수행해야 합니다. 긴급 폐기와 계획 교체는 업무 영향과 복구 절차가 달라 별도 시나리오로 적습니다.

자주 헷갈리는 지점

짧은 수명이면 권한은 넓어도 괜찮다고 한다.
수명과 최소 권한·발급 조건·신뢰 관계를 함께 제한합니다.
감사 편의를 위해 키 원문을 로그에 쓴다.
비밀 대신 주체·자격 증명 식별자·발급/만료·대상·결과를 기록합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

  1. 비밀이 필요한 지점 추적

    개발자→저장소→빌드→배포→실행 환경을 그려 어디에 자격 증명이 나타나는지 표시합니다. 키 값 대신 주체·용도·접근 권한을 기록합니다.

    관찰할 결과
    불필요하게 키가 복제되는 지점과 로그 노출 가능성을 찾습니다.

  2. 임시 신원 흐름 설계

    deploy-role이 필요한 자원에만 접근하고 자격 증명이 만료되는 흐름을 적습니다. long_lived_key=false와 실제 발급·만료 검증은 분리합니다.

    관찰할 결과
    역할·대상·작업·수명·발급 조건·감사 항목이 있습니다.

  3. 교체·폐기 반례 점검

    새 경로는 정상인데 옛 키가 계속 허용되는 경우, 폐기 후 배포가 멈추는 경우를 시험 계획으로 씁니다. 비상 복구가 이전 노출 키 재사용이 되지 않도록 합니다.

    관찰할 결과
    전환 성공과 옛 자격 증명 거부를 각각 검증합니다.

전체 예제 연결하기

예제 · 명령 또는 관찰 절차
가상 배포: deploy-role → 임시 자격 증명 → 필요한 자원만 접근
기록: 키 값 대신 역할 ID·발급 시각·만료·작업·결과

예상 결과와 해석

비밀 값이 아닌 신원과 작업을 중심으로 한 발급·만료·교체 흐름도가 나옵니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

긴급 키 폐기 시 배포 서비스가 받는 영향과 복구 방식을 적고, config의 long_lived_key를 false로 바꾸는 것 이상의 검증 절차를 만드세요.

막혔을 때 힌트 보기

환경 변수도 프로세스·로그에 노출될 수 있습니다. 단순 위치 변경과 접근 통제를 구분합니다.

과제 해설과 예시 답안 보기
  1. 노출 의심 키는 사용 경로·영향을 파악하고 새 경로를 검증해 전환·폐기합니다.
  2. Git 줄 삭제는 과거 사본 회수가 아님을 적고 기록·배포·로그의 노출 범위를 확인합니다.
  3. 키 값 없이 역할 ID·발급/만료·작업·결과를 감사 필드로 남깁니다.

결과를 판단하는 기준

최소 권한·발급 신뢰·수명·전환·폐기·감사·복구가 연결된 계획입니다. 플래그 변경을 실제 회수 완료로 해석하지 않습니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

이해한 내용을 점검하기

답을 고른 뒤 이유까지 확인하세요. 점수는 저장하지 않습니다.

1. 키를 Git 최신 파일에서 삭제하면 이미 복제된 키도 사용할 수 없나요?

정답과 이유 읽기

정답: 아니다. 과거 사본이 남을 수 있어 해당 자격 증명의 폐기·교체가 필요하다.

소스의 문자열 삭제와 실제 자격 증명 무효화는 별도입니다. 노출된 키의 권한·사용 기록·폐기를 확인해야 합니다.

2. 자격 증명 교체 검증에서 빠지면 안 되는 것은?

정답과 이유 읽기

정답: 새 경로 정상 동작과 옛 자격 증명의 거부를 둘 다 확인

새 경로가 작동해도 옛 키가 유효하면 노출 위험이 남습니다. 전환·폐기·업무 영향·감사를 모두 검증해야 합니다.

내 결과물 확인하기

  • 실제 비밀 없이 수명·교체를 설계했다.
  • 폐기 후 서비스 정상 동작 확인까지 포함했다.
