01 / UNDERSTAND

먼저 이해하기

사용자 대신 배포 작업이나 서버 프로세스가 클라우드에 접근하는 경우를 워크로드 신원으로 생각합니다. 장기 비밀키를 저장하는 방식 대신 신뢰한 발급자의 증명을 검증하고 짧은 수명의 역할 자격 증명을 받는 구성이 가능합니다. 단기라는 이유만으로 모든 요청이 안전해지는 것은 아닙니다.

OIDC 계열 설계에서는 누가 발급했는지 iss, 어느 수신자를 위한 증명인지 aud, 어떤 주체인지 sub를 구분합니다. issuer만 맞고 다른 저장소·브랜치의 주체라면 배포 역할을 허용하면 안 됩니다. 이 모형은 세 문자열을 정확히 비교하고 와일드카드를 지원하지 않습니다.

신뢰 정책은 누가 역할을 맡을 수 있는지, 권한 정책은 맡은 역할이 무엇을 할 수 있는지 다룹니다. 올바른 워크로드가 역할을 맡아도 권한이 과도하면 사고 영향은 커집니다. 저장소·환경의 경계, 세션 수명, 최소 권한과 감사 기록을 함께 설계합니다.

operations.py의 claims는 이미 서명·유효기간·발급자 검증을 마친 값이라고 가정한 JSON입니다. JWT 파싱이나 서명 검증, 공개키 갱신, 만료·재전송 방지와 실제 STS 발급은 구현하지 않았습니다. MATCH는 세 조건의 일치일 뿐 로그인이나 토큰 진위의 증명이 아닙니다.

자주 헷갈리는 지점

단기 키라면 주체 조건을 넓혀도 괜찮다고 한다.
탈취 가능 기간과 역할을 맡을 수 있는 주체의 범위는 따로 관리합니다.
JSON에서 sub를 읽으면 인증이 끝난다.
진위와 시간 검증을 먼저 수행하는 검증된 OIDC 경로가 필요합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

C2를 무조건 허용하려고 sub를 광범위하게 바꾸는 제안의 위험을 적으세요. 사본의 C1에서 aud를 빼고 DENY인지 확인한 뒤 신뢰 조건과 역할 권한을 각각 표로 작성합니다.

막혔을 때 힌트 보기

다른 저장소의 주체를 허용하는 것과 배포 동작에 필요한 권한을 늘리는 것은 다른 변경입니다.

과제 해설과 예시 답안 보기
  1. C2는 신뢰한 저장소·브랜치의 sub와 다르므로 거부한다고 적습니다.
  2. C1에서 aud를 제거하면 세 조건 중 하나가 없어 False입니다.
  3. 역할 신뢰는 지정된 저장소·환경, 역할 권한은 필요한 자원·행동으로 각각 제한하고 서명·시간 검증은 검증된 OIDC 구성에 맡깁니다.

결과를 판단하는 기준

issuer가 같아도 C2와 C3는 DENY입니다. 문자열 검사를 통과한 C1도 진짜 OIDC 토큰으로 인증된 결과가 아닙니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
