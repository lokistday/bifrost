01 / UNDERSTAND

먼저 이해하기

클라우드는 운영 책임을 없애는 것이 아니라 나누는 방식입니다. IaaS에서는 고객이 게스트 OS와 애플리케이션을 관리하는 경우가 많고, 관리형 서비스에서는 공급자가 더 많은 계층을 맡습니다. 정확한 경계는 선택한 서비스의 문서를 확인해야 합니다.

데이터 분류, 사용자 접근, 구성 선택은 여전히 고객의 중요한 책임입니다. responsibility.csv는 비교를 위한 단순 표이며 모든 공급자·서비스의 계약을 대체하지 않습니다. config.json은 특정 공급자의 실제 배포 파일이 아닌 교육 모델입니다.

IaaS는 VM 같은 기반 자원을 사용하면서 게스트 OS·애플리케이션 운영을 고객이 맡는 형태를 생각할 수 있습니다. PaaS는 실행 환경의 일부를 공급자가 관리하고 고객은 코드·구성·데이터에 집중합니다. SaaS는 완성된 애플리케이션을 사용하지만 사용자 접근과 데이터 공개 선택까지 자동으로 해결되는 것은 아닙니다.

보호 대상이 데이터인지 OS인지 계정인지에 따라 책임이 달라집니다. 메모 내용을 비공개로 유지해야 한다면 공급자가 물리 시설을 관리하더라도 고객은 공유 링크·사용자 회수·외부 연동을 검토해야 합니다. 책임 표에는 수행자뿐 아니라 확인할 근거도 적습니다.

구성 검사는 형식과 위험 조건을 나누어 봅니다. INVALID는 검사할 값 자체가 잘못된 상태, REVIEW는 유효한 형식이지만 교육 기준에 걸린 상태, PASS는 그 항목의 좁은 규칙만 만족한 상태입니다. 셋 모두 실제 서비스의 안전성을 인증하는 점수는 아닙니다.

자주 헷갈리는 지점

IaaS·PaaS·SaaS를 위험이 없는 순서로 외운다.
운영 경계와 남는 책임을 비교하고 실제 서비스별 문서·설정을 확인합니다.
교육 JSON을 실제 공급자에 배포할 수 있는 설정으로 생각한다.
provider=fictional인 설계 모델입니다. 실제 API·IAM 문법과 별개입니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

  1. 서비스 형태별 관리 대상 나누기

    같은 메모 서비스를 VM 직접 운영, 관리형 실행 환경, SaaS 사용으로 그립니다. 시설·OS·코드·권한·데이터 공개를 행으로 나눕니다.

    관찰할 결과
    서비스 형태에 따라 바뀌는 책임과 고객에게 남는 책임이 구분됩니다.

  2. 교육 표와 실제 문서 구분

    responsibility.csv의 guest_os_patch=usually_no는 모든 SaaS 계약의 확정 답이 아닙니다. 실제 선택 시 확인할 공급자 문서·설정·운영 담당을 적습니다.

    관찰할 결과
    일반적 비교와 공급자별 검증 항목이 분리됩니다.

  3. 가상 구성의 상태 읽기

    config.json은 실제 공급자 설정이 아닌 모델입니다. review.py의 세 상태와 무엇을 검사하지 않는지 LAB-GUIDE.md에서 확인합니다.

    작게 나눠 확인하기
    python3 review.py
    관찰할 결과
    초기 요약은 passed=0/8 review=8 invalid=0입니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

같은 메모 서비스를 VM 직접 운영과 SaaS 사용으로 나누어 OS 패치·계정 회수·공개 링크의 책임을 비교하세요.

막혔을 때 힌트 보기

공급자가 암호화를 제공한다는 사실과 고객이 올바르게 설정했다는 사실은 다릅니다.

과제 해설과 예시 답안 보기
  1. VM 직접 운영에서는 게스트 OS 패치와 애플리케이션 운영 책임을 고객 영역으로 적습니다.
  2. SaaS에서는 OS 운영의 전형적 공급자 책임과 고객의 사용자 회수·공유 링크·데이터 분류를 나눕니다.
  3. 실제 경계는 서비스 문서로 확인하고 교육 구성 검사는 오프라인 모델임을 표시합니다.

결과를 판단하는 기준

시설·OS·앱·신원·데이터의 책임이 분리됩니다. “클라우드이므로 보안은 전부 공급자 책임”이라는 결론이 없습니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
