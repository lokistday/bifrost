로컬 파일 실습 · Python 3.10 이상

01 / UNDERSTAND

먼저 이해하기

인스턴스 메타데이터 서비스는 워크로드에 구성 정보와 역할의 임시 자격 증명을 제공할 수 있습니다. 애플리케이션이 사용자 대신 임의 HTTP 요청을 보내면 원래 외부 이용자가 직접 닿지 못하는 로컬 서비스에 접근할 수 있어 경계가 바뀝니다. 이 차시는 실제 URL을 호출하지 않고 구성과 권한만 검토합니다.

IMDSv2의 토큰 흐름을 요구하는 설정은 단순 요청을 통한 일부 노출 경로를 줄입니다. 그러나 유효한 토큰을 얻을 수 있는 코드 실행이나 충분한 요청 기능까지 모두 막는 신원 경계는 아닙니다. 허용된 워크로드와 요청 경로, 필요 없는 메타데이터 접근 제한을 함께 검토합니다.

M1은 필요한 토큰이 없어 DENY_TOKEN, M2는 가정된 유효 토큰과 경로가 있어 REACHABLE_MODEL, M3은 경로가 막혀 BLOCKED_NETWORK입니다. token_valid는 실제 토큰 검증 결과를 가정한 필드이며 코드가 토큰을 발급·검증하는 것은 아닙니다.

메타데이터가 보이는 것과 클라우드 자원에 허용되는 행동은 다릅니다. 표본 역할은 ReadNotes만 허용하고 DeleteNotes는 없습니다. 임시 자격 증명 유출 의심에는 역할 최소 권한, 세션·감사·권한 회수와 갱신을 검토하며 단기 키라서 무해하다고 보지 않습니다.

자주 헷갈리는 지점

임시 자격 증명은 유출되어도 영향이 없다고 한다.
유효 기간 내 허용 행동과 권한 회수·영향 조사를 검토합니다.
token_valid JSON을 실제 인증 결과로 쓴다.
실제 검증을 가정한 입력 필드이며 발급·검증을 구현하지 않았다고 명시합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

tokens_required를 false로 바꾼 사본에서 M1이 어떻게 바뀌는지 확인하세요. 네트워크 차단·토큰 요구·역할 권한 중 어느 조치가 어떤 단계의 영향을 줄이는지 표로 씁니다.

막혔을 때 힌트 보기

토큰 요구를 없애도 네트워크 경로와 클라우드 권한이 자동 생기지는 않습니다.

과제 해설과 예시 답안 보기
  1. 토큰 요구를 해제한 M1은 모형상 REACHABLE_MODEL로 바뀜을 확인합니다.
  2. M3은 여전히 경로 차단이고 역할의 DeleteNotes는 계속 False라고 적습니다.
  3. 애플리케이션의 허용 요청 제한·워크로드 네트워크·필요 최소 역할·노출 후 세션 회수와 감사 계획을 단계별로 연결합니다.

결과를 판단하는 기준

메타데이터 접근·자격 증명 취득·자원 행동 허용을 같은 단계로 합치지 않습니다. IMDSv2만으로 모든 SSRF와 코드 실행 영향을 해결한다고 주장하지 않습니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

1. IMDSv2 토큰 요구를 켜면 모든 SSRF 영향이 사라지나요?

정답과 이유 읽기

정답: 요청 능력·워크로드 경로·역할 권한도 확인해야 한다.

토큰 흐름은 일부 경로를 줄이지만 모든 실행·요청 권한을 대신하지 않습니다.

2. M2가 REACHABLE_MODEL이면 DeleteNotes도 허용되나요?

정답과 이유 읽기

정답: 역할 권한을 별도로 평가해야 한다.
