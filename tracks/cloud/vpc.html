01 / UNDERSTAND

먼저 이해하기

VPC와 서브넷은 주소·라우팅·격리의 구조를 잡습니다. 공개·비공개 서브넷의 의미는 라우팅과 게이트웨이, 주소 부여 방식에 달려 있습니다. 이름을 private으로 붙였다고 자동으로 인터넷 경로가 사라지는 것은 아닙니다.

보안 그룹·네트워크 ACL·호스트 방화벽·애플리케이션 인가는 각각 다른 지점에서 작동합니다. 공급자에 따라 stateful 여부와 규칙 평가가 다릅니다. 여기서는 DB 공개 금지, 관리 접속 출발지 제한이라는 설계 원칙을 가상 구성에서 검토합니다.

외부 노출에는 여러 조건이 맞아야 합니다. 자원 주소·라우팅·게이트웨이·필터·서비스 리슨 상태를 순서대로 확인합니다. database_public=false 하나는 이 모델의 의도 표시이며 실제 장비에서 모든 경로가 닫혔다는 측정 결과가 아닙니다.

보안 그룹은 연결된 자원에 도달하거나 나가는 트래픽을 제어하는 공급자 기능의 한 예입니다. 서브넷 경계의 ACL, 호스트 방화벽, 애플리케이션 인가와 역할이 다를 수 있습니다. 반환 트래픽·상태 추적·규칙 조합은 공급자 문서에 맞춰 검증합니다.

관리 출발지는 유효한 네트워크 CIDR로 씁니다. 0.0.0.0/0과 ::/0은 각각 모든 IPv4·IPv6를 포함합니다. /0보다 좁다고 자동으로 안전한 것은 아니므로 실제 승인된 관리자·접속 경로·인증 조건을 근거로 범위를 정합니다.

자주 헷갈리는 지점

private 이름만 보고 외부 노출이 없다고 한다.
주소·라우팅·게이트웨이·필터·리슨 상태를 따라갑니다.
IPv4만 제한하면 모든 관리 접근이 닫힌다고 생각한다.
IPv6·대체 인터페이스·관리 프록시·비상 경로도 검토합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

관찰 절차·자료 예시 · 그대로 셸에 붙여 넣지 말고 본문 안내를 따라 확인
config.json의 network 확인:
database_public: true
admin_source: 0.0.0.0/0

변경 전 예상 결과와 해석

DB 공개와 전체 IPv4 관리 허용이 검토 대상입니다. 실제 노출을 판단하려면 라우팅·주소·필터·서비스 리슨 상태가 더 필요합니다.

이제 단계별로 바꾸고 관찰하기

  1. 노출 경로를 그림으로 확인

    인터넷→Web, Web→DB, 관리자→관리 경로를 분리합니다. DB의 인터넷 직접 접근과 관리 전체 허용이 왜 다른 위험인지 씁니다.

    관찰할 결과
    공개·데이터·관리 흐름이 분리된 그림입니다.

  2. 모델 값 수정과 형식 검증

    database_public=false, admin_source=192.0.2.0/24로 바꾸고 검사합니다. 192.0.2.1/24는 host bit가 남아 모델에서 INVALID임을 비교합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 가상 네트워크 구성 검토 · Python 3.10 이상
    python3 review.py config-work.json
    관찰할 결과
    유효 예시에서는 network.database와 network.admin이 PASS입니다. 빈 CIDR·잘못된 주소·host bit가 남는 입력은 INVALID입니다.

  3. IPv6와 실제 경로 검증 설계

    ::/0을 허용한 관리 경로가 남아 있지 않은지 별도 항목에 씁니다. 정상 관리자 접근, 비승인 출발지 거부, DB 직접 접근 거부를 시험 계획으로 정합니다.

    관찰할 결과
    IPv4 한 줄만 좁히고 끝내지 않는 검증표가 됩니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

사본에서 database_public을 false로 바꾸고 관리 출발지를 192.0.2.0/24라는 문서용 예시로 제한하세요. 실제 운영 적용이 아닌 설계 검토이며 IPv6 정책도 별도로 적습니다.

막혔을 때 힌트 보기

클라우드 구성 변경과 정상 배포·백업·관리 경로의 영향도 함께 확인해야 합니다.

과제 해설과 예시 답안 보기
  1. DB 공개 의도를 false로 바꾸고 관리 출발지를 유효하고 구체적인 문서용 CIDR로 지정합니다.
  2. 빈 값·접두사 누락·잘못된 IP·host bit·IPv6 전체 범위를 반례로 확인합니다.
  3. 실제 환경에서는 경로·필터·리슨·신원·정상 운영 영향까지 별도 검증하도록 기록합니다.

결과를 판단하는 기준

모델의 PASS 범위를 설명하면서 실제 노출이나 관리자 신원을 인증한 것처럼 쓰지 않습니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
