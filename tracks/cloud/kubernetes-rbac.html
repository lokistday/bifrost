01 / UNDERSTAND

먼저 이해하기

Kubernetes ServiceAccount는 워크로드가 API에 접근할 때 사용하는 주체입니다. 같은 viewer 이름이라도 네임스페이스가 다르면 다른 ServiceAccount입니다. 주체 인증과 그 주체의 API 행동 허용은 구분합니다.

Role은 네임스페이스 안의 자원·verb 등을 허용하고 RoleBinding은 주체를 역할에 연결합니다. 표본은 learn의 pod-reader가 핵심 API 그룹의 pods에 get·list를 허용합니다. learn의 viewer가 learn의 pods를 읽는 K1만 이 연결에 맞습니다.

다른 네임스페이스의 pods, secrets 자원, 이름이 같지만 다른 주체의 요청은 이 바인딩으로 허용되지 않습니다. 실제 RoleBinding이 다른 네임스페이스의 ServiceAccount를 주체로 지정하는 것은 가능하므로 “다른 네임스페이스 주체는 항상 금지”라고 일반화하지 않습니다.

Kubernetes RBAC의 허용은 여러 바인딩에서 더해집니다. 이 모형은 한 Role·한 RoleBinding만 평가하며 별도 Deny 정책, ClusterRoleBinding·서브리소스·resourceNames·권한 위임과 실제 토큰 검증을 구현하지 않습니다. 네임스페이스가 네트워크·호스트 격리를 완성한다는 뜻도 아닙니다.

자주 헷갈리는 지점

네임스페이스를 완전한 보안 격리로 본다.
API 권한·네트워크·런타임·호스트 경계를 각각 검토합니다.
한 Role에서 허용이 없으면 전역 Deny라고 한다.
다른 RoleBinding과 클러스터 범위 부여도 확인합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 로컬 파일 실습 · Python 3.10 이상

  2. 역할이 허용한 자원 읽기

    get/list와 pods가 구체적인 허용 범위임을 확인합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 로컬 파일 실습 · Python 3.10 이상
    python3 -c "from boundary_models import load;r=load()['role'];print(r['namespace'],r['rules'][0]['resource'],r['rules'][0]['verbs'])"
    관찰할 결과
    learn pods ['get', 'list']

  3. 다른 네임스페이스의 주체 연결

    주체를 명시적으로 other/viewer로 바꾸면 K4가 맞습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 로컬 파일 실습 · Python 3.10 이상
    python3 -c "from boundary_models import load,rbac_allowed;d=load();b={**d['binding'],'subject':{'namespace':'other','name':'viewer'}};print(rbac_allowed(d['rbac_requests'][0],d['role'],b),rbac_allowed(d['rbac_requests'][3],d['role'],b))"
    관찰할 결과
    False True
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

Role에 secrets/get을 추가하는 제안의 영향을 적으세요. binding의 subject.namespace를 other로 바꾸면 K1과 K4 중 어느 요청이 허용되는지도 사본에서 확인합니다.

막혔을 때 힌트 보기

바인딩이 적용되는 네임스페이스와 주체 ServiceAccount의 네임스페이스를 분리해 읽으세요.

과제 해설과 예시 답안 보기
  1. 현재 역할은 pods만 허용하므로 secrets 요청 K3은 DENY라고 적습니다.
  2. secrets 읽기는 민감한 자격 정보 접근을 넓힐 수 있어 목적·대상·대체 신원·감사를 검토합니다.
  3. subject를 other로 바꾼 사본은 K1 DENY, K4 ALLOW_MODEL이며 대상 자원은 여전히 learn 범위임을 확인합니다.

결과를 판단하는 기준

주체 네임스페이스와 자원 네임스페이스를 각각 특정합니다. 다른 바인딩의 추가 허용 가능성과 클러스터 전체 정책은 모형 밖입니다.
