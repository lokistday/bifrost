01 / UNDERSTAND

먼저 이해하기

서버 공개키를 받았다는 사실만으로 원하는 서버의 키임을 알 수 없습니다. 인증서는 이름과 공개키 등을 연결한 서명된 구조이며 신뢰 저장소까지의 경로와 사용 목적을 검증해야 합니다. 연결 대상 이름을 확인하는 절차도 필요합니다.

이름 검증은 접속하려던 이름이 인증서의 적절한 이름 항목에 맞는지 확인합니다. 신뢰한 발급자의 인증서라도 other.example용이면 learn.example 연결에 사용할 수 없습니다. 실제 이름 검증은 DNS·IP 식별자와 와일드카드 규칙 등 표준을 따르며 단순 부분 문자열 검색으로 처리하지 않습니다.

기간 검증은 검증 시각이 유효 구간에 있는지 확인합니다. 이름과 기간이 맞아도 서명·체인 제약·키 사용 목적·신뢰 저장소·폐기 상태 같은 다른 검증이 남습니다. 경고를 끄고 연결에 성공한 것을 TLS 인증 성공으로 부르면 안 됩니다.

실습은 실제 X.509가 아닌 JSON 메타데이터를 사용합니다. 날짜는 YYYY-MM-DD 고정 형식, 이름은 정확 일치, root는 가상 이름 목록으로만 비교합니다. root_in_training_store=True는 서명을 따라 체인을 검증한 결과가 아니며 실제 인증서 검증기는 아닙니다.

자주 헷갈리는 지점

이름에 example이 들어가면 같은 서버로 본다.
접속 대상과 인증서 식별자를 표준 규칙으로 검증합니다.
연결 성공을 위해 검증 경고를 항상 끈다.
원인을 조사하고 신뢰 경로·이름·시간 설정을 고칩니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

T1의 세 값이 모두 True인데도 실제 인증서 검증 완료라고 말할 수 없는 이유를 세 가지 쓰세요. 작업 사본의 root를 Unknown Root로 바꾸고 결과를 비교합니다.

막혔을 때 힌트 보기

문자열 이름을 신뢰 목록에서 찾는 것과 인증서 서명을 따라 신뢰 경로를 검증하는 것은 다릅니다.

과제 해설과 예시 답안 보기
  1. T1은 가상 이름·날짜·루트 표시만 맞는다고 한정합니다.
  2. 실제 서명 경로·체인 제약·키 사용 목적과 정책상 폐기 확인이 생략되었음을 씁니다.
  3. Unknown Root 결과와 T2·T3를 비교하고 실제 서비스에는 검증된 TLS 클라이언트의 기본 검증을 유지합니다.

결과를 판단하는 기준

루트 변경 후 이름과 기간은 True지만 root_in_training_store는 False입니다. 세 축을 구분하되 세 True를 실제 X.509 검증 완료로 표현하지 않습니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
