01 / UNDERSTAND

먼저 이해하기

nonce는 해당 알고리즘이 요구하는 재사용 방지 조건을 만족해야 합니다. 비밀일 필요는 없지만 같은 키에서 유일해야 하는 경우가 많습니다. 구체적인 길이와 생성 규칙은 알고리즘과 라이브러리 문서를 따라야 합니다.

lab.py nonce는 같은 XOR 스트림을 두 메시지에 쓰면 암호문끼리 XOR한 값이 평문끼리 XOR한 값과 같아지는 장난감 모델입니다. 실제 AES-GCM 구현이나 완전한 공격 실습은 아닙니다. 난수 생성에는 일반 random 대신 보안용 생성기를 사용합니다.

nonce의 유일성과 예측 불가능성은 같은 조건이 아닙니다. 알고리즘이 요구하는 조건에 따라 카운터나 난수 생성 등 방식을 선택합니다. AES-GCM에서는 동일 키에 nonce 재사용을 피해야 하며 길이·사용량 제한은 라이브러리·규격을 확인합니다.

XOR는 같은 값으로 두 번 연산하면 상쇄됩니다. C1=P1 XOR S, C2=P2 XOR S이면 C1 XOR C2=P1 XOR P2입니다. 키 스트림이 재사용되면 암호문 사이에 평문 관계가 새어 나온다는 핵심을 작은 예제로 관찰합니다.

난수를 쓴다고 중복 확률이 수학적으로 0인 것은 아닙니다. 생성량과 공간 크기를 고려하고, 카운터라면 재시작·동시 프로세스·백업 복원에서 되감기지 않게 관리합니다. 키를 바꾸면 중복 관리 범위도 그 키 식별자와 연결해야 합니다.

자주 헷갈리는 지점

secrets로 생성하면 무한히 생성해도 중복은 절대 없다고 한다.
안전한 난수 생성과 중복 확률·알고리즘 사용량 제한을 함께 고려합니다.
nonce를 숨기면 재사용해도 괜찮다고 한다.
비밀 여부가 아니라 해당 키에서의 재사용 조건을 지켜야 합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

  1. 상쇄되는 XOR를 따라가기

    lab.py의 a·b·stream으로 각 암호문을 만들고 두 암호문 XOR가 두 평문 XOR와 같아지는지 봅니다. 이것은 평문 관계 누출 예시입니다.

    작게 나눠 확인하기
    python3 lab.py nonce
    관찰할 결과
    True

  2. 스트림을 바꿔 비교

    한쪽 스트림만 바꾸면 상쇄되던 항이 남습니다. 아래 고정된 작은 예에서는 등식이 False가 됩니다. 두 스트림 사용 자체가 운영 암호 구현은 아닙니다.

    작게 나눠 확인하기
    xor = lambda x, y: bytes(a ^ b for a, b in zip(x, y))
a, b = b"YES", b"NO!"
s1, s2 = bytes([31,22,9]), bytes([30,22,9])
print(xor(xor(a,s1),xor(b,s2)) == xor(a,b))
    관찰할 결과
    False

  3. 수명주기 반례 설계

    nonce를 0부터 세다가 재시작하는 경우, 두 프로세스가 같은 범위를 쓰는 경우, 예전 백업으로 복원하는 경우를 표로 씁니다. 키별 고유 범위·원자적 할당·키 교체 조건을 검토합니다.

    관찰할 결과
    생성 방법뿐 아니라 중복을 막는 운영 조건이 남습니다.

직접 바꾸고 확인하기

장난감 코드의 stream을 두 메시지에서 다르게 했을 때 등식이 유지되는지 확인하세요. 프로세스 재시작·동시 실행·키 교체 시 nonce 중복을 어떻게 피할지 설계합니다.

막혔을 때 힌트 보기

랜덤 값은 충분한 길이와 사용량 관리가 필요합니다. 무조건 중복이 불가능하다고 쓰지 마세요.

과제 해설과 예시 답안 보기
  1. 같은 스트림의 두 번 XOR 상쇄를 식과 실행 결과로 확인합니다.
  2. 다른 스트림 예에서는 False임을 기록하고 이것이 AES-GCM 전체 공격 구현이 아님을 적습니다.
  3. 재시작·동시 실행·복구의 중복 위험을 키별 nonce 관리와 연결합니다.

결과를 판단하는 기준

nonce 공개 가능성과 재사용 금지를 구분합니다. 일반 random이나 고정 상수를 새 암호화 nonce로 반복하지 않습니다.
