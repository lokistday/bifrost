01 / UNDERSTAND

먼저 이해하기

봉투 암호화에서는 데이터 암호화 키 DEK로 내용을 보호하고 별도 키 KEK로 DEK를 감쌉니다. 큰 데이터와 작은 키 재료의 역할을 분리하면 데이터 처리와 키 관리의 경계를 설명하기 쉽습니다. DEK·KEK·nonce·문서 문맥·포장 키 ID를 혼동하지 않습니다.

실습의 데이터는 AES-GCM으로 암호화되어 있고 DEK는 RFC3394 AES Key Wrap으로 포장돼 있습니다. 이전 KEK로 DEK를 풀고 새 KEK로 같은 DEK를 다시 포장한 새 envelope를 만듭니다. 새 포장 값은 달라지지만 데이터 암호문과 nonce는 그대로이고 새 KEK로 풀어 같은 평문을 얻습니다.

재포장은 KEK 변경이며 DEK 변경·데이터 재암호화가 아닙니다. 이전 KEK가 유출되었고 공격자가 이전 포장 값을 보관했다면 단순 재포장만으로 과거 DEK 노출을 취소할 수 없습니다. 영향을 평가해 새 DEK와 데이터 재암호화·백업 이전까지 필요한지 판단합니다.

AES-KW는 키 재료를 보호하지만 주변 JSON의 kek_id나 업무 권한까지 인증하는 전체 KMS는 아닙니다. 운영에서는 신뢰한 키 ID 매핑·사용 권한·키 접근 감사·회복 정책이 필요합니다. 표본 키와 값은 모두 공개 교육 자료이며 실제 서비스의 보안 저장소로 쓰지 않습니다.

자주 헷갈리는 지점

KEK 교체를 DEK 교체라고 쓴다.
어떤 바이트와 키 역할이 바뀌었는지 구분합니다.
kek_id 문자열 자체를 신뢰한 키의 증명으로 본다.
인증된 키 매핑·사용 권한과 감사가 필요합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

새 envelope의 wrapped_dek 한 바이트를 바꾸어 InvalidUnwrap을 확인하세요. KEK 정기 교체와 이전 KEK 유출에서 재포장만으로 충분한지 비교하고 DEK 재암호화 필요 조건을 적습니다.

막혔을 때 힌트 보기

포장 값과 데이터 암호문은 다른 바이트입니다. 이전 포장 사본이 남았을 가능성을 고려하세요.

과제 해설과 예시 답안 보기
  1. 새 포장 값을 bytes로 바꿔 한 바이트를 뒤집고 새 KEK로 unwrap하면 InvalidUnwrap이 발생함을 확인합니다.
  2. 정기 KEK 교체에서는 데이터 정책에 맞는 재포장을 검토하되 데이터·메타데이터의 무결성을 따로 확인합니다.
  3. 이전 KEK와 포장 사본 노출은 DEK 노출 가능성이 있으므로 새 DEK 재암호화·백업 범위·과거 유출 영향을 조사합니다.

결과를 판단하는 기준

새 envelope는 원본 암호문을 유지하고 같은 데이터를 복호화합니다. 재포장 성공을 과거 키 침해의 복구 완료라고 발표하지 않습니다.
