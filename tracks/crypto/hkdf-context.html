01 / UNDERSTAND

먼저 이해하기

공통 비밀을 암호화·인증·송신·수신에 그대로 재사용하면 용도 사이의 결합과 오류 위험이 커집니다. 키 유도 함수는 원래 비밀과 문맥을 입력으로 필요한 길이의 별도 키 재료를 만듭니다. 용도 분리는 키를 어떤 프로토콜·방향·버전에 쓰는지 설계하는 일입니다.

HKDF는 HMAC 기반 Extract와 Expand로 나뉩니다. Extract는 입력 키 재료와 salt에서 PRK를 만들고 Expand는 PRK·info·카운터를 사용해 필요한 길이의 출력을 만듭니다. info는 비밀이 아니라 합의된 용도 문맥이며 송신자와 수신자가 같은 바이트를 사용해야 합니다.

실습은 SHA-256 기반 HKDF와 RFC 5869 부록 A.1의 공개 시험값을 사용합니다. 결과 42바이트의 일치를 확인하고 client-v1과 server-v1의 info가 다른 출력을 만드는지 봅니다. 시험 벡터는 구현 실수를 찾는 자료이며 공개된 고정 입력을 운영 키로 쓰면 안 됩니다.

HKDF는 약한 비밀번호의 추측 비용을 높이는 비밀번호 KDF를 대신하지 않습니다. 입력 비밀의 엔트로피를 마술처럼 늘리지 않고 잘못된 키 합의·인증도 고치지 않습니다. 운영에서는 검증된 라이브러리와 프로토콜의 키 일정·레이블 규칙을 따릅니다.

자주 헷갈리는 지점

info를 임의 문자열로 매번 바꾸고 상대와 맞추지 않는다.
프로토콜에서 용도·버전·인코딩을 합의하고 양쪽의 키 유도를 시험합니다.
공개 시험 벡터를 실제 키로 사용한다.
시험값은 공개이며 운영 비밀 생성과 전혀 다릅니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

client-v1을 두 번 쓴 결과와 client-v1/server-v1을 비교하세요. info를 비워 두고 같은 키를 양방향에 쓰는 설계의 문제, 비밀번호에 HKDF만 적용하면 안 되는 이유를 적습니다.

막혔을 때 힌트 보기

같은 입력은 같은 출력, 다른 문맥은 다른 키 재료를 유도합니다. 실제 비밀의 강도와 별개입니다.

과제 해설과 예시 답안 보기
  1. 동일 레이블 두 결과는 같고 서로 다른 레이블은 다름을 실행합니다.
  2. 방향·용도·버전 레이블을 스키마로 고정하고 양쪽에서 같은 바이트를 쓰는지 시험합니다.
  3. 비밀번호 저장은 전용 KDF와 비용·salt 관리가 필요하며 HKDF는 고엔트로피 키 재료를 분리하는 다른 용도임을 설명합니다.

결과를 판단하는 기준

결정성과 문맥 분리를 확인하되 출력이 달라졌다는 사실만으로 독자 프로토콜의 안전성을 주장하지 않습니다. HKDF 길이는 SHA-256에서 최대 255×32바이트입니다.
