01 / UNDERSTAND

먼저 이해하기

HMAC 태그가 맞으면 키를 가진 쪽이 만든 메시지와 바이트가 일치함을 확인하는 데 도움이 됩니다. 그러나 공격자가 그 메시지와 태그를 그대로 다시 보내면 태그는 여전히 맞습니다. 무결성·인증과 신선도는 서로 다른 보장입니다.

실습은 메서드·경로·본문·순번과 프로토콜 레이블을 함께 HMAC-SHA256으로 인증합니다. 수신자는 태그를 먼저 검증한 뒤 이미 처리한 마지막 순번보다 큰 요청만 허용합니다. 변경된 본문의 기존 태그는 BAD_TAG, 원본 반복은 REPLAY로 서로 다르게 분류합니다.

이 모형은 한 주체·한 키의 순차 처리만 가정합니다. 순번의 빈 구간은 허용하며, 실제로는 키·사용자·세션별 상태 범위를 정하고 동시 요청에서 원자적으로 갱신해야 합니다. 중복 처리를 막을 데이터 저장·업무 트랜잭션과 멱등성도 설계해야 합니다.

상태를 메모리에만 두고 재시작하면 last_seen=0으로 돌아가 재전송을 허용할 수 있습니다. 키 교체·시간 만료·재시도·순서 뒤바뀜·분산 서버도 다루지 않았습니다. 고정 키는 공개 교육값이고 이 코드는 운영 요청 서명 프로토콜이 아닙니다.

자주 헷갈리는 지점

유효한 MAC이면 새로운 요청이라고 본다.
태그 검증과 신선도·중복 상태 검증을 분리합니다.
거부된 변조 요청도 순번 상태를 갱신한다.
인증되지 않은 입력으로 정상 상태가 오염되지 않게 합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

정상 요청을 처리한 뒤 last_seen을 0으로 초기화해 같은 요청이 다시 허용되는지 확인하세요. 서버 재시작·두 서버 동시 처리·키 교체에서 상태를 어떻게 보존할지 적습니다.

막혔을 때 힌트 보기

원본 태그는 재전송해도 맞습니다. 태그 검증 뒤의 순번 상태가 별도 방어입니다.

과제 해설과 예시 답안 보기
  1. 같은 태그의 반복이 MAC 위조가 아니라 원본 재사용임을 적습니다.
  2. 상태 초기화에서 ACCEPT가 나옴을 검증하고 마지막 순번을 내구성 있게 보존할 경로를 설계합니다.
  3. 상태의 주체·키 범위를 지정하고 원자적 순번 갱신·업무 처리·재시도 정책과 키 교체를 검토합니다.

결과를 판단하는 기준

태그만으로 재전송은 막지 못하며 상태를 잃으면 방어가 사라집니다. 실제 구현은 검토된 프로토콜과 안전한 상태 저장을 사용해야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
