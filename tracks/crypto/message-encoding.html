01 / UNDERSTAND

먼저 이해하기

암호 도구는 의미가 아니라 바이트를 입력받습니다. [ab, c]와 [a, bc]를 단순 연결하면 둘 다 abc가 됩니다. HMAC이 같은 결과를 내도 암호학적 충돌을 찾은 것이 아니라 애초에 동일한 입력 바이트를 준 것입니다.

길이를 필드 앞에 넣으면 경계를 보존할 수 있습니다. 실습은 각 바이트 필드 앞에 4바이트 big-endian 길이를 넣어 두 목록을 서로 다른 메시지로 만듭니다. 실제 구조에는 타입·필드 순서·인코딩·버전과 허용 길이도 함께 정의해야 합니다.

문자열은 UTF-8 같은 인코딩을 정하고 길이를 문자 수가 아닌 인코딩 뒤 바이트 수로 계산합니다. JSON의 키 순서·공백·중복 키·숫자 표현, URL의 정규화처럼 생산자와 검증자의 해석이 다르면 올바른 태그도 다른 의미에 재사용될 수 있습니다.

프로토콜 레이블을 포함하면 같은 키를 쓰는 다른 문맥의 메시지와 구분하는 데 도움이 됩니다. 다만 임의의 길이 접두사만 추가해 완전한 프로토콜이 되지는 않습니다. 이 교육 표현은 HTTP Message Signatures의 표준 정규화 구현이 아니며 운영에서는 해당 프로토콜과 검증된 라이브러리를 사용합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

필드 [ab,c]와 [a,bc]의 단순 연결과 길이 접두사를 Hex로 비교하세요. 한글 한 글자를 필드로 넣어 문자 수와 UTF-8 바이트 수가 다른 것도 확인합니다.

막혔을 때 힌트 보기

길이는 len(문자열)이 아니라 len(인코딩된 bytes)입니다. 같은 입력 태그는 HMAC 충돌을 의미하지 않습니다.

과제 해설과 예시 답안 보기
  1. 두 목록의 단순 결합은 616263으로 같다고 씁니다.
  2. 길이 접두사로 필드 경계가 달라지는 Hex를 비교합니다.
  3. 가의 UTF-8은 eab080 세 바이트이므로 접두사가 00000003임을 확인하고 타입·순서·버전·최대 크기를 문서화합니다.

결과를 판단하는 기준

naive_same=True는 같은 입력을 만들었다는 뜻이며 HMAC 충돌이 아닙니다. 인코딩 규칙은 송신·검증·업무 해석에 동일하게 적용되어야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
