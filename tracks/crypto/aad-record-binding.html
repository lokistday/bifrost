01 / UNDERSTAND

먼저 이해하기

암호문이 변조되지 않았어도 다른 문서의 암호문을 그대로 옮겨 붙이는 의미 혼동이 생길 수 있습니다. 암호 도구가 확인할 바이트에 테넌트·문서 ID·스키마 버전 같은 문맥을 포함하면 다른 자리에 놓인 값을 검출하는 데 도움이 됩니다. 이 연습은 기본 AEAD 변조 검사에서 레코드 연결로 확장합니다.

AAD는 암호화하지 않지만 태그가 인증하는 연관 데이터입니다. 표본은 [프로토콜 레이블,blue,17,1]을 고정된 JSON 바이트로 만들어 AES-GCM에 넣었습니다. 복호화할 때도 요청에서 기대한 동일 바이트를 사용해야 합니다. 검증하지 않은 저장 메타데이터를 그대로 신뢰해 기대 문맥을 바꾸면 결합의 목적을 잃을 수 있습니다.

기존 암호문에 문서18이나 테넌트red의 문맥을 주면 실제 AES-GCM 검증이 InvalidTag로 실패합니다. 라이브러리의 고수준 decrypt는 성공한 평문만 반환하며 예제는 실패를 잡아 평문을 출력하지 않습니다. 실패한 내용을 부분 복구하거나 캐시에 정상 데이터로 넣지 않습니다.

AAD 일치는 사용자 인가나 문서 소유권 검사를 대신하지 않습니다. nonce의 키별 유일성·키 접근 통제·메타데이터의 출처도 필요합니다. 표본은 한 번 제작한 공개 키·nonce·암호문을 복호화만 하며 변경 내용을 같은 키·nonce로 재암호화하지 않습니다.

자주 헷갈리는 지점

AAD를 비밀 저장 공간으로 사용한다.
AAD는 기밀성을 제공하지 않으며 공개 가능한 문맥만 넣습니다.
암호문 옆의 문서 ID를 무조건 기대값으로 신뢰한다.
요청·소유권과 연결한 기대 문맥을 검증합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

같은 암호문에 버전2 문맥을 주면 어떤 예외가 나는지 실행하세요. 서버가 기대 문서 ID를 요청 권한 검사와 연결해야 하는 이유와 AAD에 비밀을 넣으면 안 되는 이유도 적습니다.

막혔을 때 힌트 보기

AAD는 인증되지만 공개되는 바이트입니다. 기존 암호문은 blue/17/1에만 결합돼 있습니다.

과제 해설과 예시 답안 보기
  1. decrypt_record의 version 인수만 2로 바꾸어 InvalidTag가 발생함을 확인합니다.
  2. 태그 실패는 평문 없음으로 처리하고 원본 데이터·키·문맥 조사 경로를 따로 기록합니다.
  3. 기대 문맥은 인증된 요청·인가된 문서와 연결하고 AAD에는 기밀값 대신 공개 가능한 식별자를 사용합니다.

결과를 판단하는 기준

버전2도 InvalidTag입니다. 태그 실패를 데이터로 사용하지 않으며 같은 키·nonce로 수정 암호문을 새로 만들지 않습니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
