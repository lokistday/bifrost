01 / UNDERSTAND

먼저 이해하기

-O2 빌드는 함수를 인라인하거나 코드를 합칠 수 있으므로 소스 줄과 일대일 대응하지 않을 수 있습니다. 디컴파일도 원본 복원이 아니라 기계어 의미를 고수준으로 표현한 추정입니다. 변수 이름과 구조가 같다는 보장은 없습니다.

보고서에는 목적, 해시나 빌드 명령, 환경, 정적 근거, 입력별 동적 결과, 반례, 한계를 남깁니다. 검사 함수가 문자열을 비교한다는 결론과 이 코드가 전체 서비스의 인증이라는 주장은 근거 수준이 다릅니다.

비교 실험에서는 입력과 소스는 유지하고 빌드 옵션을 바꿉니다. 실행 파일을 서로 다른 이름으로 보관하면 어떤 결과가 어느 빌드에서 나왔는지 추적할 수 있습니다. 바이너리 SHA-256을 적으면 나중에 같은 파일인지 확인하는 근거도 생깁니다.

최적화는 소스의 변수명·함수 호출·분기 모양을 그대로 유지할 의무가 없습니다. 관찰 가능한 의미를 유지하면서 명령 수를 줄이거나 함수를 인라인할 수 있습니다. 따라서 디스어셈블의 줄 모양보다 입력에 대한 판정과 반환 흐름을 비교합니다.

좋은 결론은 어떤 빌드와 입력에서 무엇을 확인했는지 제한합니다. 이 데모의 문자열 비교를 분석한 것과 실제 인증 서비스의 전체 보안을 검증한 것은 범위가 다릅니다. 재현에 필요한 자료·명령·반례를 남기고 아직 확인하지 못한 환경은 한계로 적습니다.

자주 헷갈리는 지점

두 빌드를 같은 출력 파일명으로 덮어써 비교 대상을 잃는다.
파일명을 분리하고 빌드 명령과 해시를 함께 보관합니다.
디컴파일 변수명이 원본 이름과 같아야 정답이라고 생각한다.
디컴파일 표현은 추정된 고수준 의미입니다. 원본 구조·이름 복원 보장과 구분합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC·objdump · analysis.md
gcc -O2 check.c -o check-optimized
objdump -d check-optimized > optimized.txt
./check-optimized BIFROST
./check-optimized BIFROSa

변경 전 예상 결과와 해석

코드 모양이 달라질 수 있지만 두 입력의 결과는 match와 no match를 유지합니다.

이제 단계별로 바꾸고 관찰하기

  1. 두 빌드의 신원 남기기

    최적화 빌드를 새 이름으로 만들고 두 파일의 해시와 빌드 조건을 적습니다. 해시값은 환경별로 다르므로 특정 정답 문자열로 비교하지 않습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC·objdump · analysis.md
    gcc -Wall -Wextra -O2 check.c -o check-optimized
sha256sum check check-optimized
    관찰할 결과
    서로 식별할 수 있는 두 파일의 SHA-256과 실제 빌드 명령을 확보합니다.

  2. 같은 입력으로 동작 비교하기

    두 빌드에 같은 정상·반례 입력을 넣습니다. 원본과 최적화 파일을 번갈아 실행하면 어떤 빌드의 결과인지 기록하기 쉽습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC·objdump · analysis.md
    ./check BIFROST
./check-optimized BIFROST
./check BIFROSa
./check-optimized BIFROSa
    관찰할 결과
    match
match
no match
no match

  3. 코드 모양과 의미를 나눠 보고하기

    최적화 출력을 별도 저장하고 호출 수, 비교 명령, 함수 범위 등이 어떻게 달라졌는지 관찰한 사실만 적습니다. 차이가 작거나 없더라도 있는 것처럼 만들지 않습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC·objdump · analysis.md
    objdump -d check-optimized > optimized.txt
    관찰할 결과
    실제 관찰한 코드 차이와 같은 입력에 대한 동일한 판정을 별도 칸에 남깁니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

analysis.md를 완성하고 두 빌드의 같은 동작·다른 코드 형태를 설명하세요. 다른 사람이 같은 명령으로 재현할 수 있게 합니다.

막혔을 때 힌트 보기

소스와 모양이 다른 지점을 오류라고 단정하지 말고 관찰한 의미를 먼저 비교합니다.

과제 해설과 예시 답안 보기
  1. analysis.md의 환경·CPU·도구 버전·빌드 명령·해시·정적 근거·입력별 동적 결과·반례·한계를 채웁니다.
  2. 두 빌드에서 BIFROST는 match, BIFROSa는 no match임을 확인합니다. 필요하면 누락 인자와 종료 상태도 같은 기준으로 추가합니다.
  3. 코드 모양이 달라진 구체 지점을 하나 적고, 이번 문자열 비교 데모의 범위를 넘어 서비스 인증이나 모든 입력 안전성을 주장하지 않습니다.

결과를 판단하는 기준

재현 명령과 결과표가 있는 보고서가 완성되어야 합니다. 비교한 입력의 동작은 유지되며 코드 형태 차이는 실제 출력에 근거해야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

1. 최적화 뒤 함수 호출이 사라졌습니다. 원래 기능도 사라졌다고 즉시 결론 내릴 수 있을까요?

정답과 이유 읽기

정답: 아니다. 인라인이나 동등한 비교로 바뀌었는지 의미와 입력 결과를 확인해야 한다.

정답과 이유 읽기
