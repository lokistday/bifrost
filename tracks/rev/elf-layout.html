01 / UNDERSTAND

먼저 이해하기

ELF의 섹션 표는 코드·데이터·심볼 등 링크와 분석에 유용한 단위를 설명하고, 프로그램 헤더는 실행할 때 어떤 영역을 메모리에 어떻게 적재할지 설명합니다. .text라는 이름을 찾는 것과 LOAD 세그먼트의 권한을 확인하는 것은 같은 질문이 아닙니다.

layout.c의 banner는 상수 문자열, initialized는 초기값 7인 정적 객체, zeroed는 0으로 초기화되는 1024바이트 객체입니다. -O0 빌드에서 보통 .rodata, .data, .bss와 연결해 관찰할 수 있습니다. 실제 대응은 심볼 표와 주소로 확인하며 이름만으로 자료의 성격을 단정하지 않습니다.

.bss의 NOBITS는 해당 크기의 초기값 바이트를 파일에 그대로 저장하지 않는다는 뜻입니다. 적재 후 필요한 메모리는 존재하므로 LOAD의 MemSiz가 FileSiz보다 클 수 있습니다. 파일에서 바이트가 없다는 사실을 실행 중 메모리도 없다는 주장으로 바꾸면 안 됩니다.

파일 오프셋은 디스크 안 위치, 가상주소는 프로세스 주소 공간의 위치입니다. PIE와 ASLR 때문에 실행 주소가 매번 달라질 수 있습니다. 이 차시는 ELF 정적 구조를 읽는 단계이며 런타임 매핑 전체나 권한 변화·실행 여부를 이 표 하나로 증명하지 않습니다.

자주 헷갈리는 지점

파일 오프셋과 가상주소를 같은 좌표로 쓴다.
도구 열 이름과 PIE/ASLR 가정을 함께 기록합니다.
섹션과 세그먼트는 항상 1대1이다.
Section to Segment mapping으로 실제 대응을 확인합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL x86-64 · GCC·GNU binutils
gcc -g -O0 -Wall -Wextra layout.c -o layout
./layout
readelf -SW layout
readelf -lW layout

변경 전 예상 결과와 해석

BF-LAYOUT init=7 zero=0
섹션 표에 .text/.rodata/.data/.bss, 프로그램 헤더에 LOAD가 보입니다. 주소·크기의 정확한 값은 빌드마다 다릅니다.

이제 단계별로 바꾸고 관찰하기

  1. 동작과 심볼 기준 만들기

    분석할 소스를 직접 빌드하고 실행해 초기값이 예상대로인지 확인합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL x86-64 · GCC·GNU binutils
    gcc -g -O0 -Wall -Wextra layout.c -o layout
./layout
    관찰할 결과
    BF-LAYOUT init=7 zero=0

  2. 섹션별 저장 형태 읽기

    -S는 섹션, -s는 심볼입니다. zeroed의 섹션 인덱스와 .bss의 NOBITS를 연결합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL x86-64 · GCC·GNU binutils
    readelf -SW layout
readelf -sW layout
    관찰할 결과
    .bss는 NOBITS, zeroed 심볼 크기는 1024입니다. 인덱스·주소는 고정하지 않습니다.

  3. 적재 관점과 대조하기

    -l의 LOAD 권한 및 파일/메모리 크기와 아래의 Section to Segment mapping을 읽습니다. 섹션 하나가 세그먼트 하나라고 가정하지 않습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL x86-64 · GCC·GNU binutils
    readelf -lW layout
    관찰할 결과
    LOAD 항목과 섹션-세그먼트 대응이 출력됩니다. .bss가 포함된 적재 영역은 파일 데이터 외에 0 초기화 메모리를 필요로 합니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

zeroed 배열을 1024에서 2048로 늘린 사본을 빌드해 .bss 크기와 LOAD의 FileSiz/MemSiz를 비교하세요. 파일 전체 크기가 반드시 1024만큼 늘지 않는 이유를 쓰세요.

막혔을 때 힌트 보기

NOBITS와 Section to Segment mapping을 확인합니다. 파일 크기, 섹션 크기, 메모리 크기는 서로 다른 값입니다.

과제 해설과 예시 답안 보기
  1. 사본에서 zeroed[2048]로 고치고 -g -O0로 다시 빌드합니다.
  2. 심볼 크기가 1024→2048이고 .bss/적재 메모리 요구가 늘었는지 비교합니다.
  3. NOBITS는 초기값을 파일에 1024바이트 더 저장하는 방식이 아니므로 실행 파일 전체 크기 증가량을 배열 증가량과 같다고 단정하지 않습니다.

결과를 판단하는 기준

두 빌드의 zeroed 크기·.bss 유형·해당 LOAD 파일/메모리 크기를 실제 출력으로 비교합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
