01 / UNDERSTAND

먼저 이해하기

컴파일러는 소스를 번역하고 링커는 필요한 코드와 심볼을 연결합니다. 실행 파일의 형식과 CPU가 환경에 맞아야 실행할 수 있습니다. Linux ELF 파일을 Windows 기본 셸에서 그대로 실행하는 흐름과 WSL에서 실행하는 흐름을 구분하세요.

-g는 소스 줄과 변수의 디버깅 정보를 추가하고 -O0는 이 실습의 관찰을 단순하게 합니다. 실제 배포 빌드는 최적화로 변수와 명령 배치가 달라질 수 있습니다. 경고가 없다 해도 안전이 증명된 것은 아닙니다.

실습은 소스 memory.c → 컴파일·링크 → 실행 파일 memory → 프로세스 실행의 네 단계를 구분합니다. 파일 내용이 소스 문자라고 실행 가능한 것은 아니며, 컴파일이 실패했는데 이전 memory가 남아 있으면 오래된 코드를 실행할 수 있습니다.

경고 옵션은 의심스러운 코드를 더 많이 알려 주지만 모든 잘못된 메모리 접근을 찾아 주지는 않습니다. 오류 없이 빌드됐다는 사실, 예상 출력이 맞다는 사실, 모든 입력에서 안전하다는 주장은 서로 다른 근거가 필요합니다.

반환 코드도 출력과 따로 기록할 수 있습니다. Bash에서 실행 직후 echo $?는 직전 명령의 종료 상태를 보여 줍니다. 중간에 다른 명령을 넣으면 그 명령의 상태로 바뀌므로 검사 위치를 맞춥니다.

자주 헷갈리는 지점

Linux ELF를 Windows 기본 환경의 실행 파일과 같은 것으로 취급한다.
OS 형식과 CPU를 기록하고 이 차시는 Ubuntu/WSL에서 실행합니다.
빌드 명령 뒤 file을 실행한 다음 echo $?를 보고 빌드 상태라고 부른다.
echo $?는 직전 명령의 상태이므로 컴파일 바로 다음에 확인합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC・file
gcc -Wall -Wextra -g -O0 memory.c -o memory
file memory
./memory

변경 전 예상 결과와 해석

local=7 heap=9
10 20 30
file 출력의 아키텍처·ELF 정보는 환경마다 다릅니다.

이제 단계별로 바꾸고 관찰하기

  1. 빌드 조건을 고정하기

    파일과 도구의 조건을 먼저 적습니다. uname -m은 현재 Linux 실행 환경의 아키텍처를 보여 줍니다. file의 결과와 대조할 기준입니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC・file
    gcc --version
uname -m
ls -l memory.c
    관찰할 결과
    GCC 버전, 예: x86_64 또는 aarch64, 소스 파일 정보를 얻습니다.

  2. 실행 파일 만들기

    컴파일 명령의 종료 상태를 바로 확인합니다. 0이 아니라면 진단 메시지부터 해결하고 실행 단계로 넘어가지 않습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC・file
    gcc -Wall -Wextra -g -O0 memory.c -o memory
echo $?
file memory
    관찰할 결과
    빌드 성공 시 종료 상태는 0이고 file은 현재 환경에 맞는 ELF 실행 파일 정보를 보여 줍니다.

  3. 한 줄 변경의 효과 재확인하기

    사본에서 local = 7을 local = 8로 바꾸고 같은 명령으로 다시 빌드합니다. malloc 영역에 쓰는 9나 배열 값은 바꾸지 않아 결과 원인을 하나로 제한합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC・file
    ./memory
echo $?
    관찰할 결과
    기준 출력은 local=7 heap=9 / 10 20 30이며 성공 종료 상태는 0입니다. 수정 빌드라면 local=8만 달라집니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

컴파일 명령, gcc 버전, uname -m, file 결과를 함께 남기세요. 소스를 한 줄 바꾼 후 다시 빌드합니다.

막혔을 때 힌트 보기

Permission denied는 실행 권한, Exec format error는 형식·CPU 불일치 가능성을 먼저 구분합니다.

과제 해설과 예시 답안 보기
  1. 원본 기준 GCC 버전·CPU·정확한 빌드 명령·file 출력·실행 결과를 한 묶음으로 기록합니다.
  2. memory.c 사본에서 local 초기값만 8로 바꾸고 컴파일 성공을 확인한 뒤 그 출력 파일을 실행합니다.
  3. 컴파일 실패는 번역/링크 단계, Permission denied나 Exec format error는 실행 단계라는 점을 기록합니다. 메시지별 실제 원인은 추가 확인합니다.

결과를 판단하는 기준

기준은 local=7 heap=9 / 10 20 30입니다. local만 8로 바꿔 재빌드하면 local=8 heap=9 / 10 20 30입니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
