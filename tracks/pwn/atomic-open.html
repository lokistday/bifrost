01 / UNDERSTAND

먼저 이해하기

파일 이름은 시점에 따라 다른 객체를 가리킬 수 있습니다. 존재·속성을 먼저 검사하고 같은 이름을 다시 열면 둘 사이에 바뀔 수 있는데, 이를 TOCTOU 경계라고 합니다. 검사가 정확해도 사용 시점에 같은 객체라는 가정이 유지되는지 따져야 합니다.

새 파일을 만들 때 O_CREAT|O_EXCL을 함께 쓰면 이미 있는 이름을 덮어쓰지 않는 생성을 요청합니다. exists 검사 후 별도 생성으로 나누는 것보다 검사와 생성을 한 연산에 결합합니다. 이 보장의 세부와 파일 시스템 특성은 해당 OS 문서에서 확인합니다.

open_regular는 고정 디렉터리 FD와 단일 구성 요소 이름을 사용해 openat하고 O_NOFOLLOW로 마지막 구성 요소 심볼릭 링크를 거부합니다. 연 뒤에는 fstat으로 실제 열린 객체가 일반 파일인지 확인합니다. 경로 문자열에 대한 이전 검사만 믿지 않고 사용 중인 객체를 봅니다.

O_NOFOLLOW는 모든 상위 경로와 hard link·마운트·소유자·내용까지 보장하는 만능 옵션이 아닙니다. 이번 모형은 mkdtemp로 만든 자기 디렉터리, 제한된 이름, 고정 dirfd라는 전제입니다. 실제 서비스는 디렉터리 제어와 소유자·권한·목적에 맞는 객체 검증이 필요합니다.

이름을 unlink해도 이미 열린 FD는 객체를 계속 참조할 수 있습니다. 마지막 fstat은 이름과 객체 수명을 구분해 보여 줍니다. 임의 공격자 경합을 실제로 발생시켜 확률을 측정한 실험은 아니며, 자기 일반 파일·자기 심볼릭 링크·중복 생성만 결정적으로 비교합니다.

자주 헷갈리는 지점

존재 여부를 검사한 경로는 나중에도 반드시 같은 파일이라고 생각한다.
이름의 변경 가능성을 고려하고 원자적 생성·열린 객체 검증·디렉터리 제어를 설계합니다.
O_NOFOLLOW 하나면 상위 경로·hard link·소유자까지 모두 검증된다고 생각한다.
마지막 구성 요소 정책과 다른 신뢰 경계를 구분합니다. 이 실습의 전제를 명시합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

작업 사본의 open_regular에서 O_NOFOLLOW만 제거하면 alias가 열려 정상 symlink 거부 기대가 실패하는지 확인하세요. 실제 외부 파일은 쓰지 말고 프로그램이 만든 note.txt 링크만 사용한 뒤 원본을 복구하세요.

막혔을 때 힌트 보기

이 결함 표본은 자기 일반 파일로 향하는 링크를 열었는지 확인하고 실패 상태로 끝납니다. 임의 경로로 링크를 만들 필요가 없습니다.

과제 해설과 예시 답안 보기
  1. 원본의 네 줄과 종료 상태 0을 먼저 기록합니다. O_NOFOLLOW만 뺀 사본에서는 alias가 열려 의도한 거부 계약을 만족하지 못해 상태 2가 나와야 합니다.
  2. 변경한 코드가 fstat 일반 파일 검사는 유지해도 symlink 마지막 구성 요소를 막는 정책은 사라진다고 설명합니다. 객체 유형과 이름 해석은 다른 검사입니다.
  3. 복구 뒤 네 줄·상태 0·자기 임시 자원 정리를 확인하고, 상위 경로·hard link·동시 경합·소유자 검증은 이 실험에서 증명하지 않았다고 적습니다.

결과를 판단하는 기준

정상 구현은 네 경계와 상태 0을 만족하고 nofollow 제거 사본은 정상 종료 기대에서 실패합니다. 실제 운영 경합 방어가 완성됐다고 확대하지 않습니다.
