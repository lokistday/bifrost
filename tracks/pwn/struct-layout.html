01 / UNDERSTAND

먼저 이해하기

C struct는 필드를 묶지만 메모리에 필드 크기의 합만큼 빽빽하게 저장된다고 보장하지 않습니다. ABI와 정렬 때문에 필드 사이·끝에 padding이 들어갈 수 있습니다. sizeof와 offsetof로 관찰한 배치는 그 실행 환경의 사실이며 다른 컴파일러·플랫폼의 전송 명세가 아닙니다.

구조체 전체를 그대로 전송하면 padding·엔디언·정수 표현 같은 호스트 세부가 신뢰 경계를 넘습니다. 초기화한 멤버 값만 보고 모든 padding 값도 의미 있게 정해졌다고 가정하지 않습니다. 구조체 비교를 memcmp 하나로 대체하는 것도 논리 필드 비교와 다를 수 있습니다.

이 실습의 가상 전송 형식은 type 1바이트, code 4바이트 big-endian, count 2바이트 big-endian으로 정확히 7바이트입니다. encode는 멤버 값을 비트 연산으로 바이트에 넣고 decode는 명세대로 복원합니다. 구조체의 실제 sizeof가 얼마든 전송 크기는 계약으로 정합니다.

decode는 필드 접근 전에 입력 크기가 정확히 7인지 확인합니다. 이전 파서 차시의 길이 검사를 유지하면서, 이번에는 유효한 바이트를 호스트 값으로 옮기는 단계를 배웁니다. 직렬화 성공은 메시지 인증·권한·값의 업무 범위까지 검증한 것은 아닙니다.

기본 모드는 의미 있는 멤버만 출력하고 padding을 덤프하지 않습니다. --layout은 sizeof와 offsetof의 관찰용입니다. 바이트 순서와 자료형 크기 계약을 바꾸면 인코더·디코더·표본·테스트를 함께 바꿔야 하며 packed 옵션만으로 모든 이식성을 얻는다고 가정하지 않습니다.

자주 헷갈리는 지점

sizeof(struct)가 곧 네트워크 메시지 길이라고 생각한다.
호스트 배치와 전송 형식을 따로 정하고 명시적으로 직렬화합니다.
멤버를 초기화했으니 padding도 안전한 의미를 가진다고 가정한다.
padding은 논리 필드가 아닙니다. 신뢰 경계를 넘길 때 멤버를 정한 형식으로 인코딩합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

사본에서 code를 0x0A0B0C0D로 바꾸고 전송 Hex를 예상하세요. decode의 바이트 순서를 고의로 뒤집으면 왕복 검사가 실패하는지도 확인한 뒤 복구하세요.

막혔을 때 힌트 보기

전송 순서에서 type와 count는 유지하고 code 네 바이트만 바뀝니다. 호스트 엔디언을 추측해 struct를 덤프하는 방식으로 과제를 해결하지 않습니다.

과제 해설과 예시 답안 보기
  1. code만 바꾸면 기대 Hex는 010a0b0c0d0506이고 전송 길이는 7입니다. roundtrip=True와 short=REJECT도 유지되어야 합니다.
  2. decode의 상위·하위 code 바이트 위치를 바꾼 사본은 같은 멤버 값으로 돌아오지 않아 roundtrip=False가 됩니다. 독립된 고정 Hex와 왕복을 둘 다 검사합니다.
  3. 복구 뒤 테스트를 통과시키고, sizeof(struct)가 아닌 명시적 전송 계약이 이식성의 근거라고 설명합니다.

결과를 판단하는 기준

변경 Hex 010a0b0c0d0506과 왕복 True를 확인합니다. 고의 바이트 순서 결함은 검출되어야 하며 메모리 배치 수치를 전송 명세로 쓰지 않습니다.
