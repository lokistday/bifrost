01 / UNDERSTAND

먼저 이해하기

정의되지 않은 동작은 매번 충돌하지 않을 수 있습니다. bounds.c는 범위를 넘은 값을 읽으며 실행 결과 자체를 정답으로 삼을 수 없습니다. AddressSanitizer는 메모리 접근을 검사하는 코드를 빌드에 추가해 오류 위치를 찾도록 돕습니다.

진단의 맨 위 오류 유형, 접근 크기, 처음 사용자 코드가 나오는 줄을 읽습니다. 도구가 검출하지 않았다는 사실이 모든 입력의 안전을 보장하지 않습니다. 수정 후 같은 입력과 경계 조건을 다시 확인해야 합니다.

배열 밖 값을 출력했는데 숫자가 나왔다는 사실은 그 접근이 허용됐다는 뜻이 아닙니다. 값이 쓰레기처럼 보이든 우연히 익숙한 숫자이든 정의되지 않은 동작의 결과를 예상 출력으로 삼지 않습니다. 검사 대상은 i=3일 때 배열을 읽는 지점입니다.

AddressSanitizer의 보고서에는 오류 분류, 읽기/쓰기 종류와 크기, 호출 스택, 관련 객체의 범위 등이 나올 수 있습니다. 라이브러리 내부 줄보다 처음 등장하는 자신의 bounds.c 줄과 values의 유효 범위를 연결해 원인을 설명하세요.

고친 뒤 도구 진단이 사라지는 것과 올바른 기능이 유지되는 것을 함께 확인합니다. 진단 없음만 기록하면 루프를 통째로 지워 아무것도 출력하지 않는 수정도 통과로 오해할 수 있습니다. 세 유효 원소가 정확히 한 번씩 출력되는지까지 봅니다.

자주 헷갈리는 지점

수정본에서 계측 옵션을 빼고 보고서가 사라졌다고 비교한다.
전후 빌드와 입력을 동일하게 유지하고 변경한 원인 줄만 비교합니다.
진단 보고서의 주소를 외우고 배열 길이는 설명하지 못한다.
주소 대신 객체 범위·접근 인덱스·최초 잘못된 줄을 연결해 원인을 적습니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC AddressSanitizer
gcc -g -O0 -fsanitize=address -fno-omit-frame-pointer bounds.c -o bounds
./bounds

변경 전 예상 결과와 해석

AddressSanitizer가 stack-buffer-overflow 등 배열 범위 밖 읽기를 진단합니다. 문구·주소·종료 코드는 도구 버전에 따라 다를 수 있습니다.

이제 단계별로 바꾸고 관찰하기

  1. 오류 예제를 계측하여 빌드하기

    본문 옵션을 사용합니다. -g는 소스 위치를 연결하고 -fno-omit-frame-pointer는 스택 추적을 읽는 데 도움을 줍니다. 빌드가 성공한 뒤 실행합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC AddressSanitizer
    gcc -g -O0 -fsanitize=address -fno-omit-frame-pointer bounds.c -o bounds
./bounds
    관찰할 결과
    배열 범위 밖 읽기에 대한 AddressSanitizer 보고서가 나와야 합니다. 실제 주소나 전체 문구는 고정하지 않습니다.

  2. 보고서를 입력 범위와 연결하기

    보고서에서 READ, 사용자 코드 줄, values 객체 범위를 찾습니다. 원소 수 3과 마지막 유효 인덱스 2를 쓰고 루프의 i=3 접근이 왜 벗어나는지 설명합니다.

  3. 같은 옵션으로 수정본 재검증하기

    bounds-fixed.c에서 조건을 < 3으로 바꿉니다. 처음과 같은 계측 옵션으로 별도 실행 파일을 만들어 비교해야 도구를 빼서 진단이 사라진 상황과 구분할 수 있습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC AddressSanitizer
    gcc -g -O0 -fsanitize=address -fno-omit-frame-pointer bounds-fixed.c -o bounds-fixed
./bounds-fixed
    관찰할 결과

20
30

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

복사한 코드에서 반복 조건을 고쳐 같은 옵션으로 빌드하고 오류가 사라지는지 확인하세요. 변경한 줄과 진단 전·후를 남깁니다.

막혔을 때 힌트 보기

Sanitizer 런타임을 찾지 못하면 Ubuntu GCC 설치를 확인하세요. 정상 출력 숫자보다 첫 잘못된 접근 줄이 핵심입니다.

과제 해설과 예시 답안 보기
  1. 원본 보고서에서 오류 유형과 처음 사용자 코드가 나오는 줄을 보관합니다. 무의미한 네 번째 숫자를 정답으로 적지 않습니다.
  2. 사본의 <= 3을 < 3으로 바꾸고 같은 Sanitizer 옵션으로 빌드합니다.
  3. 수정본이 10·20·30을 출력하고 해당 진단이 없는지 확인합니다. 이 입력과 이 빌드에서 확인한 결과라는 한계를 보고서에 적습니다.

결과를 판단하는 기준

원본은 범위 밖 읽기 진단, 수정본은 세 줄의 정상 출력과 해당 진단 없음입니다. 두 빌드의 옵션이 동일해야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

INDEPENDENT PRACTICE

도움 없이, 조건을 바꿔 보기

수정한 프로그램에서 정상 입력과 거부할 길이를 모두 실행하고 Sanitizer가 조용하다는 사실의 한계를 적으세요.

  1. 위 해설을 닫고 예상 결과와 근거를 먼저 적습니다.
  2. 코드·원시 자료·문서 근거로 확인하고 예상과 실제 차이를 설명합니다.
  3. 새 반례 하나를 만들고 무엇까지 확인했는지 기록합니다.

05 / VERIFY

이해한 내용을 점검하기

답을 고른 뒤 이유까지 확인하세요. 점수는 저장하지 않습니다.

1. 수정 후 Sanitizer 보고서가 사라졌지만 아무 값도 출력하지 않습니다. 완료로 보기 어려운 이유는?

정답과 이유 읽기

정답: 배열을 읽는 정상 기능도 유지되는지 확인해야 하기 때문이다.

오류 제거와 기능 유지가 함께 목표입니다. 세 유효 원소가 기대대로 출력되는지도 검증해야 합니다.

2. Sanitizer 없이 실행했을 때 충돌이 없었습니다. 경계 오류가 없다는 근거인가요?

정답과 이유 읽기

정답: 아니다. 정의되지 않은 동작은 정상처럼 보일 수도 있다.

충돌 여부는 유효 범위의 증명이 아닙니다. 코드의 인덱스와 객체 범위를 확인하고 도구로 관찰을 보완합니다.

내 결과물 확인하기

  • 최초 잘못된 접근과 범위를 설명했다.
  • 수정 후 동일 도구로 재검증했다.
