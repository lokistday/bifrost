01 / UNDERSTAND

먼저 이해하기

스트림 I/O의 한 번 read가 메시지 하나와 같다고 보장되지 않습니다. 헤더 일부만 오거나 본문이 여러 조각으로 나뉠 수 있고, write도 일부만 처리할 수 있습니다. 실제 처리한 양을 확인하고 남은 구간을 누적해야 메시지 경계를 유지할 수 있습니다.

stream_chunks는 매번 최대 2바이트만 반환하는 결정적 메모리 어댑터를 사용합니다. OS의 스케줄러나 네트워크를 제어하는 예제가 아닙니다. read_exact는 원하는 양을 모을 때까지 반복하고, 중간에 0을 만나면 필요한 입력을 다 받지 못한 것으로 거부합니다.

frame은 헤더 2바이트를 먼저 모아 길이를 읽고 최대 본문 16바이트 제한을 확인한 뒤 본문을 모읍니다. 이전 파서가 완성된 입력 전체를 검사했다면 이번에는 입력을 완성하는 과정이 추가됩니다. 예제 payload는 알려진 ASCII BIFRO이며 일반 바이너리를 문자열로 출력하는 라이브러리가 아닙니다.

write_all도 한 번 쓴 양만큼 위치를 옮겨 남은 바이트를 보냅니다. 진행량 0을 성공으로 무한 반복하면 멈추지 않을 수 있어 이 어댑터는 명시적으로 거부합니다. 실제 시스템의 EINTR·EAGAIN·타임아웃·반닫힘은 이 부분 모형의 0 반환과 동일한 의미로 뭉치지 않습니다.

기본 완전 입력은 헤더 한 번과 본문 세 번, 총 네 번의 짧은 읽기로 처리됩니다. 잘린 본문은 일부를 모아도 EOF에서 실패해야 합니다. 크기 상한·기다림 상한·동시 연결 자원·다중 메시지 버퍼 관리는 실제 서버에서 추가 설계가 필요합니다.

자주 헷갈리는 지점

한 번의 read나 write가 요청한 길이를 반드시 처리한다고 생각한다.
반환된 실제 양을 누적하고 남은 구간·EOF·오류를 처리합니다.
진행량 0일 때 같은 호출을 무한 반복하면 언젠가 성공한다고 생각한다.
0의 의미와 기다림 정책을 명시합니다. 이번 writer 모형은 0 진행을 거부합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

사본의 full·short_body reader와 정상 writer의 chunk를 모두 2에서 1로 바꿔 호출 수를 예상하세요. 그 뒤 누적 루프를 한 번의 호출로 바꾼 결함이 완전 입력 성공 검사에 잡히는 이유를 설명하세요.

막혔을 때 힌트 보기

헤더 2와 본문 5를 따로 셉니다. 잘린 입력의 EOF 확인도 호출 한 번이고, writer는 총 7바이트를 처리합니다.

과제 해설과 예시 답안 보기
  1. chunk=1이면 완전 입력은 헤더 2회+본문 5회=7회, 잘린 입력은 헤더 2회+본문 3회+EOF 1회=6회입니다.
  2. 정상 writer는 7회로 written=7이고 0 진행 writer는 계속 REJECT입니다. 서로 다른 reader/writer의 chunk 필드를 모두 바꿨는지 확인합니다.
  3. 한 번 읽은 양이 원하는 길이보다 작을 수 있어 단일 호출을 전체 성공으로 처리하는 코드는 잘못됐다고 설명합니다. 실제 syscall의 신호·비차단 처리와 시간 제한은 미구현 범위입니다.

결과를 판단하는 기준

변경 뒤 reads=7/6, written=7 calls=7, stalled=REJECT입니다. 호출 수만 맞추려고 결과 문자열을 수정하지 않습니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

1. 본문 5바이트를 요청했지만 2바이트만 왔습니다. 적절한 처리는?

정답과 이유 읽기

정답: 실제 받은 2바이트를 누적하고 남은 3바이트를 읽는다.

짧은 읽기는 정상 상황일 수 있습니다. 반환량을 기준으로 남은 길이를 추적해야 합니다.

2. 실습에서 read_some은 0으로 EOF를 표현합니다. 실제 EAGAIN도 똑같이 EOF로 처리해도 되나요?

정답과 이유 읽기

정답: 아니다. 비차단 대기 상태·EOF·오류의 의미를 따로 설계해야 한다.

이 어댑터는 제한된 모형입니다. 실제 syscall의 오류·신호·대기 조건을 같은 성공/EOF 의미로 합치면 안 됩니다.
