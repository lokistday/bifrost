01 / UNDERSTAND

먼저 이해하기

바이너리 형식은 몇 바이트가 어떤 순서로 무엇을 뜻하는지 계약이 필요합니다. 이 실습의 가상 형식은 첫 2바이트가 big-endian payload 길이이고, 뒤에 그 길이만큼의 바이트가 와야 합니다. 다른 프로토콜의 실제 헤더나 파일 형식이 아닙니다.

헤더를 읽기 전에 size>=2를 확인해야 data[0]과 data[1]이 유효합니다. 그런 다음 상위 바이트를 8비트 왼쪽으로 옮기고 하위 바이트와 OR해 길이를 만듭니다. unsigned char를 사용해 부호 확장에 대한 혼동을 줄입니다.

길이 비교는 length == size-2입니다. size>=2를 먼저 검사했으므로 뺄셈이 underflow하지 않습니다. length+2를 먼저 계산하는 방식보다 연산 전제와 입력 잔여 길이가 드러나며, 짧은 payload와 여분 바이트를 모두 구분 없이 거부하는 엄격한 계약입니다.

입력 버퍼를 C struct 포인터로 강제 변환하면 정렬·padding·엔디언·실제 길이 같은 가정이 섞일 수 있습니다. 이 작은 예제는 바이트를 명시적으로 읽어 호스트의 메모리 배치와 전송 형식을 분리합니다. 복잡한 형식은 검증된 파서와 명세를 사용합니다.

이 함수는 전달된 버퍼와 크기가 실제로 유효하다는 호출자 전제에서 길이만 확인합니다. payload 내용, 인증, 압축 크기, 여러 메시지 스트림의 분리는 다루지 않습니다. 패킷 조각을 받는 실제 네트워크 프로그램에서는 한 번의 읽기가 한 메시지와 같다는 가정도 피해야 합니다.

자주 헷갈리는 지점

길이 필드부터 읽은 뒤 입력이 짧은지 확인한다.
필드를 읽기 전에 최소 헤더 바이트가 있는지 먼저 검사합니다.
네트워크 바이트를 struct로 cast하면 모든 플랫폼에서 같은 뜻이라고 생각한다.
padding·정렬·엔디언·길이 전제를 검토해야 합니다. 이 예제는 바이트를 명시적으로 해석합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC · C11 · 로컬 소스 실습
gcc -std=c11 -Wall -Wextra -Werror -Wformat=2 -g -O0 packet_parse.c -o packet_parse
./packet_parse

변경 전 예상 결과와 해석

정상 길이 3만 OK이고 잘린 헤더·짧은 본문·여분 바이트는 REJECT입니다.

이제 단계별로 바꾸고 관찰하기

  1. 정상 표본을 손으로 읽기

    normal은 00 03 42 49 46입니다. 첫 두 바이트의 길이는 3, 뒤의 BIF는 3바이트입니다. 손으로 계산한 값과 실행 결과를 비교합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC · C11 · 로컬 소스 실습
    gcc -std=c11 -Wall -Wextra -Werror -Wformat=2 -g -O0 packet_parse.c -o packet_parse
./packet_parse
    관찰할 결과
    normal=OK length=3
short-header=REJECT
short-body=REJECT
extra-byte=REJECT

  2. 헤더·본문·여분 바이트 경계 구분하기

    short_header는 1바이트뿐이라 헤더 전에 거부됩니다. short_body는 길이 4라고 적었지만 실제 3바이트이고 extra는 길이 1보다 실제 2바이트가 있어 둘 다 거부됩니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC · C11 · 로컬 소스 실습
    ./packet_parse
    관찰할 결과
    세 잘못된 표본 모두 REJECT. 이름은 서로 다른 원인을 구분하기 위한 것입니다.

  3. 같은 파서를 계측해서 재검증하기

    잘못된 표본에서도 헤더를 읽기 전에 길이를 검사하므로 경계 밖 읽기 없이 거부되어야 합니다. 계측의 검사 범위는 제공 표본의 실행 경로입니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Ubuntu/WSL · GCC · C11 · 로컬 소스 실습
    gcc -std=c11 -Wall -Wextra -g -O0 -fsanitize=address,undefined -fno-omit-frame-pointer packet_parse.c -o packet-asan
./packet-asan
    관찰할 결과
    정상·거부의 네 줄이 유지되고 실행한 경로에서 계측 진단이 없어야 합니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

사본의 normal 길이 필드를 00 02로 바꾸고 거부를 확인한 뒤 원래대로 복구하세요. 빈 payload {0,0}을 새 사례로 추가해 허용 여부를 설명하세요.

막혔을 때 힌트 보기

이번 계약은 length와 남은 입력 크기가 정확히 같아야 합니다. 빈 payload는 별도로 금지하지 않았으므로 0과 0을 비교하게 됩니다.

과제 해설과 예시 답안 보기
  1. normal의 헤더를 00 02로 바꾸면 실제 본문 3바이트와 달라 REJECT입니다. 실패 시 length 출력값은 유효한 파싱 결과로 사용하지 않아야 한다고 기록합니다.
  2. 새 표본 {0,0}은 전체 size=2이고 선언 길이=0, 잔여=0이므로 OK length=0입니다. 업무상 빈 본문이 금지되어야 한다면 별도 조건과 테스트가 필요합니다.
  3. 헤더 크기 확인 → 바이트 순서 해석 → 잔여 길이 비교 → 성공일 때만 out 사용의 네 단계와 이번 형식의 한계를 적습니다.

결과를 판단하는 기준

변경한 길이는 거부, 복구하면 정상 OK length=3, 새 빈 본문은 OK length=0입니다. 실패 out 값을 성공 값처럼 쓰지 않는 조건을 확인합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
