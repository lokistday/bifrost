01 / UNDERSTAND

먼저 이해하기

분석 결과를 비교할 때 JSON 공백이나 객체 키 순서만 달라 해시가 바뀌면 의미 변경과 표현 변경을 혼동하기 쉽습니다. 이 실습은 schema=1, 고유 ID와 상태를 갖는 events 목록이라는 좁은 계약을 정하고 의미가 같은 입력의 표현을 정규화합니다.

canonical은 events를 ID로 정렬하고 객체 키를 정렬하며 불필요한 공백 없이 ASCII JSON으로 직렬화합니다. 이 계약에서는 events 순서를 의미에 포함하지 않으므로 역순 입력이 같은 바이트가 됩니다. 순서가 의미인 실제 이벤트 스트림에 이 규칙을 그대로 적용하면 정보를 잃습니다.

반대로 상태값이 ok에서 denied로 바뀌면 정규화 뒤 바이트와 해시도 달라져야 합니다. verify는 순서만 바꾼 동등 사례와 실제 값이 바뀐 비동등 사례를 함께 비교합니다. 중복 ID와 허용하지 않은 상태는 애매하게 덮어쓰지 않고 거부합니다.

SHA-256은 결과 바이트의 비교에 유용하지만 제작자의 신원이나 원본 자료의 사실성을 보증하지 않습니다. 재현 가능한 분석에는 입력 해시, 스크립트 버전, 명령, 환경, 정규화 계약도 함께 남겨야 합니다. 이 예제의 정규화는 범용 JSON 서명 표준이나 완전한 증거 관리 체계가 아닙니다.

자주 헷갈리는 지점

정렬하면 어떤 데이터든 의미가 보존된다.
순서가 의미인지 먼저 정하고 필요한 경우 그대로 보존합니다.
결과 해시만 있으면 재현 절차를 생략한다.
입력·코드·환경·명령·정규화 계약을 함께 남깁니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
python3 toolbox.py verify

변경 전 예상 결과와 해석

canonical={"events":[{"id":"R01","status":"ok"},{"id":"R02","status":"denied"}],"schema":1}
order-independent=True value-sensitive=True
sha256=b9d3a37611682440379f60a8ba04705e66a71a7b5f5e0f6bd8975c5b3b2a191c

이제 단계별로 바꾸고 관찰하기

  1. 계약과 정규화 출력 읽기

    입력의 이벤트 순서는 R02,R01이지만 출력은 ID 정렬로 R01,R02입니다. 키 순서·공백·인코딩 규칙을 함께 기록합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
    python3 toolbox.py verify
    관찰할 결과
    order-independent=True value-sensitive=True와 고정 SHA-256이 출력됩니다.

  2. 순서 변경의 동등성 확인

    사본의 events 순서만 뒤집습니다. 값과 ID는 유지해 정규화가 같은 바이트를 만드는지 비교합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
    python3 toolbox.py verify --source repro-order.json
    관찰할 결과
    원본과 canonical 및 sha256이 같습니다. order-independent=True입니다.

  3. 값 변경과 구조 오류 구분

    R02 상태만 ok로 바꾼 사본을 실행합니다. 또 다른 사본에는 같은 ID를 두 번 넣어 모호한 입력을 거부하는지 확인합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 오프라인 · Python 3.10 이상 · 표준 라이브러리
    python3 toolbox.py verify --source repro-value.json
python3 toolbox.py verify --source repro-duplicate.json
    관찰할 결과
    값 변경 사본은 다른 sha256을 출력합니다. 중복 사본은 INVALID: duplicate ID, 종료 상태 2입니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

repro.json 사본에서 events 순서만 뒤집고 원본과 해시를 비교하세요. 다른 사본에서 R02 상태를 ok로 바꿔 비교하고, 두 변화의 의미를 기록하세요.

막혔을 때 힌트 보기

이 계약은 순서를 버려도 된다고 먼저 정했습니다. 순서가 사건의 의미라면 정렬 정규화를 쓰면 안 됩니다.

과제 해설과 예시 답안 보기
  1. 순서만 뒤집으면 ID 정렬 뒤 바이트가 같아 원본의 b9d3...a191c 해시가 유지됩니다.
  2. R02=ok 변경은 결과의 의미가 달라 canonical과 해시가 모두 바뀝니다.
  3. 분석 기록에는 원본 입력 해시, toolbox.py 버전/해시, 실행 명령, Python 버전과 순서를 무시한다는 계약을 같이 남깁니다.

결과를 판단하는 기준

표현 순서 변화·값 변화·중복 구조 오류를 분리한 결과와 재현 메타데이터가 있어야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
