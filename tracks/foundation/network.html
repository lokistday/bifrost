01 / UNDERSTAND

먼저 이해하기

IP 주소는 네트워크의 목적지를, 포트는 호스트 안의 통신 끝점을 식별합니다. DNS는 도메인 이름의 레코드를 조회하는 절차입니다. 이름을 안다고 해당 포트 연결이 되는 것은 아니며, DNS 성공과 서비스 성공을 따로 확인해야 합니다.

TCP는 순서·재전송·연결 상태를 제공하고 UDP는 데이터그램을 보냅니다. UDP라는 이유만으로 모든 응용이 신뢰성 없다고 단정할 수는 없습니다. 응용 자체가 추가 기능을 구현할 수 있습니다. 먼저 아래 가상 사례에서 각 값을 분리해 보세요.

하나의 IP에서 여러 서비스를 운영할 수 있어 IP만으로 대상 프로그램을 정할 수 없습니다. TCP 연결을 관찰할 때는 출발지 IP·포트와 목적지 IP·포트를 함께 봅니다. 포트 443을 쓴다는 이유만으로 서비스의 정상 동작이나 안전을 증명할 수는 없습니다.

이 예시의 HTTPS는 TCP 위의 TLS 다음에 HTTP를 주고받는 경우입니다. 모든 HTTPS가 같은 전송 방식은 아니며 HTTP/3는 QUIC을 사용합니다. 지금은 예시의 조건을 명시하고 문제를 이름 조회·전송·암호화 연결·응용 응답으로 나누는 연습에 집중합니다.

자주 헷갈리는 지점

UDP 응용은 모두 복구나 순서 기능이 전혀 없다고 일반화한다.
전송 계층이 제공하는 기능과 응용 프로토콜이 추가한 기능을 나누어 봅니다.
443이라는 숫자만 보고 TLS 인증과 서비스 안전까지 보장된다고 생각한다.
포트는 끝점 식별 정보입니다. 실제 프로토콜·인증서·정책과 응답을 따로 관찰합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

관찰 절차·자료 예시 · 그대로 셸에 붙여 넣지 말고 본문 안내를 따라 확인
이름: bifrost.test
DNS 응답: 192.0.2.20
목적지: 192.0.2.20:443
전송: TCP
응용: HTTPS

변경 전 예상 결과와 해석

이름 조회 → IP 획득 → 목적지 포트 연결 → TLS → HTTP의 순서로 설명할 수 있습니다. 이 주소는 문서용 예시이며 접속 대상이 아닙니다.

이제 단계별로 바꾸고 관찰하기

  1. 이름과 주소의 연결 표시하기

    bifrost.test라는 이름과 DNS 응답 192.0.2.20을 화살표로 연결합니다. 이름과 숫자가 서로 다른 표현임을 표시합니다.

    관찰 절차·자료 예시 · 그대로 셸에 붙여 넣지 말고 본문 안내를 따라 확인
    bifrost.test --DNS 조회--> 192.0.2.20
    관찰할 결과
    조회 성공은 주소를 얻었다는 뜻이며 아직 443 서비스에 연결한 것은 아닙니다.

  2. 포트와 전송을 추가하기

    목적지는 IP:포트, 전송은 TCP로 따로 적습니다. 서버에 도달하더라도 해당 포트가 거부되면 HTTP 내용은 받지 못할 수 있습니다.

    관찰 절차·자료 예시 · 그대로 셸에 붙여 넣지 말고 본문 안내를 따라 확인
    192.0.2.20:443 / TCP → TLS → HTTP
    관찰할 결과
    이 예시의 계층 순서는 전송 연결, TLS, HTTP 요청·응답입니다.

  3. 마지막으로 확인된 단계 찾기

    HTTP 404를 받았다면 응용 계층의 응답까지 관찰한 것입니다. 반면 이름 조회 실패는 목적지 주소를 얻는 단계에서 막혔습니다. 오류 이름만 보고 같은 네트워크 장애로 묶지 않습니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

DNS가 틀린 경우, TCP가 거부된 경우, HTTP 404를 받은 경우를 각각 어느 단계의 문제인지 분류하세요.

막혔을 때 힌트 보기

404 응답을 받았다면 적어도 HTTP 서버와 응답을 주고받았습니다. 이름 조회 실패와 같지 않습니다.

과제 해설과 예시 답안 보기
  1. DNS 실패는 이름·레코드·조회 경로를 확인할 문제로 분류합니다. 이 단계만으로 서버가 꺼졌다고 결론 내리지 않습니다.
  2. TCP 거부는 예시의 목적지 IP·포트에 대한 전송 연결 문제로 분류합니다. 서비스 미수신·방화벽 거부 등 원인은 추가 근거가 필요합니다.
  3. HTTP 404는 요청 대상에 대한 HTTP 응답입니다. 서버까지의 통신 실패와 분리하고 URL 경로와 응답 내용을 확인합니다.

결과를 판단하는 기준

세 사례를 각각 이름 조회 / 전송 연결 / HTTP 응용 응답으로 분류하고 판단 근거를 한 줄씩 남깁니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

INDEPENDENT PRACTICE

도움 없이, 조건을 바꿔 보기

DNS 응답은 있지만 목적지 연결이 시간 초과인 경우와 HTTP 403을 받은 경우를 비교하세요.

  1. 위 해설을 닫고 예상 결과와 근거를 먼저 적습니다.
  2. 코드·원시 자료·문서 근거로 확인하고 예상과 실제 차이를 설명합니다.
  3. 새 반례 하나를 만들고 무엇까지 확인했는지 기록합니다.
시도한 뒤 판단 기준 읽기

시간 초과는 경로·차단·서버 상태 등 여러 가설이 남습니다. 403 응답은 HTTP 처리 단계까지 도달한 근거이며 DNS나 전송 실패로 분류하지 않습니다.
