01 / UNDERSTAND

먼저 이해하기

분석에 도움이 되는 로그는 사건 이름·요청 식별자·결과·상태처럼 의미가 정해진 필드를 가집니다. 전체 요청 dict를 문자열로 덤프하면 비밀번호·토큰·불필요한 개인 정보도 기록될 수 있어, 필요한 필드를 선택하는 경계를 먼저 정합니다.

log_record는 event·request_id·result·status 네 키만 새 dict에 넣습니다. password와 authorization은 키가 있어도 출력하지 않습니다. 허용 필드 목록은 자료 최소화의 한 방법이지만 허용한 필드 안에 사용자가 비밀을 넣는 상황까지 자동으로 감지하지는 못합니다.

JSON 직렬화는 값 안의 줄바꿈을 이스케이프해 한 사건이 한 물리적 줄에 남도록 돕습니다. 사람이 붙인 문자열 로그에서는 입력의 줄바꿈이 새 사건처럼 보일 수 있습니다. JSON을 다시 화면에 표시할 때는 뷰어의 해석 방식도 검토해야 합니다.

event는 정해진 이름 문법, result는 세 값의 집합, status는 정확한 정수 범위를 검사합니다. request_id는 짧은 텍스트로 제한합니다. 구조가 맞아도 사건 내용이 진실이라는 보장은 없어 출처·시간·서버가 생성한 식별자 같은 추가 맥락이 중요합니다.

이 차시는 로그 직렬화와 최소 필드 선택을 검증합니다. 실제 logging 핸들러의 전송·보관·접근 제어·회전·시계 동기화는 포함하지 않습니다. 디버그 수준을 낮추거나 오류를 많이 쓴다고 비밀이 안전해지는 것은 아니므로 수집 목적과 보관 정책도 따로 설계합니다.

자주 헷갈리는 지점

허용 필드만 골랐으니 어떤 값에도 비밀이 없다고 단정한다.
허용 필드에도 잘못된 값이 들어올 수 있습니다. 수집 지점의 값 정책과 민감 정보 검토가 필요합니다.
로그의 문자열을 수동 연결하고 줄바꿈을 사건 경계로 믿는다.
구조화 직렬화와 길이 제한으로 경계를 명시하고 소비하는 뷰어에서도 안전하게 표시합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

입력에 password·authorization·body를 추가해도 출력 키가 네 개인지 확인하세요. request_id에 줄바꿈을 넣고 한 줄 유지와 JSON 왕복을 검사한 뒤, 허용 필드에 비밀을 넣으면 왜 여전히 노출될 수 있는지 설명하세요.

막혔을 때 힌트 보기

필드 선택과 값의 비밀 탐지는 다릅니다. request_id 값으로 비밀을 넣어도 이 함수가 자동으로 알아내지는 못합니다.

과제 해설과 예시 답안 보기
  1. json.loads(line)의 키 집합을 {event,request_id,result,status}와 비교합니다. password·authorization·body는 원본 값과 관계없이 출력에서 빠져야 합니다.
  2. request_id의 줄바꿈은 JSON 문자열에서 이스케이프되어 splitlines는 1이고 파싱 후에는 원래 값과 같아야 합니다.
  3. request_id에 비밀을 넣으면 그대로 선택될 수 있다고 적고, 실제 요청 ID는 서버가 정한 비민감 값으로 사용하는 등 수집 지점의 정책이 필요하다고 설명합니다.

결과를 판단하는 기준

허용 키만 포함·한 줄 JSON·입력 값 왕복을 각각 확인합니다. 모든 비밀을 제거하는 범용 마스커나 위변조 방지 로그라고 주장하지 않습니다.
