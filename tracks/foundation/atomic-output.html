01 / UNDERSTAND

먼저 이해하기

대상 파일을 쓰기 모드로 바로 열면 새 결과를 다 쓰기 전에 기존 내용이 사라질 수 있습니다. 보고서를 일부만 생성하고 실패한 경우를 고려하려면, 새 내용을 임시 파일에 완성하고 성공한 뒤 대상 이름으로 교체하는 순서를 사용할 수 있습니다.

with는 블록을 정상 종료하든 예외로 벗어나든 파일 닫기 같은 종료 처리를 요청합니다. 예외가 무조건 없어지는 것은 아닙니다. 임시 파일이 제대로 닫힌 뒤 교체하도록 순서를 정해야 Windows의 열린 파일 제약도 다루기 쉽습니다.

atomic_json은 대상과 같은 폴더에 임시 파일을 만들고 JSON을 쓰고 flush와 fsync를 호출한 뒤 os.replace를 실행합니다. 같은 파일 시스템 안에서 성공한 교체는 중간 내용이 아니라 새 파일로 이름을 전환하도록 돕습니다. 함수는 앱이 통제하는 폴더를 전제로 합니다.

finally는 교체 전 실패로 남은 임시 파일도 정리합니다. fail_before_replace는 실패를 의도적으로 주입하는 표본 옵션입니다. 이때 대상 version=1이 유지되고, 다음 성공 실행에서 version=2로 바뀌는지 확인하면 실패 복구 계약이 명확해집니다.

원자적 이름 교체와 전원 장애 뒤의 완전한 내구성, 여러 파일의 동시 변경, 여러 작성자의 충돌 해결은 같은 보장이 아닙니다. 이 예제는 디렉터리 메타데이터 fsync나 데이터베이스 트랜잭션을 구현하지 않습니다. 파일 권한·소유권 보존 정책도 실제 도구에서 별도로 정해야 합니다.

자주 헷갈리는 지점

with를 쓰면 예외도 자동으로 성공으로 바뀐다고 생각한다.
with는 종료 처리를 관리합니다. 예외 처리·성공 보고·복구 정책은 따로 정합니다.
원자적 교체가 모든 전원 장애와 여러 파일의 일관성까지 증명한다고 생각한다.
이 함수가 보장하는 단일 파일 이름 교체와 내구성·다중 파일 트랜잭션을 구분합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

작업 사본의 새 값에 {"version":3,"status":"complete"}를 사용해 실패/성공 결과를 비교하세요. finally의 임시 파일 삭제를 뺀 사본은 실패 뒤 잔여를 검출하는 검사에서 실패해야 합니다.

막혔을 때 힌트 보기

기존 보고서가 유지되는지와 임시 자원이 남지 않는지는 서로 다른 검사입니다. 정상 성공만 실행하면 정리 결함을 놓칠 수 있습니다.

과제 해설과 예시 답안 보기
  1. atomic_json 호출의 새 값만 바꾸고, 교체 전 실패 뒤 기존 {"version":1}이 유지되는지 확인합니다.
  2. 성공한 뒤 새 보고서는 두 키를 포함하며 sort_keys 때문에 status가 먼저 표시될 수 있습니다. 값으로 파싱해 비교하면 키 표시 순서에 덜 의존합니다.
  3. 임시 파일 unlink를 뺀 사본을 별도 임시 폴더에서 실행하면 실패 때 .pending-*가 남습니다. 검출 결과를 기록하고 복구합니다.

결과를 판단하는 기준

실패 뒤 version=1, 성공 뒤 version=3과 status=complete이며 정상 구현의 잔여는 0개입니다. 교체 보장을 여러 파일·동시 작성자 보장으로 확대하지 않습니다.
