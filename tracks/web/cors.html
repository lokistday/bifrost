01 / UNDERSTAND

먼저 이해하기

Origin은 scheme·host·port의 조합입니다. 같은 호스트라도 http와 https, 서로 다른 유효 포트는 다른 Origin일 수 있습니다. 동일 출처 정책은 주로 브라우저 스크립트가 다른 출처의 자료에 접근하는 범위를 제한하며 서버의 사용자별 인가 정책을 대신하지 않습니다.

CORS는 서버 응답 헤더로 특정 출처의 스크립트가 응답을 읽도록 허용하는 방식입니다. 어떤 요청은 브라우저가 먼저 preflight를 보내지만, 모든 교차 출처 요청이 항상 preflight를 거치는 것은 아닙니다. CORS 오류가 발생했어도 서버에서 요청 처리가 이미 일어났을 수 있습니다.

자격 증명을 포함한 응답을 노출할 때 Access-Control-Allow-Origin에 *를 사용해 모든 Origin을 허용할 수는 없습니다. 이 실습은 브라우저가 직렬화한 Origin 문자열 하나를 정확히 허용하며 Credentials와 Vary: Origin 헤더를 함께 만듭니다. Vary는 캐시가 출처에 따라 다른 응답임을 구분하도록 하는 단서입니다.

출처를 포함 문자열이나 접미 문자열로 비교하면 비슷한 이름의 다른 호스트가 허용될 수 있습니다. learn.example.invalid.attacker.invalid는 learn.example.invalid와 다른 호스트입니다. null Origin도 파일·격리된 문서 등에서 발생할 수 있으므로 이유 없이 신뢰하지 않습니다.

Python 모형은 헤더 생성 결과만 보여 줍니다. 응답을 EXPOSE로 표시해도 로그인·리소스 인가가 성공했다는 뜻은 아닙니다. 실제 CORS 검증에는 HTTPS 환경의 브라우저, preflight 응답, 캐시, 오류 응답, 자격 증명 흐름을 함께 확인해야 합니다.

자주 헷갈리는 지점

CORS는 서버가 받는 모든 교차 출처 요청을 막는 방화벽이라고 생각한다.
CORS는 브라우저의 응답 접근 정책입니다. 요청 전송과 서버 처리 여부를 별도로 확인합니다.
호스트 이름이 포함되면 같은 Origin이라고 판단한다.
scheme·host·port와 정확한 허용 목록을 확인합니다. 유사한 접미 호스트는 다릅니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

http://learn.example.invalid, https://learn.example.invalid:8443, null을 허용 목록 함수에 전달한 결과를 기록하세요. 임의 Origin 반사를 추가하면 어떤 데이터 노출 조건이 생길 수 있는지도 적으세요.

막혔을 때 힌트 보기

다른 Origin에 헤더를 만들지 않는 것과 서버가 요청을 거부하는 것은 같은 의미가 아닙니다. 인증·인가 결과가 있는 API 응답을 기준으로 생각해 보세요.

과제 해설과 예시 답안 보기
  1. 세 출처는 SITE와 정확히 일치하지 않아 모두 빈 헤더 dict여야 합니다. 실제 브라우저는 기본 포트를 정규화해 Origin을 직렬화한다는 점도 구분합니다.
  2. Origin을 그대로 응답에 복사하고 Credentials를 true로 쓰면 공격자 출처에도 인증된 응답을 노출할 조건이 될 수 있다고 설명합니다.
  3. 정상 Origin은 계속 허용하면서 사용자별 자료는 서버 인가가 검사해야 한다고 기록합니다. CORS 실패만으로 CSRF나 직접 HTTP 클라이언트 접근이 차단됐다고 주장하지 않습니다.

결과를 판단하는 기준

세 입력 모두 {}이며 정상 SITE는 세 헤더를 유지합니다. 보고서는 요청 전송·응답 읽기·사용자 인가를 다른 항목으로 설명해야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

1. 개발자 도구에 CORS 오류가 보입니다. 서버의 데이터 변경이 없었다고 결론낼 수 있나요?

정답과 이유 읽기

정답: 아니다. 일부 요청은 전송·처리된 후 응답 읽기만 차단될 수 있다.

브라우저의 응답 노출과 서버 처리는 다른 단계입니다. CSRF 방어와 상태 변경 설계는 별도로 필요합니다.

2. 자격 증명이 있는 응답에서 허용 Origin을 결정할 때 적절한 것은?

정답과 이유 읽기

정답: 검토된 정확한 Origin만 허용하고 서버 인가를 별도로 수행한다.

정확한 허용 목록과 캐시 처리, 인증·인가를 함께 검토해야 합니다. 이 모형은 한 Origin의 헤더 생성만 다룹니다.
