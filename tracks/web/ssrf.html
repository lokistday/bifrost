Python 3.10 이상 · 오프라인 웹 정책 모형

  • Web ZIP을 풀고 web 폴더에서 실행합니다. Linux/WSL/macOS는 python3, Windows PowerShell은 python3 대신 py -3를 사용합니다. 외부 요청·브라우저 서버·계정은 필요하지 않습니다.

01 / UNDERSTAND

먼저 이해하기

SSRF는 사용자에게 영향을 받는 주소로 서버가 요청하도록 만들어, 사용자가 직접 접근할 수 없는 내부 서비스 등에 서버 권한으로 접근하는 문제입니다. 브라우저 CORS는 서버의 HTTP 클라이언트를 제한하지 않으므로 다른 방어가 필요합니다.

URL은 scheme·hostname·port·사용자 정보·경로·쿼리 등의 구성 요소로 파싱해야 합니다. assets.example.invalid@other.invalid의 실제 hostname은 other.invalid입니다. 문자열 시작 부분에 허용 호스트가 보인다고 목적지를 신뢰하면 안 됩니다.

이 모형은 https·정확한 한 호스트·443 포트·허용된 두 경로·사용자 정보 없음·쿼리와 fragment 없음이라는 좁은 URL 구문 계약을 확인합니다. urllib.parse는 URL을 나눌 뿐 안전한 목적지임을 검증하지 않으므로 파싱 후 각 항목을 검사합니다.

구문 허용만으로 실제 연결 목적지가 확정되지는 않습니다. DNS 결과·재바인딩·리다이렉트·프록시·클라우드 메타데이터 등은 추가 신뢰 경계입니다. 운영 환경은 허용된 목적지의 해석과 재검증, 리다이렉트 제한, 네트워크 출구 정책을 함께 적용해야 합니다.

가능하면 사용자가 URL 전체를 주는 기능 대신 서버가 정한 자료 ID를 허용된 목적지에 매핑합니다. 이 실습의 ALLOW_SYNTAX는 첫 단계 통과만 뜻하며 요청을 보내지 않습니다. network_requests=0이고 .invalid 주소는 외부 접속을 위한 것이 아닙니다.

자주 헷갈리는 지점

urlsplit이 성공하면 안전한 URL이라고 믿는다.
파싱은 구성 요소를 나누는 일입니다. 정책·실제 목적지·연결 경계를 별도로 확인합니다.
서버 요청도 브라우저 CORS가 막아 줄 것이라 생각한다.
서버의 HTTP 클라이언트는 브라우저 CORS 정책의 보호 대상이 아닙니다. 서버와 네트워크 출구에서 제어합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
python3 web_controls.py ssrf

변경 전 예상 결과와 해석

한 표본 URL만 구문 허용이고 나머지 세 입력은 거부하며 실제 네트워크 요청은 0입니다.

이제 단계별로 바꾸고 관찰하기

  1. 네 가지 URL 사례 분류하기

    ssrf 모드는 문자열만 파싱합니다. loopback·userinfo·redirect-param이 각각 왜 거부되는지 함수의 다른 조건과 연결합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 web_controls.py ssrf
    관찰할 결과
    allowed=ALLOW_SYNTAX
loopback=DENY
userinfo=DENY
redirect-param=DENY
network_requests=0

  2. @ 앞의 이름과 실제 hostname 구분하기

    이 URL을 실제로 열지 말고 urlsplit의 읽기 결과만 봅니다. username과 hostname을 반대로 판단하지 않도록 출력합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 -c "from urllib.parse import urlsplit; p=urlsplit('https://assets.example.invalid@other.invalid/guide.txt'); print(p.username); print(p.hostname)"
    관찰할 결과
    assets.example.invalid
other.invalid

  3. 구문 통과와 실제 연결 검증 분리하기

    허용 경로 diagram.png는 구문 통과지만 다른 경로나 포트는 거부됩니다. 통과 뒤 DNS·리다이렉트까지 검사했다는 기록을 남기면 잘못된 주장입니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 -c "from web_controls import allowed_fetch; print(allowed_fetch('https://assets.example.invalid/diagram.png')); print(allowed_fetch('https://assets.example.invalid:8443/guide.txt')); print(allowed_fetch('https://assets.example.invalid/private.txt'))"
    관찰할 결과
    True
False
False
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

허용 URL 뒤에 ?next=...를 붙인 사례와 포트 8443 사례를 비교하세요. 자료 ID guide와 diagram을 서버가 정한 두 URL에 매핑하는 사전을 설계하고, 알 수 없는 ID를 거부하는 이유를 설명하세요.

막혔을 때 힌트 보기

리다이렉트 목적지의 검증을 문자열 쿼리 검사만으로 해결했다고 주장하지 마세요. 이 실습은 어떠한 응답도 받지 않습니다.

과제 해설과 예시 답안 보기
  1. 쿼리가 있는 URL은 parsed.query 조건, 8443은 parsed.port 조건에서 거부된다고 표로 연결합니다.
  2. 예시 매핑은 {"guide":"https://assets.example.invalid/guide.txt", "diagram":"https://assets.example.invalid/diagram.png"}입니다. 미등록 ID는 오류로 처리하고 기본 URL로 자동 전환하지 않습니다.
  3. ID 매핑은 입력 공간을 줄이지만 운영 연결의 DNS·리다이렉트·출구 통제·타임아웃·응답 크기 같은 추가 검증은 필요하다고 명시합니다.

결과를 판단하는 기준

두 잘못된 URL은 False입니다. ID 매핑과 미등록 거부를 설명하고, 구문 허용이 실제 안전한 연결을 증명하지 않는다는 한계를 기록합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
