01 / UNDERSTAND

먼저 이해하기

CSRF는 브라우저가 대상 사이트의 쿠키 같은 인증 정보를 자동으로 보내는 특성을 이용해 사용자가 의도하지 않은 상태 변경을 유도하는 문제입니다. 로그인한 사용자라는 사실과 그 사용자가 이 변경을 의도했다는 사실은 다르며, 타인 자료 인가 검사와도 별도의 질문입니다.

동기화 토큰 방식에서는 서버가 세션과 연결한 예측하기 어려운 값을 발급하고 변경 요청에서 확인합니다. 토큰을 단순히 URL에 넣으면 기록·참조 정보로 노출될 수 있어 전달 위치도 설계해야 합니다. 실제 구현에서는 프레임워크의 검증된 기능과 세션별 토큰 정책을 사용합니다.

이 모형은 POST·alice 세션·정확한 Origin·공개 표본 토큰 네 조건을 확인합니다. 고정 토큰은 한 세션의 조건 분리를 보여 주기 위한 값이며 실제 인증·토큰 생성·만료·재사용 방어를 구현하지 않습니다. compare_digest를 사용해도 공개된 고정 토큰을 비밀로 만들지는 못합니다.

상태 변경을 GET으로 열지 않는 설계와 SameSite 쿠키는 방어의 여러 층입니다. SameSite의 site와 Origin의 scheme·host·port는 같은 단위가 아니고, 예외와 브라우저 동작도 고려해야 합니다. 단일 속성이 모든 흐름에서 토큰 검증을 대체한다고 가정하지 않습니다.

Origin 검사도 실제 요청의 신뢰 경계를 이해해야 합니다. 임의 HTTP 클라이언트는 헤더 값을 만들 수 있으므로 인증·인가가 따로 필요합니다. XSS가 같은 출처에서 실행되면 토큰 보호도 약해질 수 있어 출력 방어를 함께 유지해야 합니다.

자주 헷갈리는 지점

로그인 쿠키가 있으면 모든 변경이 사용자의 의도라고 판단한다.
인증된 사용자와 요청의 정당성은 별도입니다. 상태 변경에 적합한 CSRF 방어를 적용합니다.
이 예제의 공개 TOKEN을 서비스에 복사한다.
고정 공개 값은 조건 관찰용입니다. 실제 서비스는 세션별 예측 불가능한 값과 검증된 프레임워크 구현을 사용합니다.

변경 전 예상 결과와 해석

정상 POST 한 사례만 ALLOW이고 토큰 누락·다른 출처·GET 변경은 DENY입니다.

이제 단계별로 바꾸고 관찰하기

  1. 정상 변경과 누락 토큰을 비교하기

    csrf 모드는 유효한 네 조건의 요청을 ALLOW로, 토큰 없는 요청을 DENY로 분리합니다. 파일의 allow_change 조건과 각 튜플 값을 연결해서 읽습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 web_controls.py csrf
    관찰할 결과
    valid=ALLOW
no-token=DENY
foreign=DENY
get-change=DENY

  2. 토큰을 알아도 다른 출처는 거부되는지 확인하기

    같은 표본 세션과 토큰을 유지하고 Origin만 바꿉니다. 이 결과는 모형이 입력 문자열을 비교했다는 뜻이며 실제 브라우저에서 요청이 발생했는지 검증한 결과는 아닙니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 -c "from web_controls import allow_change,TOKEN; print(allow_change('POST','alice',TOKEN,'https://other.example.invalid'))"
    관찰할 결과
    False

  3. 세션·메서드의 경계를 따로 검사하기

    Origin과 토큰이 같아도 세션이 누락되면 거부되는지 확인합니다. 읽기 요청과 상태 변경을 같은 허용 규칙으로 처리하지 않는 이유를 기록합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 -c "from web_controls import allow_change,SITE,TOKEN; print(allow_change('POST',None,TOKEN,SITE)); print(allow_change('GET','alice',TOKEN,SITE))"

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

사본의 cases에 잘못된 토큰·누락 세션·정상 요청을 추가해 각각 결과를 예상하세요. 왜 서버에서 CORS 설정만으로 CSRF 방어를 완성했다고 할 수 없는지도 설명하세요.

막혔을 때 힌트 보기

CORS는 브라우저 코드가 응답을 읽도록 허용하는 정책입니다. 모든 교차 출처 요청의 전송이나 서버 상태 변경을 일괄 차단하는 장치는 아닙니다.

과제 해설과 예시 답안 보기
  1. 정상 네 조건을 기준으로 token만 wrong으로 바꾸면 DENY, session만 None으로 바꾸면 DENY가 나오는지 확인합니다.
  2. 원래 정상 네 조건을 그대로 추가한 사례는 계속 ALLOW여야 합니다. 모든 요청 거부를 보안 수정의 성공으로 취급하지 않습니다.
  3. 보고서에는 이 모형의 고정 토큰·단일 세션 한계와 실제 세션별 발급·만료·프레임워크 검증 필요성을 적고, 인증·인가·CSRF·CORS의 질문을 구분합니다.

결과를 판단하는 기준

추가 세 사례는 DENY, DENY, ALLOW입니다. CORS와 CSRF의 차이, 정상 동작 유지, 모형에서 검증하지 않은 브라우저·세션 동작을 명시합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

INDEPENDENT PRACTICE

도움 없이, 조건을 바꿔 보기

CSRF 토큰은 맞지만 다른 사용자 자원에 쓰는 요청을 가정하세요. 어느 검사가 추가로 필요한가요?

  1. 위 해설을 닫고 예상 결과와 근거를 먼저 적습니다.
  2. 코드·원시 자료·문서 근거로 확인하고 예상과 실제 차이를 설명합니다.
  3. 새 반례 하나를 만들고 무엇까지 확인했는지 기록합니다.
시도한 뒤 판단 기준 읽기

이해한 내용을 점검하기

답을 고른 뒤 이유까지 확인하세요. 점수는 저장하지 않습니다.

1. 브라우저가 로그인 쿠키를 보내는 상태에서 외부 페이지가 변경 요청을 유도했습니다. 쿠키만 확인해도 충분한가요?

정답과 이유 읽기

정답: 아니다. 인증과 별도로 변경 요청의 정당성을 검증해야 한다.

브라우저가 자동으로 붙이는 인증 정보는 사용자 의도와 다릅니다. 경로에 맞는 CSRF·인가 검증과 상태 변경 설계가 필요합니다.

2. 공개된 고정 토큰을 compare_digest로 비교했습니다. 안전한 운영 토큰이 되었나요?

정답과 이유 읽기

정답: 아니다. 비교 방식과 발급값의 비밀성·예측 불가능성은 다르다.

비교 함수는 토큰 발급·세션 결합·노출 방지를 대신하지 않습니다. 여기의 토큰은 공개 교육 표본입니다.
