01 / UNDERSTAND

먼저 이해하기

세션 식별자는 브라우저와 서버의 상태를 연결하는 값입니다. 로그인 전에 쓰던 식별자를 인증 후에도 그대로 쓰면 누군가 미리 알던 식별자가 인증 상태와 연결될 수 있습니다. 로그인처럼 신뢰 수준이 바뀔 때 새 식별자로 갱신하고 이전 식별자를 무효화하는 이유입니다.

rotate_after_verified_login은 인증 검증이 이미 끝났다는 전제에서 old ID를 제거하고 새 ID에 user와 만료값을 저장합니다. 이 함수는 비밀번호를 검사하지 않습니다. S-OLD·S-NEW는 공개 표본이고 실제 세션 ID는 충분히 예측 불가능한 값으로 발급해야 합니다.

로그아웃은 브라우저 쿠키를 지우는 일과 서버가 식별자를 더 이상 인정하지 않는 일을 구분해야 합니다. 쿠키만 없애면 이미 복사된 식별자가 서버에서 계속 유효할 수 있습니다. 이 모형의 logout은 메모리 저장소에서 ID를 제거해 다음 조회를 실패시킵니다.

만료 조건은 now>=expires입니다. 고정 now=90에서 새 수명을 50으로 정했으므로 139는 아직 유효하고 140부터 무효입니다. 실제 설계에서는 절대 수명과 유휴 수명, 시계 정책, 다른 기기의 세션·권한 변경 후 무효화 등을 별도로 정합니다.

이 실습은 한 프로세스의 상태 전이를 관찰합니다. 쿠키 속성·TLS·분산 저장소의 원자성·세션 탈취 방지·CSRF 검증을 구현하지 않습니다. ID 교체와 만료 검증이 있더라도 사용자별 자원 인가와 계정 복구 절차는 그대로 필요합니다.

자주 헷갈리는 지점

브라우저 쿠키만 지우면 서버의 복사된 세션 ID도 자동 무효라고 생각한다.
서버 저장소에서 유효성을 끝내야 합니다. 쿠키 제거와 서버 무효화를 별도로 확인합니다.
새 ID 발급과 비밀번호 검증을 같은 함수의 보장으로 해석한다.
이 모형의 전제는 인증 검증 완료입니다. 실제 신원 검증은 별도의 작업입니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

작업 사본에서 이전 ID를 삭제하는 줄을 빼고, 교체 뒤 old ID가 남는 결함을 어떤 검사로 잡을지 작성하세요. 새 ID 충돌 시 갱신이 거부되는지와 만료 경계 139/140도 확인하세요.

막혔을 때 힌트 보기

old ID의 user가 None일 때는 user_for 결과만으로 삭제 여부를 알 수 없습니다. 서버 저장소의 키 존재 여부도 함께 검사해야 합니다.

과제 해설과 예시 답안 보기
  1. 원본에서는 "S-OLD" not in sessions가 True입니다. old ID 삭제를 뺀 사본에서는 키가 남으므로 이 불변 조건 검사가 실패해야 합니다.
  2. 새 ID를 이미 존재하는 S-OLD로 주면 ValueError이며 기존 상태가 유지되어야 합니다. 새 ID의 충돌을 조용히 덮어쓰지 않습니다.
  3. 인증된 새 세션은 139에 alice, 140에 None이고, 91에 logout한 뒤에는 같은 91에서도 None임을 별도 표본으로 비교합니다.

결과를 판단하는 기준

저장소에서 이전 키 제거·충돌 거부·만료·로그아웃을 각각 검사합니다. 비밀번호 인증이나 실제 쿠키 검증을 완료했다고 주장하지 않습니다.
