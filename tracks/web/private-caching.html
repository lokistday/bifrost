01 / UNDERSTAND

먼저 이해하기

공유 캐시는 여러 사용자의 요청 사이에서 응답을 재사용할 수 있습니다. 개인 프로필이 URL /profile만으로 같은 항목에 저장되면 alice의 본문이 bob에게 전달될 수 있습니다. 원본 서버의 인가가 올바르더라도 캐시 재사용 경계를 잘못 정하면 노출이 생길 수 있습니다.

no-store는 저장을 제한하고 private는 공유 캐시의 저장을 제한하며, no-cache는 저장 자체의 금지가 아니라 재사용 전에 검증이 필요하다는 뜻입니다. 이름이 비슷해도 다른 계약입니다. 실제 표준은 요청/응답·자격 증명·검증자·여러 지시문 상호작용을 더 자세히 다룹니다.

cache_rule은 고정된 다섯 가지 상태를 분류하는 부분 모형입니다. public,max-age=60의 가상 개인 응답은 경로만으로 재사용해 잘못된 정책의 결과를 보여 줍니다. 실제 HTTP 캐시·시간 경과·ETag/304·Vary·Authorization 예외를 구현한 것은 아닙니다.

보호 표본은 새 캐시에서 no-store를 사용해 bob에게 bob 본문을 생성합니다. 응답 정책을 바꾼다고 기존 캐시에 남은 복사본이 자동으로 모두 지워지지는 않습니다. 실제 수정에서는 CDN·프록시·브라우저의 기존 캐시 수명과 무효화 계획도 별도로 확인합니다.

Vary나 쿠키별 키를 추가하면 어떤 요청을 구분할지 바꿀 수 있지만, 민감 응답의 무분별한 공유를 언제나 해결하는 만능 규칙은 아닙니다. 공개 정적 자산과 사용자 전용 응답을 구분하고, 로그인·로그아웃·오류 응답까지 실제 경로에서 검사해야 합니다.

자주 헷갈리는 지점

no-cache는 캐시에 저장할 수 없다는 뜻이라고 생각한다.
저장과 재사용 전 검증은 다릅니다. no-store와 no-cache를 구분합니다.
새 응답에 no-store를 넣었으니 과거 캐시도 모두 삭제됐다고 생각한다.
기존 복사본의 수명·무효화는 별도 작업입니다. 새 캐시 실험의 범위를 명시합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

공개 개인 응답의 두 번째 사용자 기대값을 profile:bob으로 적어 실패를 확인하세요. 새 no-store 표본과 비교하고, 기존 캐시 복사본 처리 및 no-cache의 실제 재검증에 필요한 근거를 기록하세요.

막혔을 때 힌트 보기

캐시를 새로 만드는 실험과 이미 배포된 캐시를 무효화하는 작업은 다릅니다. 이 함수에는 실제 CDN 정리 기능이 없습니다.

과제 해설과 예시 답안 보기
  1. public 표본의 두 번째 실제값은 profile:alice이므로 bob 기대가 실패합니다. 이는 의도적으로 잘못된 캐시 정책의 재현입니다.
  2. 새 dict에서 no-store로 실행하면 bob 본문을 받고 저장된 항목은 0입니다. 이를 이전 캐시 항목이 전 세계에서 삭제됐다고 해석하지 않습니다.
  3. 실제 운영 검증에는 캐시 계층·TTL·키·헤더·기존 복사본 무효화와 ETag/Last-Modified 등 재검증 흐름이 필요하다고 기록합니다.

결과를 판단하는 기준

잘못된 재사용 실패와 새 보호 표본 통과를 비교합니다. no-cache를 저장 금지로 설명하거나 no-store가 과거 복사본을 자동 삭제한다고 쓰면 미완성입니다.
