01 / UNDERSTAND

먼저 이해하기

인증은 누군지 확인하고 인가는 그 사람이 해당 작업을 할 수 있는지 결정합니다. URL의 숫자가 바뀌어도 서버가 리소스 소유자나 역할을 다시 확인해야 합니다. 화면에서 버튼을 숨기는 것은 서버 검사가 아닙니다.

permissions.csv는 두 사용자와 익명 사용자의 기대 결과입니다. demo.py의 can_read는 소유자 비교라는 작은 모델입니다. 실제 서비스는 세션으로 확인한 사용자 ID를 쓰고 권한 정책·관리자 예외·감사 기록까지 설계해야 합니다.

권한 판단에는 요청자, 대상 자료, 작업을 함께 넣어야 합니다. 이 예시의 정책은 소유자만 자신의 노트를 읽는 것입니다. 문서 ID가 순서대로 되어 있는지 추측하기 어려운지와 관계없이 각 요청에서 소유자를 확인해야 합니다.

can_read(user, owner)의 단순 동등 비교는 모델입니다. None과 None처럼 둘 다 누락되어도 같다고 판단하는 한계가 있으므로 서비스 정책으로 사용하려면 유효한 인증 사용자와 실제 자료가 있는지 먼저 확인해야 합니다. 익명이라는 문자열을 한 번 넣어 본 것만으로 모든 익명 상태를 검증한 것은 아닙니다.

권한표는 기대 동작을 구현과 독립적으로 적는 도구입니다. 본인 허용, 타인 거부, 익명 거부뿐 아니라 존재하지 않는 자료와 빠진 인증 정보를 추가하면 기본 거부 정책을 더 명확히 검증할 수 있습니다. 사용자 ID는 요청 본문의 주장보다 서버가 확인한 인증 결과에서 가져옵니다.

자주 헷갈리는 지점

요청에서 온 owner나 user를 검증 없이 믿는다.
서버의 인증 결과와 신뢰하는 자료 소유자 정보를 사용합니다.
본인 자료 허용만 확인하고 권한 검사가 끝났다고 본다.
타인·익명·없는 자료·누락 신원도 별도 테스트로 둡니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

  1. 정책을 코드보다 먼저 읽기

    permissions.csv의 네 행을 allow/deny로 정리합니다. alice-note의 소유자는 alice, bob-note의 소유자는 bob이라는 자료 맵을 별도로 둡니다.

    작게 나눠 확인하기
    alice → alice-note 읽기: 허용
alice → bob-note 읽기: 거부
anonymous → alice-note 읽기: 거부
bob → bob-note 읽기: 허용
    관찰할 결과
    정상 허용 두 건과 거부 두 건입니다.

  2. 본문 모델의 출력 확인하기

    demo.py를 실행해 own=True other=False를 찾습니다. 이어 실제 정책에서 빠진 입력이 무엇인지 검토합니다.

    작게 나눠 확인하기
    python3 demo.py
    관찰할 결과
    다른 실습 출력 사이에 own=True other=False가 나옵니다.

  3. 누락 입력을 명시적으로 거부하기

    아래는 노트 소유자 맵과 인증 사용자 유효성을 포함한 작은 확장 모델입니다. 외부 요청의 user를 신뢰하는 서버 구현으로 해석하지 말고 권한표를 검증하는 함수로 사용합니다.

    작게 나눠 확인하기
    owners = {"alice-note": "alice", "bob-note": "bob"}
def can_read_note(user, resource):
    if user not in {"alice", "bob"}:
        return False
    owner = owners.get(resource)
    return owner is not None and user == owner

print(can_read_note(None, "alice-note"))
print(can_read_note("alice", "missing-note"))
    관찰할 결과
    False
False

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

권한표의 네 행을 각각 테스트로 옮기세요. 요청이 제공한 user 값을 그대로 믿으면 생기는 문제도 적습니다.

막혔을 때 힌트 보기

누가 요청했는지는 신뢰할 수 있는 인증 결과에서 가져와야 합니다. 요청 본문의 owner를 권한 근거로 쓰지 않습니다.

과제 해설과 예시 답안 보기
  1. 권한표 네 행의 actor와 resource를 확장 모델에 넣고 action이 read일 때 기대값과 비교합니다. 자료 ID와 소유자 문자열은 다른 값임을 유지합니다.
  2. 익명은 None과 anonymous 두 형태를 각각 거부하고 없는 자료도 거부하는 사례를 추가합니다.
  3. 신원은 인증 단계에서 확정한 user로 전달한다는 신뢰 경계를 설명합니다. 요청의 owner 값을 소유자 근거로 사용하지 않습니다.

결과를 판단하는 기준

네 행은 True, False, False, True 순서입니다. 추가한 익명·누락 자료 사례는 False여야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

이해한 내용을 점검하기

답을 고른 뒤 이유까지 확인하세요. 점수는 저장하지 않습니다.

1. 브라우저에서 Bob의 노트 버튼을 숨겼습니다. 서버 인가가 없어도 될까요?

정답과 이유 읽기

정답: 아니다. 직접 만든 요청도 서버가 대상 권한을 검사해야 한다.

화면 조작은 권한 경계가 아닙니다. 요청자는 UI와 별도로 HTTP 요청을 만들 수 있으므로 서버에서 확인해야 합니다.

2. 단순 함수 return user == owner에서 user와 owner가 모두 None이면 True입니다. 가장 알맞은 개선은?

정답과 이유 읽기

정답: 없는 사용자와 없는 자료를 먼저 명시적으로 거부한다.

동등 비교 전에 인증 주체와 대상 자료의 유효성을 확인해야 합니다. 누락값끼리 같다는 사실은 접근 허용 근거가 아닙니다.
