01 / UNDERSTAND

먼저 이해하기

클라이언트의 JSON을 그대로 사용자 객체에 병합하면 화면에 없는 role·owner·금액 같은 필드도 바뀔 수 있습니다. 이를 Mass Assignment 문제로 부릅니다. 화면에서 입력 칸을 숨기는 것은 서버가 받을 필드를 제한하지 않으므로 서버 경계에 명시적인 수정 계약이 필요합니다.

이 모형은 display_name과 theme만 수정하도록 허용합니다. role과 owner는 서버 관리 필드이고, 알 수 없는 필드나 빈 객체는 거부합니다. 관리자 요청과 일반 사용자 요청이 다르다면 각각의 허용 필드 계약과 인가를 따로 설계합니다.

허용한 키의 값도 검증해야 합니다. display_name은 공백만 아닌 문자열 1~40자, theme는 dark 또는 light입니다. 파일명·HTML 출력·SQL 같은 다른 사용 문맥에는 추가 처리가 필요하며, 이 일반 필드 검사가 모든 XSS나 데이터베이스 문제를 해결하지는 않습니다.

update_profile은 actor가 owner인지 확인하고, 입력 검증을 마친 뒤 새 dict에 허용된 변경을 넣습니다. 원본은 바꾸지 않아 거부된 요청이 일부 필드만 수정한 상태를 남기지 않습니다. 이번 자료는 문자열 값뿐이라 바깥 dict 복사로 충분하며 중첩 객체가 추가되면 복사 계약도 다시 검토합니다.

불필요한 필드를 조용히 무시할지 요청 전체를 거부할지는 API 계약의 선택입니다. 이 모형은 오류를 드러내기 위해 전체 거부를 택했습니다. 필드 허용·사용자 인가·동시 갱신 충돌·감사 기록은 서로 다른 검증이며 실제 서버·저장을 구현한 예제는 아닙니다.

자주 헷갈리는 지점

화면에 role 입력 칸이 없으므로 서버에서도 바뀔 수 없다고 생각한다.
클라이언트 요청은 직접 만들 수 있습니다. 서버에서 필드 허용 목록과 인가를 적용합니다.
필드 이름만 허용하면 값의 자료형·길이도 검증됐다고 생각한다.
허용 키와 값 계약은 별도입니다. 다른 출력·저장 문맥의 안전 처리도 유지합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

정상 display_name과 role=admin을 같은 요청에 넣어 전체 요청이 거부되는지 확인하세요. 40자·41자 이름과 공백만 있는 이름도 비교하고, 거부 뒤 원본 상태를 검사하세요.

막혔을 때 힌트 보기

부분 성공을 기대하지 않는 계약입니다. 정상 키 하나가 포함되어도 알 수 없는 키가 있으면 변경 전체가 실패합니다.

과제 해설과 예시 답안 보기
  1. 사본의 payload를 {"display_name":"Freya","role":"admin"}으로 만들면 ValueError이고 원본 display_name=Loki·role=learner가 유지되어야 합니다.
  2. A 40개는 허용, 41개는 거부입니다. 공백만 있는 값도 거부합니다. 값 길이와 내용 검증을 별도 사례로 남깁니다.
  3. actor=bob은 허용 필드만 보내도 PermissionError입니다. 키 계약과 리소스 인가를 별도 검사로 기록합니다.

결과를 판단하는 기준

혼합 요청은 전체 거부·원본 유지, 이름 경계는 40 허용/41 거부, 타인 요청은 인가 거부입니다. 요청 전체 병합을 수정 과제로 넣지 않습니다.
