01 / UNDERSTAND

먼저 이해하기

HTTP 요청은 각자 처리되므로 서버는 이전 요청과의 관계를 별도로 관리해야 합니다. 쿠키는 브라우저의 전달 수단이고 서버 측 세션은 식별자에 연결된 상태입니다. 모든 쿠키가 세션 쿠키인 것은 아닙니다.

Set-Cookie는 서버가 저장을 요청하는 응답 헤더, Cookie는 브라우저가 조건에 맞게 보내는 요청 헤더입니다. HttpOnly는 스크립트 접근을 제한하고 Secure는 HTTPS 전달을 제한하며 SameSite는 교차 사이트 전송에 영향을 줍니다. 이 옵션들은 서버의 권한 검사를 대신하지 않습니다.

세션 식별자는 비밀번호 자체가 아니라 로그인 상태를 조회하는 열쇠처럼 동작할 수 있습니다. 그래서 예측하기 어렵게 생성하고 로그인 등 신뢰 수준이 바뀔 때 갱신하며 만료·폐기 정책을 서버에서 적용해야 합니다. 브라우저가 user=alice라고 보냈다는 이유만으로 Alice로 인정하지 않습니다.

로그아웃은 현재 식별자에 연결된 서버 상태를 무효화하는 일과 브라우저의 쿠키를 만료시키는 일을 함께 고려합니다. 브라우저에서만 지우면 복사된 식별자가 서버에서 계속 통할 수 있습니다. 만료된 식별자로 요청하면 보호된 자료를 주지 않고 다시 인증하도록 처리하는 정책을 정합니다.

HttpOnly는 JavaScript의 쿠키 읽기를 줄이지만 XSS가 있는 페이지에서 사용자를 대신한 요청까지 막지는 못합니다. SameSite만으로 모든 CSRF 상황이 해결되는 것도 아닙니다. 쿠키 옵션, 서버 측 요청 검증, 출력 보안과 리소스 권한 검사는 서로 다른 경계를 다룹니다.

자주 헷갈리는 지점

쿠키가 있다는 사실만으로 유효 로그인이라고 판단한다.
서버가 식별자의 유효성·만료·폐기 상태를 확인해야 합니다.
예시의 localhost 쿠키 옵션을 운영 HTTPS 설정으로 그대로 사용한다.
자료는 형식 관찰용입니다. 운영 HTTPS에서는 Secure 등 쿠키 범위·수명 정책을 함께 설계합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

관찰 절차·자료 예시 · 그대로 셸에 붙여 넣지 말고 본문 안내를 따라 확인
requests.txt에서 Set-Cookie 응답과 다음 Cookie 요청을 찾습니다.
로그인 → 세션 생성 → 쿠키 전달 → 세션 조회 → 권한 검사 순서도를 작성합니다.

변경 전 예상 결과와 해석

서버의 상태와 브라우저의 식별자 저장을 나눈 순서도가 완성됩니다. DEMO_ONLY는 실제 세션이 아닙니다.

이제 단계별로 바꾸고 관찰하기

  1. 요청과 응답의 헤더 구분하기

    requests.txt 첫 요청에는 이미 Cookie가 있고 응답에는 Set-Cookie가 있습니다. 이 자료는 로그인 전체 캡처가 아니라 기존 세션 요청과 쿠키 설정 형식을 보여 주는 예시입니다.

    관찰 절차·자료 예시 · 그대로 셸에 붙여 넣지 말고 본문 안내를 따라 확인
    요청: Cookie: session=DEMO_ONLY
응답: Set-Cookie: session=DEMO_ONLY; HttpOnly; SameSite=Lax
    관찰할 결과
    브라우저가 보내는 값과 서버가 설정을 요청하는 값을 구분합니다.

  2. 생성을 포함한 전체 흐름 그리기

    순서도에는 자격 증명 확인 → 새 세션 식별자와 서버 상태 생성 → Set-Cookie 응답 → 다음 Cookie 요청 → 서버 세션 조회 → 인가 판단을 적습니다. 자료에서 직접 관찰한 단계와 설명을 위해 추가한 단계를 구분합니다.

  3. 폐기 이후의 요청 생각하기

    유효한 세션으로 자료를 읽은 경우와 로그아웃 후 이전 식별자로 다시 요청한 경우를 비교합니다. 서버가 옛 식별자를 인정하면 로그아웃 정책이 완성되지 않은 것입니다.

    관찰 절차·자료 예시 · 그대로 셸에 붙여 넣지 말고 본문 안내를 따라 확인
    유효 식별자 → 세션 조회 성공 → 해당 자료 권한 검사
폐기·만료 식별자 → 세션 조회 거부 → 보호된 자료 미제공
    관찰할 결과
    자료 접근은 세션의 유효성과 리소스 권한을 모두 통과해야 합니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

로그아웃, 세션 만료, 탈취된 식별자 세 상황에서 서버가 무엇을 해야 하는지 적으세요.

막혔을 때 힌트 보기

브라우저 쿠키를 지우는 것과 서버 세션을 무효화하는 것을 따로 생각하세요.

과제 해설과 예시 답안 보기
  1. 로그아웃: 서버의 세션을 무효화하고 브라우저 쿠키를 만료시킵니다. 이미 복사된 옛 식별자로 다시 요청하는 경우도 거부되어야 합니다.
  2. 만료: 서버가 만료 시점을 확인하고 새 인증을 요구합니다. 쿠키가 브라우저에 남아 있다는 것만으로 유효하다고 판단하지 않습니다.
  3. 탈취 의심: 해당 세션 또는 정책상 관련 세션을 폐기하고 재인증·기록 확인 절차를 정합니다. 토큰 값을 학습 노트에 보관하지 않습니다.

결과를 판단하는 기준

서버 상태와 브라우저 저장소가 나뉜 순서도, 세 상황의 서버 처리, 이전 식별자 재사용 거부라는 검증 기준이 있어야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

INDEPENDENT PRACTICE

도움 없이, 조건을 바꿔 보기

로그아웃 후 브라우저 쿠키만 지운 경우와 서버 세션도 무효화한 경우를 상태표로 비교하세요.

  1. 위 해설을 닫고 예상 결과와 근거를 먼저 적습니다.
  2. 코드·원시 자료·문서 근거로 확인하고 예상과 실제 차이를 설명합니다.
  3. 새 반례 하나를 만들고 무엇까지 확인했는지 기록합니다.

이해한 내용을 점검하기

답을 고른 뒤 이유까지 확인하세요. 점수는 저장하지 않습니다.

1. 로그아웃 구현이 브라우저 쿠키만 지웠습니다. 서버 세션이 유효한 채 남았다면 어떤 문제가 있나요?

정답과 이유 읽기

정답: 복사된 식별자가 다시 사용될 수 있다.

클라이언트 저장값 제거와 서버 권한 폐기는 별도입니다. 서버가 옛 식별자를 인정하면 복사본을 통한 사용이 남습니다.

2. HttpOnly 쿠키를 쓰면 리소스 소유자 확인을 생략해도 될까요?

정답과 이유 읽기

정답: 아니다. HttpOnly는 스크립트의 쿠키 접근을 제한하며 인가는 별도이다.

쿠키 전달·노출 보호와 특정 자료 접근 허용은 다른 판단입니다. 서버는 매 요청의 대상과 작업 권한을 확인해야 합니다.
