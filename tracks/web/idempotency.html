01 / UNDERSTAND

먼저 이해하기

정상 기능도 요청 순서와 재시도에서 보안 문제가 생길 수 있습니다. 재고가 음수가 되지 않음, 주문 하나와 재고 차감이 함께 남음, 같은 요청 키의 같은 내용은 한 번만 효과를 냄 같은 불변 조건을 먼저 정하면 경계가 명확해집니다.

Checkout은 제품 kit 하나의 재고 3을 관리하는 메모리 SQLite 모형입니다. UPDATE에 stock>=quantity 조건을 넣고 실제 변경 행 수를 확인합니다. 먼저 재고를 읽고 나중에 무조건 차감하는 두 단계와 달리 조건을 변경 문장에 결합합니다.

재고 차감과 주문 INSERT는 BEGIN IMMEDIATE와 COMMIT 사이에 있습니다. 둘 사이에서 예외가 나면 ROLLBACK하고 같은 예외를 다시 올립니다. 예외를 넓게 잡는 이유는 정리이며, 실패를 삼키고 성공을 반환하는 동작과 다릅니다.

주문 키는 user와 request_key의 조합이고 같은 키의 quantity가 같으면 REPLAY, 다르면 CONFLICT입니다. 동일 효과를 반복하지 않는 멱등성은 인증·인가와 다르며 요청 키 자체도 비밀 인증 정보가 아닙니다. 제품·주소·가격이 늘어나면 어떤 요청 내용을 비교할지 계약을 넓혀야 합니다.

이 표본은 단일 연결·고정 제품·순차 호출입니다. 실제 결제·다중 서비스의 정확히 한 번 효과·여러 서버 동시성·재시도 보관 기간을 증명하지 않습니다. SQLite의 실제 트랜잭션과 제약은 사용하지만 운영 규모의 동시 부하 검증은 별도입니다.

자주 헷갈리는 지점

같은 요청 키면 수량이 바뀌어도 이전 성공을 그대로 적용한다.
동일 키의 요청 내용이 같은지 비교합니다. 바뀐 요청은 충돌로 처리하는 계약을 정합니다.
except에서 롤백했으니 예외를 숨기고 성공을 반환해도 된다고 생각한다.
정리 후 원래 실패를 다시 전달합니다. 원자적 복구와 성공 보고는 다른 문제입니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

원본 재고 3에서 같은 alice/REQ-1/2 요청을 세 번 실행해 재고와 주문 수를 확인하세요. 사본에서 예외 경로 ROLLBACK을 제거하면 중간 실패 뒤 불변 조건 검사가 실패하는지 확인한 뒤 복구하세요.

막혔을 때 힌트 보기

거부와 실패에서도 재고·주문을 함께 확인합니다. REPLAY 출력만으로 중복 효과가 없다고 단정하지 마세요.

과제 해설과 예시 답안 보기
  1. 같은 요청 세 번의 결과는 RESERVED, REPLAY, REPLAY이고 재고 1·주문 1행입니다. 기대값을 함수의 결과로 재계산하지 않고 고정해 비교합니다.
  2. 별도 작업 사본의 롤백을 제거하고 fail_after_update=True를 실행하면 차감이 열린 트랜잭션에 남아 같은 연결에서 재고가 달라질 수 있습니다. 기존 상태 3·주문 0 불변 조건이 실패해야 합니다.
  3. 원본 롤백을 복구한 뒤 실패 보고와 stock=3·orders=0을 함께 확인합니다. 운영 동시성·외부 결제·다른 요청 필드 비교는 미검증이라고 기록합니다.

결과를 판단하는 기준

세 번의 재시도는 주문 1행과 재고 1을 유지합니다. 중간 실패는 예외를 보고하고 재고 3·주문 0을 유지해야 합니다. 롤백 없는 사본은 실습용으로만 사용하고 복구합니다.
