01 / UNDERSTAND

먼저 이해하기

비밀번호 재설정 링크는 일반 로그인과 다른 제한된 권한을 전달합니다. 링크를 아는 것만으로 특정 작업을 할 수 있다면 토큰 노출은 그 권한의 노출입니다. 토큰은 충분한 엔트로피로 발급하고, 보관·전달·사용 횟수·만료를 함께 설계해야 합니다.

fixture_ticket은 공개 표본 토큰의 SHA-256과 alice·reset-password·expires=100을 저장합니다. 해시는 저장소에서 원문을 직접 보관하지 않는 방법의 한 부분이며, 예측 가능한 짧은 토큰을 강하게 만들지는 않습니다. 운영 발급에는 보안 목적 난수와 적절한 길이가 필요합니다.

consume_ticket은 used·만료·사용자·목적을 먼저 확인하고 토큰의 해시를 비교한 뒤 used=True로 바꿉니다. 잘못된 사용자나 목적의 시도는 표본을 소비하지 않습니다. 계정 변경·이메일 변경 같은 다른 작업에 같은 권한을 재사용하지 않도록 목적을 결합합니다.

한 번 사용은 동시 요청에서도 하나만 성공해야 의미가 있습니다. 이 Python 메모리 모형의 확인 후 변경은 분산·동시 실행의 원자성을 보장하지 않습니다. 실제 저장소에서는 조건부 갱신·트랜잭션과 비밀번호 변경을 함께 일관되게 처리해야 합니다.

이 실습은 이메일 발송·계정 존재 여부 응답·실제 비밀번호 변경을 하지 않습니다. 실제 복구 흐름은 균일한 사용자 응답, 시도 제한, 신뢰할 전달 경로, 토큰 로그 노출 방지, 복구 후 세션 처리도 검토해야 합니다. 표본 토큰을 운영에 복사하지 않습니다.

자주 헷갈리는 지점

토큰을 해시하면 짧고 예측 가능한 원문도 안전해진다고 생각한다.
해시는 엔트로피를 늘리지 않습니다. 보안 목적 난수로 발급하고 길이·사용 범위를 정합니다.
used 불리언 한 개만 있으면 여러 서버에서 한 번 사용이 보장된다고 생각한다.
확인과 상태 변경의 원자성이 필요합니다. 메모리의 순차 실험과 저장소 동시 처리를 구분합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

사본에서 used 검사를 빼면 같은 토큰 두 번 사용 검사가 실패하는지 확인하세요. expires=120의 새 표본에서 119와 120을 따로 검사하고, 해시 저장만으로 동시 한 번 사용이 보장되지 않는 이유를 설명하세요.

막혔을 때 힌트 보기

시간 경계 테스트는 각각 새 표본을 사용합니다. 재사용 검사와 만료 검사는 원인을 분리해야 합니다.

과제 해설과 예시 답안 보기
  1. 원본의 첫 사용 True 뒤 같은 ticket의 두 번째는 False입니다. used 검사만 뺀 사본은 두 번째가 True가 되어 재사용 거부 기대가 실패해야 합니다.
  2. expires=120인 독립 표본에서 now=119는 허용, 120은 거부됩니다. 잘못된 사용자·목적은 used를 False로 유지해야 합니다.
  3. 해시 비교는 토큰 일치 여부이고, 확인과 사용 표시 사이 동시성을 해결하려면 실제 저장소의 원자적 상태 변경이 필요하다고 적습니다.

결과를 판단하는 기준

재사용 결함 검출·119/120 경계·실패 뒤 미소비를 확인합니다. 실제 계정 복구 시스템이나 동시성 검증을 구현한 결과로 쓰지 않습니다.
