01 / UNDERSTAND

먼저 이해하기

XSS는 신뢰하지 않은 데이터가 브라우저의 실행 가능한 문맥에 들어가는 문제입니다. HTML 본문, 속성, URL, JavaScript 문자열은 해석 규칙이 다릅니다. 한 가지 이스케이프 함수를 모든 위치에 붙인다고 해결되지 않습니다.

일반 텍스트는 textContent처럼 코드 해석을 하지 않는 API로 넣습니다. Python html.escape는 HTML 텍스트 예제에서 <, > 등을 엔티티로 바꿉니다. 이것을 JavaScript 문자열이나 URL 검증까지 해결하는 도구로 오해하지 마세요.

출력 컨텍스트는 데이터가 들어갈 자리입니다. HTML 본문에 글자를 보여 주는 일과 href의 URL을 설정하는 일은 다른 규칙을 필요로 합니다. textContent는 일반 텍스트를 넣는 목적에 잘 맞지만 URL의 허용 스킴을 정하는 도구는 아닙니다.

html.escape의 결과 &lt;b&gt;hello&lt;/b&gt;는 HTML 본문에서 태그 기호가 문자로 해석되도록 표현한 문자열입니다. Python 콘솔에 엔티티가 보이는 것과 브라우저 DOM에서 b 요소가 생성되는 것은 구분해야 합니다. 입력→저장→출력 경계 중 어느 단계에서 인코딩했는지 정해 중복 변환을 피합니다.

서식 있는 HTML을 꼭 허용해야 한다면 단순히 innerHTML을 유지하며 몇 글자만 지우는 방법으로 끝내지 않습니다. 허용할 태그와 속성을 정하고 유지보수되는 정화 도구를 사용하며, URL·이벤트 속성 등 별도 위험 문맥을 검토합니다. 이 차시는 일반 텍스트 표시만 요구하므로 textContent로 단순화할 수 있습니다.

자주 헷갈리는 지점

이미 인코딩된 값을 매번 다시 인코딩한다.
어느 출력 경계에서 변환하는지 정하고 원본 데이터와 표시용 표현을 구분합니다.
HttpOnly나 HTTPS가 있으면 DOM 출력은 검토하지 않는다.
쿠키 노출·전송 보호와 브라우저의 코드 해석은 다른 문제이므로 출력 API와 문맥을 확인합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

browser.html의 오른쪽 대입도 textContent로 바꾸고 두 줄이 같아지는지 확인하세요. 사용자 입력을 URL에 넣는 사례에는 별도 스킴 허용 정책이 필요한 이유를 적습니다.

막혔을 때 힌트 보기

한 번 인코딩된 값을 반복 인코딩하면 &amp;lt;처럼 보일 수 있습니다. 데이터 흐름에서 출력 경계를 한 곳으로 정하세요.

과제 해설과 예시 답안 보기
  1. #text와 #markup의 대입문을 모두 textContent로 맞춘 뒤 Elements에서 자식이 텍스트인지 확인합니다.
  2. API를 바꾸기 전에는 한쪽에 b 요소가 있었고 바꾼 뒤에는 태그 문자가 그대로 보인다고 기록합니다.
  3. URL 사례에는 https 같은 허용 스킴 정책과 주소 파싱을 별도로 표시합니다. html.escape가 URL 허용 여부까지 판단하지 않는다고 설명합니다.

두 p의 textContent는 같은 문자열이고 DOM에 sample에서 생긴 b 요소가 없어야 합니다. HTML 텍스트·URL·스크립트 문맥의 차이도 서술해야 합니다.

1. 일반 사용자 닉네임을 글자로 표시하는 데 가장 직접적인 API는?

정답과 이유 읽기

정답: textContent로 텍스트를 넣는다.

닉네임에 HTML 해석이 필요 없으므로 텍스트 API가 목적에 맞습니다. 입력의 태그 모양을 코드로 해석할 이유가 없습니다.

2. href에 들어갈 주소를 html.escape로 처리했습니다. 이것만으로 안전한 URL인가요?

정답과 이유 읽기

정답: 아니다. 주소의 스킴과 허용 정책을 별도로 검사해야 한다.

HTML 표현과 URL 의미 검증은 다른 경계입니다. 인코딩은 위험한 주소 스킴 자체를 허용·거부하는 정책이 아닙니다.
