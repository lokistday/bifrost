01 / UNDERSTAND

먼저 이해하기

사용자 입력을 저장소 경로에 바로 붙이면 ../ 같은 구문으로 허용 폴더 밖을 가리킬 수 있습니다. 절대 경로·다른 구분자·URL 디코딩 순서도 영향을 주므로 금지 문자열 몇 개를 지우는 방식은 규칙을 설명하고 검증하기 어렵습니다.

이 모형은 앱이 관리하는 폴더에서 단일 txt 파일 이름만 허용합니다. ASCII 영문·숫자·밑줄·하이픈과 .txt 확장자라는 좁은 계약을 먼저 확인한 뒤 resolve한 경로가 기준 폴더 안인지 확인합니다. 중첩 경로가 필요하지 않은 기능에서는 아예 경로 구문을 받지 않는 것이 단순합니다.

이름 검사에서 ALLOW_NAME이 나와도 파일 내용·존재·소유자·권한은 확인한 것이 아닙니다. 확장자나 브라우저가 보낸 Content-Type만으로 업로드 내용이 안전하다고 판단할 수 없습니다. 크기 제한, 실제 내용 검사, 저장 위치, 실행 방지, 사용자별 인가는 다른 검증입니다.

resolve는 존재하는 심볼릭 링크도 따라갈 수 있어 폴더 밖 링크를 찾는 데 도움이 됩니다. 그러나 검사 후 열기 사이에 링크가 바뀌면 경합 문제가 남습니다. 실제 시스템은 공격자가 저장 경로를 교체할 수 없게 하거나 운영체제의 안전한 파일 열기 방식을 사용해야 합니다.

파일 이름을 사용자에게서 직접 받는 대신 서버가 발급한 자료 ID를 소유자 확인 뒤 내부 경로로 매핑할 수도 있습니다. 이 실습은 파일을 열거나 저장하지 않으며, 이름 검사와 경로 포함 관계라는 일부 단계를 관찰합니다. 모든 파일 업로드 방어를 구현한 예제가 아닙니다.

자주 헷갈리는 지점

../만 삭제하면 모든 경로 이탈이 해결된다고 생각한다.
구분자·절대 경로·디코딩·링크를 고려해야 합니다. 필요 없는 경로 구문은 애초에 받지 않는 좁은 계약을 씁니다.
폴더 안의 txt면 누구에게나 읽혀도 된다고 생각한다.
위치·확장자 검사는 사용자별 인가를 대신하지 않습니다. 내용·소유자·동작도 검사해야 합니다.

02 / WORKED EXAMPLE

따라 하며 관찰하기

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
python3 web_controls.py files

변경 전 예상 결과와 해석

허용한 단일 txt 이름만 ALLOW_NAME이고 경로·다른 확장자·인코딩 구문은 DENY입니다.

이제 단계별로 바꾸고 관찰하기

  1. 정상 이름과 경로 구문 비교하기

    files 모드는 실제 파일을 읽지 않고 이름과 해석 경로만 검사합니다. URL 인코딩처럼 보이는 %2e도 이 계약에서는 허용 문자가 아닙니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 web_controls.py files
    관찰할 결과
    note.txt=ALLOW_NAME
../private.txt=DENY
nested/note.txt=DENY
note.txt.exe=DENY
%2e%2e.txt=DENY

  2. 허용 이름의 결과가 의미하는 범위 확인하기

    choose_file의 반환 경로에서 이름만 출력합니다. missing-note.txt가 실제로 없어도 경로 검사 자체는 통과하므로 ALLOW_NAME을 파일 읽기 성공과 혼동하지 않습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 -c "from pathlib import Path; from web_controls import choose_file; print(choose_file(Path.cwd(),'missing-note.txt').name)"
    관찰할 결과
    missing-note.txt

  3. 앱 경계와 사용자 경계를 분리하기

    코드에서 정규식과 is_relative_to 검사를 각각 찾습니다. 그 앞에 사용자별 인가가 없다는 점을 확인하고, 같은 폴더의 다른 사람 파일은 어떤 별도 검사가 필요한지 정리합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 -c "from pathlib import Path; from web_controls import choose_file; print(choose_file(Path.cwd(),'alice-note.txt').name)"
    관찰할 결과
    alice-note.txt. 이 출력은 alice의 접근 권한 검증 결과가 아닙니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

note_1.txt, note..txt, /tmp/note.txt, note.TXT를 모형에 넣어 결과를 기록하세요. 이 계약에서 허용한 이름 하나가 있어도 다른 사용자의 자료를 열면 안 되는 이유를 설명하세요.

막혔을 때 힌트 보기

정규식은 대소문자를 구분합니다. 허용 이름·폴더 포함·파일 내용·사용자 인가를 네 칸으로 나누면 어느 검사를 했는지 선명해집니다.

과제 해설과 예시 답안 보기
  1. note_1.txt는 허용이고 나머지 세 이름은 거부됩니다. note.TXT를 허용하고 싶다면 요구 사항을 바꾸고 테스트를 더해야 하며 우연히 허용될 것으로 가정하지 않습니다.
  2. ALLOW_NAME은 파일 존재와 내용·안전성을 검증하지 않는다고 기록합니다. 경로 안이라는 사실은 그 사용자 소유라는 사실과 다릅니다.
  3. 사용자에게 자료 ID만 받고 서버가 소유자·동작을 검사한 뒤 내부 파일 경로를 선택하는 대안과, 경로를 동시에 바꾸는 공격자가 있는 환경의 경합 한계를 적습니다.

결과를 판단하는 기준

note_1.txt만 허용됩니다. 결과 표와 네 검증 범위 구분, 사용자별 인가와 경합 한계 설명이 있어야 완료입니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

INDEPENDENT PRACTICE

도움 없이, 조건을 바꿔 보기

정상 하위 파일, ../상위 경로, 절대 경로를 분류하세요. 심볼릭 링크가 있으면 단순 문자열 검사만으로 충분한지도 적으세요.

  1. 위 해설을 닫고 예상 결과와 근거를 먼저 적습니다.
  2. 코드·원시 자료·문서 근거로 확인하고 예상과 실제 차이를 설명합니다.
  3. 새 반례 하나를 만들고 무엇까지 확인했는지 기록합니다.
