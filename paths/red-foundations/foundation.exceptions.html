01 / UNDERSTAND

먼저 이해하기

예외는 실행 중 프로그램이 정상적으로 진행할 수 없는 조건을 나타냅니다. 숫자 형식이나 범위가 잘못된 입력은 사용자가 고칠 수 있는 예상 오류이고, 오타로 생긴 NameError는 개발 결함일 수 있습니다. 모두 같은 메시지로 덮으면 무엇을 고쳐야 하는지 사라집니다.

parse_minutes는 잘못된 값에 ValueError를 발생시키고 호출자가 처리 방법을 정합니다. 계산 함수가 곧바로 프로그램을 종료하지 않아야 테스트·다른 스크립트에서도 재사용할 수 있습니다. CLI 경계에서는 예외를 설명하고 0이 아닌 종료 상태로 반환합니다.

try는 실패할 수 있는 최소 범위를 감싸고 except는 예상한 예외 종류를 지정합니다. bare except나 except Exception으로 모든 오류를 삼킨 뒤 PASS를 출력하면 실제 결함까지 입력 오류로 위장될 수 있습니다. 원인이 다른 오류를 구분해 재현합니다.

stdout은 정상 결과를, stderr는 진단을 전달하는 관례가 있습니다. 이 도구의 정상 실행은 종료 상태 0, 잘못된 문서는 2입니다. 출력 문자열만 보는 대신 상태도 확인해야 뒤의 자동화가 실패한 계산을 성공 데이터로 소비하지 않습니다.

오류 메시지는 필드와 허용 조건을 알려 주되 비밀번호·토큰·불필요한 개인 정보를 포함하지 않아야 합니다. 이번 자료는 허구의 작은 입력이고, 오류에 파일 경로나 라이브러리 메시지가 포함될 수 있습니다. 운영 서비스용 예외 응답 정책을 그대로 제공하는 예제는 아닙니다.

자주 헷갈리는 지점

예외를 잡았으면 어떤 입력이든 성공으로 처리한다.
예외 처리는 실패를 이해 가능한 방식으로 전달하는 일도 포함합니다. 상태와 결과를 구분합니다.
모든 코드를 try/except로 감싸고 빈 문자열을 반환한다.
예상 오류만 좁은 범위에서 처리합니다. 숨겨진 개발 결함이 정상 결과로 이어지지 않게 합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

record-invalid.json 실행의 종료 상태·stdout·stderr를 표로 기록하세요. parse_minutes(1440)과 parse_minutes(1441)도 호출하고, 실패 입력을 0으로 대체했을 때 잃어버리는 의미를 설명하세요.

막혔을 때 힌트 보기

0은 정상 입력일 수 있습니다. 오류와 0을 같은 반환값으로 만들면 "공부하지 않음"과 "자료가 잘못됨"을 구분할 수 없습니다.

과제 해설과 예시 답안 보기
  1. 정상 문서의 상태 0과 잘못된 문서의 상태 2를 같은 subprocess 호출로 비교합니다. 오류 실행의 stdout이 비어 있는지도 확인합니다.
  2. 1440은 반환되지만 1441은 ValueError입니다. except에서 0을 만들어 반환하는 대신 오류를 호출자에게 알려야 원래 입력 상태를 구분할 수 있습니다.
  3. 기록에는 입력, 허용 조건, 예외 종류, 종료 상태, 진단 스트림을 적습니다. errors 모드의 의도된 관찰과 json 모드의 작업 실패가 다른 점도 설명합니다.

결과를 판단하는 기준

errors 모드의 정상 종료와 잘못된 JSON 작업의 상태 2를 구분합니다. 1440은 허용, 1441은 ValueError이며 이를 정상 0으로 보고하지 않습니다.

1. 오류를 잡은 뒤 minutes=0을 출력하고 상태 0으로 종료했습니다. 가장 큰 문제는?
