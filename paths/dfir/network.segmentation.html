01 / UNDERSTAND

먼저 이해하기

Web이 인터넷 요청을 받더라도 DB를 인터넷에 직접 공개할 필요는 없습니다. Web→DB의 특정 서비스만 허용하고 관리 경로를 별도 구간·신원 검사로 분리하면 한 지점의 침해가 전 구간으로 퍼지는 범위를 줄일 수 있습니다.

VLAN이나 서브넷을 나눴다고 접근 통제가 자동 적용되지는 않습니다. 실제 라우팅과 필터 정책을 확인해야 합니다. 백업, 모니터링, DNS, 시간 동기화, 배포 경로도 필요한 흐름이므로 모두 차단하는 정책은 운영을 망가뜨릴 수 있습니다.

신뢰 경계는 서로 다른 권한이나 위험을 가진 구간 사이의 접점입니다. 인터넷 요청을 처리하는 Web과 데이터가 있는 DB를 나누면 Web 침해 뒤 접근할 수 있는 범위를 줄일 수 있습니다. 구간 이름보다 실제 흐름과 허용 근거가 중요합니다.

관리 접속은 일반 사용자 경로와 필요한 권한이 다릅니다. 관리 출발지 제한뿐 아니라 관리자 인증, 장치 상태, 짧은 자격 증명, 작업 기록을 검토합니다. DB가 비공개라고 해서 Web의 과도한 DB 권한이 자동 해결되지는 않습니다.

기본 거부를 설계할 때는 필수 운영 트래픽도 목록화합니다. DNS·시간 동기화·백업·모니터링·배포가 멈추면 장애나 관측 공백이 생길 수 있습니다. 필요한 흐름을 좁게 허용하고 차단 변경의 영향과 복구 경로를 미리 적습니다.

자주 헷갈리는 지점

VLAN 분리만으로 모든 횡적 이동이 차단됐다고 한다.
구간 사이 라우팅·필터·주체 권한을 실제로 점검합니다.
운영을 위해 0.0.0.0/0 모든 포트를 허용한다.
필요한 DNS·백업·배포의 대상·포트·업무 근거를 따로 작성합니다.

변경 전 예상 결과와 해석

공개 경로·데이터 경로·관리 경로가 분리된 그림과 흐름 허용표가 나옵니다.

이제 단계별로 바꾸고 관찰하기

  1. 자산의 공개 필요성부터 결정

    Web:443은 사용자 진입점, DB:5432는 Web에서만 필요한 데이터 경로로 그립니다. 인터넷→DB가 왜 필요한지 업무 근거가 없다면 거부 후보입니다.

    관찰할 결과
    공개 Web, 내부 DB, 관리 경로가 나뉜 구조도입니다.

  2. 최소 흐름 표 작성

    출발지·목적지·프로토콜·포트·목적·담당자를 열로 둡니다. Web→DB 5432와 관리 경로 외에도 DNS·백업·관측 경로를 별도 행으로 씁니다.

    관찰할 결과
    허용마다 목적과 검증 방법이 붙습니다.

  3. 차단과 장애를 함께 시험 설계

    사용자 정상 요청과 Web→DB는 유지되고 인터넷→DB는 거부되는지 확인할 테스트를 정합니다. 잘못 차단했을 때 설정 복구와 관리자 접근 유지 방법도 적습니다.

    관찰할 결과
    정상·거부·복구 세 종류의 검증 항목이 있습니다.
