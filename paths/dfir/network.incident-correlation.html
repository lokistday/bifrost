01 / UNDERSTAND

먼저 이해하기

DNS 질의, 방화벽 허용, 웹 응답은 서로 다른 관측입니다. DNS 성공은 이름 해석, allow는 해당 지점의 전달 정책, HTTP 401은 애플리케이션이 인증을 요구하거나 실패를 반환한 결과입니다. 어느 하나만으로 침해 성공이나 데이터 유출을 증명하지 않습니다.

표본은 R-17이라는 요청 ID가 각 자료에 연결되어 있다고 가정합니다. 실제 DNS와 방화벽 로그에 애플리케이션 ID가 자동으로 생기지는 않습니다. 주소·포트·시간·프록시 ID 등 연결 근거와 오차를 별도로 기록해야 합니다.

R-17의 세 기록을 시각순으로 정렬하면 resolved→allow→401입니다. 다른 R-18의 200을 같은 요청의 성공으로 합치지 않습니다. 비슷한 시간이나 같은 IP만으로 다른 요청을 섞으면 잘못된 사건 이야기를 만들 수 있습니다.

영향 판단에는 인증 성공, 리소스 접근, 전송량·데이터 범위, 호스트와 클라우드 증거가 더 필요합니다. 격리·차단을 검토할 때 서비스 영향, 증거 손실, 승인과 되돌리기 조건도 정합니다. 실습은 수동 판단 자료이며 자동 차단 도구가 아닙니다.

자주 헷갈리는 지점

같은 시간대의 HTTP 200을 모두 같은 요청에 합친다.
요청 ID나 다른 명시적 연결 근거를 먼저 검증합니다.
의심 IP 차단으로 대응이 끝난다.
업무 영향과 증거 보존, 관리 경로, 검증과 복구 조건을 함께 정합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

확인한 사실, 미확인 영향, 다음 수집 자료, 차단의 업무 영향과 복구 조건을 네 칸으로 쓰세요. 사본에서 R-17의 app 기록을 빼고 증거 불충분으로 바뀌는지도 확인합니다.

막혔을 때 힌트 보기

실제 기록과 가설을 나누세요. allow와 401만으로 유출 여부를 결론 내릴 수 없습니다.

과제 해설과 예시 답안 보기
  1. R-17의 이름 해석·전달 허용·401까지만 사실로 씁니다.
  2. 인증 우회·유출은 미확인으로 두고 해당 요청의 리소스·전송 기록을 요청합니다.
  3. app 제거 사본은 correlated=2와 insufficient_evidence인지 확인합니다. 차단 계획에는 관리 경로·영향·검증·되돌리기를 적습니다.

결과를 판단하는 기준

원본은 시도 관측·영향 미확인이고 app 제거 사본은 증거 불충분입니다. 401 하나로 다른 경로의 침해도 없었다고 단정하지 않습니다.
