01 / UNDERSTAND

먼저 이해하기

Windows 이벤트에는 화면의 번역된 설명 외에 Provider, EventID, Computer, EventRecordID, TimeCreated와 이름 붙은 EventData 필드가 있습니다. 같은 번호라도 공급자·채널·버전 맥락을 확인해야 합니다. 이 차시는 Event 구조를 닮게 만든 XML이며 실제 EVTX 바이너리를 파싱하지 않습니다.

EventData의 필드 위치는 고정 순서로 외우지 않고 Data의 Name 속성으로 찾습니다. 두 합성 기록은 IpAddress와 TargetUserName의 순서가 달라도 같은 이름의 값을 추출합니다. XML 네임스페이스가 있으므로 이름만 Event라고 검색하면 지원 레코드를 놓칠 수 있습니다.

표본의 4625는 실패, 4624는 성공 로그온 사례를 참고한 합성 이벤트이고 LogonType=3은 네트워크 로그온 맥락입니다. 성공 이벤트가 있다고 대화형 데스크톱 사용이나 특정 사람의 실제 의도를 증명하지 않습니다. 대상 계정·접속 정보·관련 로그를 함께 확인합니다.

EventRecordID는 모든 장비에서 유일한 사건 번호가 아닙니다. 이 파서는 한 컴퓨터/채널의 작은 합성 내보내기 안에서 중복을 검사합니다. 실제 통합 분석은 원본 출처·컴퓨터·채널·기록 ID를 함께 식별하고 UTC 정규화·보존 해시·획득 범위를 남겨야 합니다.

자주 헷갈리는 지점

4624를 사람이 직접 데스크톱에 들어온 증거로 단정한다.
로그온 유형·계정·관련 활동과 관찰 한계를 확인합니다.
이 XML 실습이 EVTX 획득과 파싱을 구현했다고 적는다.
제공한 신뢰 가능한 합성 XML의 원시 필드 해석만 수행합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

XML 사본에서 두 번째 이벤트의 Data 순서를 뒤집어 결과가 유지되는지 확인하세요. 그다음 EventRecordID를 같은 값으로 바꿔 단일 내보내기 안의 중복 검사를 확인하세요.

막혔을 때 힌트 보기

TargetUserName은 위치가 아니라 Name으로 찾습니다. 중복 거부는 이 단일 출처 표본의 규칙입니다.

과제 해설과 예시 답안 보기
  1. Data의 Name을 유지한 순서 변경은 추출 결과를 바꾸지 않습니다.
  2. 단일 컴퓨터/채널 안의 중복 ID는 오류로 기록하고, 오류 전 일부 출력으로 전체 성공을 주장하지 않습니다.
  3. 실제 여러 출처의 같은 EventRecordID는 가능하므로 컴퓨터·채널·출처를 포함한 복합 키와 관찰 범위를 적습니다.

결과를 판단하는 기준

이름 기반 추출·UTC 변환·단일 출처의 중복 범위와 실제 EVTX를 지원하지 않는다는 한계가 분명해야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
