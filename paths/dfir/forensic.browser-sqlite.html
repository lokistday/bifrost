01 / UNDERSTAND

먼저 이해하기

여러 응용 프로그램은 SQLite에 기록을 저장하지만 테이블 이름과 시간 기준은 제품·버전마다 다릅니다. 이 차시는 visits(id,time,url,transition)라는 독자 합성 스키마와 ISO 시간만 사용합니다. 실제 브라우저의 DB를 읽었다거나 특정 브라우저의 타임스탬프를 해석했다고 주장하지 않습니다.

casework.py browser는 신뢰하는 제공 history.sql을 메모리 DB에 넣은 뒤 auto가 아닌 행을 선택합니다. typed와 link 두 행이 표시되고 전체 세 행 중 하나를 필터링합니다. 표시 수와 전체 수를 함께 남겨 필터가 자료를 어떻게 줄였는지 추적합니다.

방문 기록은 URL이 처리되었다는 단서이지 사람이 의도적으로 페이지를 읽었다는 완전한 증명이 아닙니다. 자동 로드·리디렉션·동기화·프로필 공유 등이 해석에 영향을 줄 수 있습니다. 이 예제에서 transition은 제작자가 붙인 합성 분류이며 실제 사용자 신원을 증명하지 않습니다.

실제 SQLite 수집에서는 실행 중 파일 한 개만 복사하면 최근 트랜잭션이 WAL에 남아 누락될 수 있습니다. 원본·WAL·관련 파일과 수집 절차를 함께 검토하고 작업 사본에서 읽습니다. 본 실습은 메모리 DB라 WAL 획득·삭제 기록 복원·브라우저 개인자료 분석을 수행하지 않습니다.

자주 헷갈리는 지점

typed 한 행으로 특정 사람이 직접 입력했다고 확정한다.
스키마 의미·프로필·자동화·동기화 등 추가 근거를 확인합니다.
SQL 파일을 메모리 DB에 넣으니 어떤 출처든 안전하다고 생각한다.
제공한 신뢰할 수 있는 교육 SQL만 사용합니다. 메모리 DB는 임의 SQL의 안전한 샌드박스가 아닙니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

history.sql 사본에서 B03의 transition만 auto에서 link로 바꿔 다시 질의하세요. 전체 수와 표시 수의 차이를 설명하고, 기록만으로 말할 수 없는 사실 두 가지를 쓰세요.

막혔을 때 힌트 보기

입력 자료에서 필터 조건만 바꿉니다. 원본 URL을 열거나 실제 브라우저 프로필을 사용하지 않습니다.

과제 해설과 예시 답안 보기
  1. B03의 transition을 바꾸면 총 행수 3은 그대로이고 표시 수만 2→3이 됩니다.
  2. 방문 기록만으로 실제 사람이 내용을 읽었는지, 파일이 실행되거나 외부로 유출됐는지는 확정할 수 없다고 씁니다.
  3. 실제 DB에는 스키마·epoch·WAL 여부 확인이 별도 필요하며 이 실습에서 이를 수행하지 않았다고 표시합니다.

결과를 판단하는 기준

질의 조건·전체/표시 행수·제외 행 ID와 관찰 한계가 분리되어 있어야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.
