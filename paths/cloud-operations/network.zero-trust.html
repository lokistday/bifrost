01 / UNDERSTAND

먼저 이해하기

Zero Trust는 내부 네트워크 위치라는 이유만으로 신뢰를 부여하지 않는 설계 원칙입니다. 사용자·장치·리소스·행위·상태를 고려해 인증과 인가를 집행합니다. 망 분리는 피해 범위를 줄이는 수단이며 신원 검사를 대체하지 않습니다.

Web→DB의 포트 허용은 통신 가능성만 정합니다. 어떤 워크로드 신원으로 어떤 데이터 작업을 허용할지, 자격 증명이 만료·유출되면 어떻게 차단하고 감사할지 추가 설계가 필요합니다. 모든 요청을 무조건 차단하는 것과도 다릅니다.

Zero Trust는 특정 제품 이름이나 VPN 설치와 같은 뜻이 아닙니다. 보호할 자원과 요청 주체를 중심으로 접근 판단에 필요한 조건을 정하고 집행·관찰하는 접근 방식입니다. 내부 주소에서 왔다는 이유만으로 권한을 부여하지 않습니다.

정책을 결정하는 위치와 실제 요청을 허용·거부하는 위치를 나누어 생각하면 누락된 경계를 찾기 쉽습니다. 사용자 계정뿐 아니라 Web 워크로드가 DB에 접근하는 신원도 필요합니다. 신원을 증명해도 모든 테이블·관리 작업을 허용할 이유는 없습니다.

조건에는 주체·대상·작업·장치 상태·세션 상태·위험 정보를 넣을 수 있습니다. 어떤 정보를 계속 확인할지는 서비스 특성과 비용·가용성을 고려해 설계합니다. 자격 증명 유출·만료·정책 시스템 장애 때의 거부와 복구 동작도 정의해야 합니다.

자주 헷갈리는 지점

신원 확인을 했으니 인가는 필요 없다고 한다.
누구인지 확인한 뒤에도 어떤 대상에 어떤 작업을 할 수 있는지 별도 결정합니다.
장애 때 전체 권한을 영구 개방한다.
긴급 경로의 최소 범위·승인·만료·감사·원복 조건을 정의합니다.

변경 전 예상 결과와 해석

네트워크·신원·리소스 권한·관측을 분리한 접근 판단표를 만듭니다.

이제 단계별로 바꾸고 관찰하기

  1. 두 주체를 따로 정의

    Web→DB는 서비스 신원, 관리자→Web은 사람 신원으로 구분합니다. 각각 필요한 최소 작업과 대상 범위를 적습니다.

    관찰할 결과
    서비스용 읽기/쓰기 역할과 관리자의 배포·진단 권한이 분리됩니다.

  2. 판단과 집행 연결

    네트워크 포트, 주체 인증, 리소스 권한을 각각 누가 확인하는지 적습니다. 하나라도 빠졌을 때 어떤 요청이 과하게 허용되는지 반례를 만듭니다.

    관찰할 결과
    인증·인가·경계 필터·감사 역할이 분리된 판단표입니다.

  3. 만료와 장애 조건 검증

    정상 신원, 만료 신원, 잘못된 대상, 관리되지 않은 장치, 판단 시스템 장애의 기대 동작을 작성합니다. 긴급 복구도 승인·기록이 남아야 합니다.

    관찰할 결과
    정상/거부 테스트와 만료·장애 대응이 함께 있습니다.

네트워크 연결 가능성과 DB 신원·작업 권한은 별도입니다. 실제 최소 권한을 추가 검증해야 합니다.

2. Zero Trust에 가장 가까운 판단 방식은?

정답과 이유 읽기

정답: 주체·대상·작업·조건을 검증하고 집행·기록

네트워크 위치만으로 암묵적 신뢰를 주지 않고 자원 접근에 필요한 인증·인가·관측을 설계합니다.

내 결과물 확인하기

  • 내부 위치와 신뢰를 동일시하지 않았다.
  • 신원·인가·로그가 연결되는 설계를 만들었다.

위 기준을 결과물로 확인한 뒤 완료로 표시하세요. 다음 차시를 잠그지 않습니다.
