01 / UNDERSTAND

먼저 이해하기

비밀번호 검증에는 원문 복구가 필요하지 않습니다. 공격자의 대량 추측 비용을 높이는 전용 KDF와 사용자별 salt를 사용합니다. salt는 공개 저장할 수 있고 같은 비밀번호도 서로 다른 결과를 갖게 해 사전 계산의 재사용을 줄입니다.

예제의 scrypt 매개변수와 고정 salt는 동작 관찰용이며 운영 권장값이 아닙니다. 실제 시스템은 현재 지침·하드웨어 성능·응답 시간에 맞춰 검증된 라이브러리와 설정을 선택하고 알고리즘·비용·salt를 함께 기록해 재해시를 지원합니다.

비밀번호는 사용자가 고르는 경우 후보 공간이 작을 수 있습니다. 공격자는 저장된 검증값을 얻으면 후보를 반복 계산해 맞는지 시험할 수 있습니다. KDF의 비용은 각 추측의 시간·메모리 부담을 높이는 역할을 합니다.

salt는 사용자별 새 값으로 만들고 검증값과 함께 저장할 수 있습니다. salt가 다르면 같은 비밀번호도 다른 결과가 되어 미리 만든 표와 계정 간 결과 비교의 재사용을 줄입니다. salt 자체를 비밀번호를 대신하는 비밀키로 취급하지 않습니다.

검증 시에는 저장된 알고리즘·매개변수·salt로 입력 후보를 다시 유도해 비교합니다. 로그인 성공 시 오래된 비용을 새 정책으로 재해시하는 식의 이전 계획이 필요합니다. 실제 선택은 최신 지침·검증된 라이브러리·서버 응답 예산에 맞추며 이 예제의 숫자를 운영 기준으로 복사하지 않습니다.

자주 헷갈리는 지점

salt를 숨기기만 하면 약한 비밀번호도 안전하다고 한다.
salt는 사전 계산의 재사용을 줄이는 값이며 비밀번호 강도·KDF 비용·요청 제한은 별도입니다.
동작 실험의 scrypt 숫자를 최신 운영 권장값이라고 소개한다.
현재 지침과 라이브러리를 확인하고 하드웨어·응답 예산에 맞춰 측정합니다.

    비용을 올리면 공격자의 추측뿐 아니라 정상 로그인과 서버 자원에도 부담이 생깁니다. 실제 환경에서 측정·용량·요청 제한·이전 계획이 필요한 이유를 씁니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

같은 비밀번호·같은 salt와 같은 비밀번호·다른 salt의 결과를 설명하세요. 비용을 올리면 서버와 공격자 양쪽에 어떤 영향이 있는지 적습니다.

막혔을 때 힌트 보기

salt는 비밀번호에 붙이는 비밀키가 아닙니다. pepper를 쓰는 설계라면 별도 비밀 관리가 추가됩니다.

과제 해설과 예시 답안 보기
  1. same_salt=True와 other_salt=False를 KDF 입력의 결정성으로 설명합니다.
  2. 사용자별 salt는 사전 계산 재사용을 줄이지만 개별 비밀번호 추측 자체를 막지는 못한다고 적습니다.
  3. 비용 변경의 시간·메모리·동시 로그인 영향, 매개변수 저장과 재해시 계획을 씁니다.

결과를 판단하는 기준

salt·비용·검증값·원문 비밀번호의 역할이 나뉩니다. 실습 매개변수와 고정 salt를 운영 권장값으로 제시하지 않습니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

1. 서로 다른 salt를 사용하면 같은 비밀번호의 KDF 결과는?

정답과 이유 읽기

정답: 대개 달라지며 계정 간 미리 계산한 결과 재사용을 줄인다.

salt는 유도 입력을 다르게 만들어 같은 비밀번호도 다른 검증값을 갖게 합니다. 공개 가능한 값이며 기밀성을 주는 암호화 키가 아닙니다.

2. KDF 비용을 올릴 때 함께 확인해야 하는 것은?

정답과 이유 읽기

정답: 정상 로그인 지연·메모리·동시 요청 용량·이전 계획

비용은 방어자 서버에도 적용됩니다. 현재 지침과 실제 성능을 측정해 서비스가 감당할 설정과 재해시 전략을 정해야 합니다.

내 결과물 확인하기

  • KDF·salt·일반 해시의 차이를 설명했다.
  • 예제 값을 운영 권장값으로 오인하지 않았다.
