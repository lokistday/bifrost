01 / UNDERSTAND

먼저 이해하기

평소 경로가 장애이거나 계정 침해 대응이 필요한 상황을 위해 긴급 접근을 설계할 수 있습니다. 이는 항상 켜 둔 무제한 관리자 계정의 다른 이름이 아닙니다. 필요 주체·승인·목적·자원·행동·기간과 사후 검토를 미리 정해야 합니다.

표본의 responder는 training-service에 ReadHealth·RestartService만 10:00 이상 10:15 미만으로 허용됩니다. 10:14:59는 허용하지만 정확히10:15는 만료입니다. 시간은 timezone을 포함한 실제 시각으로 비교하고 분을 버리지 않습니다.

일찍 권한을 회수해야 하면 revoked 상태를 켜서 남은 기간과 관계없이 거부합니다. 실제 공급자의 세션·정책 변경은 전파 지연이나 토큰 수명·주체 유형에 영향을 받으므로 JSON 표시만 바꿔 즉시 회수했다고 주장하지 않습니다. 기존 세션으로 거부되는지도 허용된 방법으로 검증해야 합니다.

승인·활성화·수행 행동·회수·사후 검토 기록을 연결하면 긴급 권한이 왜 필요했고 무엇을 했는지 설명할 수 있습니다. 이 모형의 approved_by는 이름 표시일 뿐 승인자 인증이 아니고 실제 세션·MFA·불변 감사·복구 계정 보관을 구현하지 않았습니다.

자주 헷갈리는 지점

긴급 계정을 영구 최고 권한으로 방치한다.
범위·기간·승인과 사후 검토를 설계합니다.
표시만 바꾸고 권한 회수를 완료 처리한다.
기존 세션과 실제 거부·전파를 검증합니다.

먼저 수정하지 않은 원본으로 아래 기준 예제를 확인하세요. 원본 폴더를 보관하고 전체 폴더의 작업 사본에서 다음 변경 단계를 진행합니다. 아래 예상 결과는 변경 전 기준입니다.

처음 상태의 전체 예제

터미널 명령 · 이 분야의 작업 사본 폴더 · 로컬 파일 실습 · Python 3.10 이상

B1 ALLOW_MODEL
B2 DENY_TIME
B3 DENY_SCOPE

이제 단계별로 바꾸고 관찰하기

  1. 만료와 범위 비교

    시간 만료 B2와 행동 범위 밖 B3가 다른 이유로 거부됩니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 로컬 파일 실습 · Python 3.10 이상

  2. 만료 전 회수

    모형은 revoked를 가장 먼저 확인하지만 실제 전파 지연은 구현하지 않았습니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · 로컬 파일 실습 · Python 3.10 이상

    DENY_REVOKED

  3. 다른 주체 요청 거부

직접 바꾸고 확인하기

lease.revoked=true 사본에서 B1이 즉시 모형상 거부되는지 확인하세요. 실제 운영에서 회수가 적용되었음을 입증할 시험과 보관할 다섯 종류의 증거를 작성합니다.

막혔을 때 힌트 보기

시작 포함·만료 제외입니다. 유효한 시간 안이어도 주체·자원·행동이 맞아야 합니다.

과제 해설과 예시 답안 보기
  1. revoked 사본의 B1은 DENY_REVOKED임을 확인합니다.
  2. 실제 운영은 기존 세션의 제한된 거부 시험·전파 시각·정책 변경 기록으로 회수 적용을 검증한다고 적습니다.
  3. 승인 티켓·활성화 시각과 주체·행동 로그·회수 증거·사후 검토를 같은 사건 ID로 연결합니다.

2. 운영에서 정책을 바꿨습니다. 회수 완료의 근거는?

정답과 이유 읽기

정답: 기존 세션 거부·전파 시각·감사 기록을 검증한다.

실제 시스템은 전파·세션 동작이 다르므로 효과와 증거를 확인해야 합니다.
