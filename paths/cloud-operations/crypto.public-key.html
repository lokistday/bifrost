01 / UNDERSTAND

먼저 이해하기

공개키 암호화는 수신자의 공개키로 보호하고 수신자의 개인키로 복호화하는 역할을 생각할 수 있습니다. 디지털 서명은 서명자의 개인키로 만들고 그 서명자의 공개키로 검증합니다. 이를 단순히 개인키로 암호화한다고 설명하면 목적과 알고리즘 차이를 놓칩니다.

실제 프로토콜은 공개키로 대용량 데이터를 직접 처리하기보다 대칭키와 결합하는 경우가 많습니다. 공개키가 진짜 상대의 것인지 신뢰하는 방법도 필요합니다. 수학적으로 맞는 검증과 올바른 사람의 키로 검증했다는 사실은 별도 조건입니다.

기밀 전송은 수신자에게만 읽히게 하는 목적이고 서명은 메시지가 특정 서명 키로 만들어졌는지 검증하는 목적입니다. Ed25519는 서명 알고리즘이므로 공개키로 암호화·개인키로 복호하는 API가 아닙니다. 목적에 맞는 알고리즘을 구분합니다.

서명 검증에는 메시지·서명·검증 공개키가 필요합니다. 메시지가 한 바이트 바뀌거나 서명·공개키가 달라지면 검증이 실패해야 합니다. 검증이 성공해도 공개키가 실제 Alice의 것인지 신뢰하는 경로가 없으면 Alice의 신원을 확정할 수 없습니다.

개인키는 서명 주체만 비밀로 보관하고 공개키는 배포할 수 있습니다. 키 교체 뒤 오래된 기록 검증을 위해 어떤 키가 어느 시점의 어떤 목적에 쓰였는지 식별할 기록이 필요합니다. 서명은 내용을 숨기거나 재전송을 자동 차단하지 않습니다.

자주 헷갈리는 지점

서명을 “개인키로 암호화”라고만 설명한다.
서명·검증 목적과 알고리즘을 분리하고 암호화 API와 혼동하지 않습니다.
서명된 메시지는 누구도 읽을 수 없다고 한다.
서명은 내용을 숨기지 않습니다. 기밀성이 필요하면 별도의 암호화 설계가 필요합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

공개키가 공격자의 것으로 바뀌었을 때를 그려 보고, 신뢰 경로와 키 교체 시 기록 검증 방침을 적으세요.

막혔을 때 힌트 보기

서명 알고리즘과 암호화 알고리즘을 동일한 연산처럼 취급하지 않습니다.

과제 해설과 예시 답안 보기
  1. 기밀 전송의 수신자 Bob 키와 서명자의 Alice 키 역할을 정확히 나눕니다.
  2. 원본만 VALID이고 메시지·서명·키 변경은 INVALID인지 기록합니다.
  3. 신뢰할 키 배포와 교체·폐기·과거 서명 검증의 조건을 적고 서명이 암호화가 아님을 설명합니다.

결과를 판단하는 기준

실제 서명 검증을 재현하고 공개키 대체 시나리오에서 잘못된 신원 신뢰가 생기는 이유를 설명합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

1. Alice의 Ed25519 서명을 검증하는 데 사용하는 키는?

정답과 이유 읽기

정답: Alice의 검증 공개키

서명은 서명자의 개인키로 만들고 그에 대응하는 공개키로 검증합니다. 기밀 전송에서 수신자 키를 사용하는 역할과 다릅니다.

2. 공격자의 키로 만든 서명이 그 공격자 공개키로 VALID입니다. 이 사실만으로 Alice가 서명했다고 할 수 있나요?

정답과 이유 읽기

정답: 불가능하다. 검증 키를 Alice와 연결하는 신뢰 근거가 필요하다.

서명 검증은 주어진 키와의 수학적 관계를 확인합니다. 공개키가 누구에게 속하는지는 별도 신뢰 경로로 확인해야 합니다.

  • 공개키 진위 확인이 필요한 이유를 적었다.
