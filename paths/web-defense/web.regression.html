01 / UNDERSTAND

먼저 이해하기

회귀 테스트는 수정 후 이전에 되던 기능이 깨지지 않았는지 확인합니다. 보안 테스트는 거부 사례만으로 부족합니다. 본인 자료 조회는 성공하고 다른 사람 자료 조회는 실패해야 합니다.

demo.py의 assert는 기대가 틀리면 실행을 중단합니다. assert는 실습 검증 도구이며 운영 권한 검사를 assert로 구현하라는 뜻은 아닙니다. Python 최적화 실행에서는 assert가 제거될 수 있습니다.

보안 수정의 통과 기준을 먼저 적습니다. 이 예시에서는 정상 이름 조회는 한 행, 없는 이름과 SQL 구조처럼 보이는 값은 바인딩 조회에서 0행, 본인 자료는 허용, 타인 자료는 거부입니다. 기대값을 함수 결과에서 다시 계산하면 같은 오류를 양쪽에서 복제할 수 있습니다.

테스트가 실제 결함을 잡는지도 확인해야 합니다. can_read를 항상 True로 만든 사본은 타인 접근 거부 테스트에서 실패해야 합니다. 그 뒤 복구해 다시 통과시켜야 실패가 도구나 환경 문제 때문이 아니라 변경 때문이라고 설명할 수 있습니다.

assert는 학습용 기대값 검증에 편리하지만 운영 요청의 접근 거부를 대신하는 제어 흐름으로 쓰지 않습니다. 정상 정책은 명시적 조건과 오류 응답으로 구현하고, 테스트는 그 동작을 외부에서 검증합니다. 테스트 개수보다 실제 입력 경계와 실패를 잡는 근거가 중요합니다.

자주 헷갈리는 지점

assert를 서버 인가 로직 자체로 사용한다.
운영 제어 흐름은 명시적으로 처리하고 테스트의 assert는 별도 검증에 사용합니다.
PASS 문자열을 실패 가능성이 있는 테스트보다 먼저 출력한다.
모든 검증을 끝낸 뒤 통과 메시지를 출력하고 고의 오류에서 도달하지 않는지 확인합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

can_read를 항상 True로 바꿔 테스트 실패를 관찰한 뒤 복구하세요. SQL 정상 입력 테스트까지 추가하고 수정 전·후 결과를 README로 정리합니다.

막혔을 때 힌트 보기

실패해야 할 테스트가 계속 통과한다면 실제 함수를 호출하는지 확인하세요. 구현을 그대로 복사한 기대값은 오류를 잡지 못합니다.

과제 해설과 예시 답안 보기
  1. 원본 통과 → 항상 True인 고의 오류에서 실패 → 함수 복구 후 통과의 세 결과를 순서와 명령으로 기록합니다.
  2. permissions.csv의 네 행을 기대 결과로 두고 소유자 맵을 통해 함수에 전달합니다. SQL은 alice·bob 한 행, nobody·제공 payload 0행을 확인합니다.
  3. README에는 원인, 수정 이유, 정상 기능 유지, 거부 사례, 모델의 한계를 적습니다. None 등 누락 입력은 앞 차시 확장 모델과 별도 테스트임을 표시합니다.

결과를 판단하는 기준

고의 오류에서는 AssertionError가 나고 PASS가 출력되지 않아야 합니다. 복구 후에는 모든 기대값이 맞고 최종 PASS가 나와야 합니다.
