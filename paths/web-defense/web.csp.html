01 / UNDERSTAND

먼저 이해하기

CSP는 문서가 불러오거나 실행할 수 있는 리소스의 출처 등을 브라우저에 지시합니다. XSS 위험을 줄이는 추가 층이지만 입력을 안전하게 출력하는 코드와 서버 인가를 고쳐 주지는 않습니다. 허용 출처에 공격자가 파일을 올릴 수 있다면 단순한 self 허용도 별도 검토가 필요합니다.

Content-Security-Policy 헤더는 집행 정책을, Content-Security-Policy-Report-Only는 위반 관찰을 위한 정책을 전달합니다. 보고 전용 헤더를 설정했다고 스크립트 실행을 차단한 것으로 기록하면 안 됩니다. 실제 보고 수집도 별도의 설정과 검증이 필요합니다.

예제의 default-src는 지정하지 않은 여러 리소스 지시문의 기본값이고 script-src는 스크립트 정책입니다. object-src none은 플러그인 객체, base-uri none은 base URL 변경, frame-ancestors none은 문서를 삽입할 상위 프레임을 제한합니다. 모든 지시문이 default-src로 대체되는 것은 아닙니다.

이 체크리스트는 다섯 개의 고정 문자열과 unsafe-inline 포함 여부를 확인합니다. 일반 CSP 파서도 브라우저도 아니어서 중복 지시문·문법·nonce·해시·리다이렉트 등의 실제 의미를 완전하게 해석하지 않습니다. CHECKLIST_PASS는 표본 체크리스트 충족만 뜻합니다.

실제 사이트에 정책을 넣을 때에는 필요한 정상 스크립트·스타일·이미지·폼을 먼저 목록화하고 단계적으로 검증해야 합니다. nonce나 해시 기반 정책도 고려합니다. 이 실습은 response-policy.txt를 읽는 오프라인 검토이며 Bifrost의 응답 헤더를 변경하지 않습니다.

자주 헷갈리는 지점

Report-Only를 설정하고 스크립트가 차단된다고 주장한다.
보고 전용은 집행 정책과 다릅니다. 헤더 이름과 실제 위반 관찰을 구분합니다.
문자열 체크리스트 PASS가 모든 CSP 문법과 XSS 방어를 증명한다고 믿는다.
이 검사는 고정 표본의 항목만 확인합니다. 실제 파싱·브라우저 집행·안전한 출력 처리는 별도로 검증합니다.

변경 전 예상 결과와 해석

고정 체크리스트 통과·보고 전용·검토 필요를 분리하고 실제 브라우저 집행은 검증하지 않았다고 출력합니다.

이제 단계별로 바꾸고 관찰하기

  1. 집행·관찰·검토 상태 비교하기

    csp 모드는 같은 기본 정책의 헤더 이름을 바꾸거나 script-src에 unsafe-inline을 추가한 세 사례를 비교합니다. 마지막 줄이 실제 브라우저 검증 미실시를 명시합니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 web_controls.py csp
    관찰할 결과
    enforced=CHECKLIST_PASS
report-only=REPORT_ONLY
inline=REVIEW
browser_enforcement=NOT_TESTED

  2. 헤더 파일과 체크 항목 연결하기

    response-policy.txt의 다섯 CSP 지시문을 찾아 역할을 적습니다. nosniff·Referrer-Policy·Content-Type·CORS 헤더는 CSP와 다른 역할의 설정입니다. 파일 자체는 응답 서버 설정이 아닙니다.

    터미널 명령 · 이 분야의 작업 사본 폴더 · Python 3.10 이상 · 오프라인 웹 정책 모형
    python3 -c "from pathlib import Path; print(next(line for line in Path('response-policy.txt').read_text().splitlines() if line.startswith('Content-Security-Policy:')))"
    관찰할 결과
    Content-Security-Policy: default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'

  3. 필요한 지시문이 빠진 사본 확인하기

    고정 체크리스트에서 base-uri를 제거하면 REVIEW가 나와야 합니다. 이 결과는 실제 브라우저 취약성의 확정 판정이 아니라 검토 항목이 빠졌다는 의미입니다.

    Python 부분 코드 · 앞 단계의 변수·객체를 유지한 같은 스크립트 · Python 3.10 이상 · 오프라인 웹 정책 모형
    from pathlib import Path
from web_controls import review_csp
line = next(s for s in Path("response-policy.txt").read_text().splitlines()
            if s.startswith("Content-Security-Policy:"))
policy = line.split(": ", 1)[1].replace("; base-uri 'none'", "")
print(review_csp("Content-Security-Policy", policy))
    관찰할 결과
    policy_probe.py로 저장하고 python3 policy_probe.py로 실행하면 REVIEW입니다.
03 / TRY IT YOURSELF

직접 바꾸고 확인하기

정책 사본에서 base-uri를 제거한 경우와 헤더 이름을 Report-Only로 바꾼 경우를 비교하세요. 실제 배포 전에 확인할 정상 리소스 세 가지와 브라우저 검증 항목을 적으세요.

막혔을 때 힌트 보기

default-src가 frame-ancestors나 base-uri까지 대신한다고 가정하지 마세요. 체크리스트 결과와 브라우저가 실제로 적용한 정책은 별도 근거입니다.

과제 해설과 예시 답안 보기
  1. 기본 정책에서 base-uri none만 빼면 REVIEW, 동일한 기본 정책을 Report-Only로 넘기면 REPORT_ONLY임을 확인합니다.
  2. 정상 JavaScript·CSS·이미지의 출처와 인라인 사용 여부를 기록하고, 실제 HTTPS 환경에서 개발자 도구의 응답 헤더·콘솔 위반·기능 동작을 검사할 계획을 세웁니다.
  3. 보안 보고에는 체크리스트 통과와 실제 집행 확인을 구분하고, XSS의 원인인 출력 컨텍스트 처리도 유지해야 한다고 적습니다.

결과를 판단하는 기준

REVIEW와 REPORT_ONLY를 다른 원인으로 설명합니다. 정상 기능 검증 계획과 실제 브라우저 집행 미검증이라는 한계를 함께 기록해야 합니다.

학습 기록: 사용한 환경과 명령 → 바꾸기 전 예상 → 실제 결과 → 차이의 이유를 남기세요.

1. CHECKLIST_PASS와 browser_enforcement=NOT_TESTED가 함께 나왔습니다. 올바른 해석은?

정답과 이유 읽기

정답: 표본 체크 항목은 충족했지만 실제 브라우저 집행은 확인하지 않았다.

실습 도구가 확인한 범위를 넘겨 주장하지 않습니다. 실제 HTTP 응답·브라우저 동작·정상 기능을 추가 검증해야 합니다.

2. 동일 정책을 Content-Security-Policy-Report-Only로 전달하면?

정답과 이유 읽기

정답: 정책 관찰에 쓰이며 그 헤더만으로 실행 차단을 주장할 수 없다.

집행과 보고 전용은 목적이 다릅니다. 실제 보고 수집과 집행 정책은 각각 설정하고 확인해야 합니다.

내 결과물 확인하기

  • CSP 지시문·헤더 이름·집행 범위를 구분했다.
