01 / UNDERSTAND

먼저 이해하기

테스트는 정해진 입력에서 함수가 약속한 값을 내거나 정해진 예외를 내는지 확인하는 실행 가능한 기록입니다. 기대값을 실제 함수로 다시 계산하면 구현의 같은 오류를 복사할 수 있으므로 사람의 요구 사항에서 독립적으로 정합니다.

test_data_tools.py는 정상 범위 0·30·1440, 거부 범위 -1·1441, 문자열·불리언·실수 등의 타입, 문서 구조, 선택 경계를 검증합니다. 입력 목록을 나누는 이유는 실패했을 때 숫자 경계인지 타입 계약인지 좁혀 볼 수 있기 때문입니다.

unittest의 assertEqual은 고정된 예상 결과와 실제 결과를, assertRaises는 특정 예외가 발생했는지 확인합니다. 테스트의 이름과 subTest의 입력값은 실패 원인을 찾는 단서입니다. 테스트용 검증을 운영 입력 검사의 대체로 사용하지 않습니다.

테스트를 통과한 뒤 >=를 >로 고친 사본을 다시 실행하면 minimum=30 사례가 실패해야 합니다. 이 실패 실험은 경계 테스트가 해당 결함을 실제 검출하는지 확인합니다. 일부러 결함을 넣어도 통과하면 호출 대상과 기대값을 먼저 점검합니다.

모든 테스트의 통과는 준비한 사례에 대한 결과입니다. 큰 파일·중복 키·성능·모든 운영체제의 동작을 증명하지 않습니다. 새 결함을 발견하면 재현 입력과 기대 동작을 추가하고, 기존 정상 동작도 다시 검사하는 방식으로 범위를 넓힙니다.

자주 헷갈리는 지점

통과 메시지만 보고 테스트가 결함을 잡는다고 단정한다.
작은 고의 결함에서 실제 실패하는지 확인한 뒤 복구합니다.
실패를 없애기 위해 요구 사항 검토 없이 기대값을 바꾼다.
독립 기대값의 근거를 먼저 확인하고 구현과 요구 사항 중 어디가 틀렸는지 판단합니다.

03 / TRY IT YOURSELF

직접 바꾸고 확인하기

작업 사본에 >= → > 결함을 넣고 실패를 기록한 뒤 복구하세요. test_minutes_boundaries에 1을 추가하고, test_minutes_rejections에 1440.0을 추가해 타입 계약도 유지되는지 보세요.

막혔을 때 힌트 보기

수정한 파일이 실제 import되는 작업 폴더인지 확인하세요. 실패를 없애려고 기대값을 False로 고치면 요구 사항이 사라집니다.

과제 해설과 예시 답안 보기
  1. 두 파일을 작업 폴더에 함께 복사하고 원본 상태의 4 tests, OK를 먼저 기록합니다.
  2. 비교 연산자 한 곳만 바꾼 뒤 test_selection_boundary가 실패하고 최소값 동등 사례의 실제값이 False인 점을 기록합니다.
  3. 구현을 복구한 뒤 정상 입력 1과 거부 입력 1440.0을 추가합니다. 1440.0은 수치가 같아도 계약이 요구한 int가 아니어서 ValueError여야 합니다.

고의 결함에서 실패 → 복구 후 통과의 두 결과를 남깁니다. 입력 사례를 늘려도 검사 메서드 수는 여전히 4일 수 있습니다. subTest 수와 메서드 수를 혼동하지 않습니다.

1. >=를 >로 바꿨는데 테스트가 모두 통과했습니다. 우선 확인할 것은?

정답과 이유 읽기

정답: 테스트 실행 파일과 import 경로, 동등 경계의 기대값이다.

결함에 민감한 입력이 호출되지 않았거나 다른 파일을 실행했을 수 있습니다. 실제 호출 대상과 경계 사례부터 확인합니다.

2. 정상 수치 1440과 실수 1440.0은 이 계약에서 같은가요?

정답과 이유 읽기

정답: 아니다. minutes는 정확히 int여야 하므로 실수는 거부한다.

업무 계약이 정확한 타입을 요구합니다. 값이 수학적으로 같다는 사실만으로 허용 자료형이 같아지지는 않습니다.
